# Feature Specification: Libraries

**Spec ID:** 0001-libraries
**Status:** Draft
**Owner:** if
**Domain:** commons

**Input:** A repository of commons is many libraries, each a folder with a manifest and a package. A person who adds one, or changes one, needs the repository to know it: the manifest read as data and held against the folder, the libraries a change touches found without running them all, the workflows of GitHub Actions written as typed TypeScript and made into the files GitHub reads, the pinned Bun that runs them, the packer that builds a library for npm with its declarations and refuses one without, and the commands that hold the whole repository to Mizan: the check of its specifications, change control, versions, the register of proofs and the ontologies it publishes. This library is those tools, as a package of their own.

## The libraries of a repository

- **FR-001**: A library MUST be a folder `commons/<name>/` with a manifest `library.ts` that is an object literal read as data and never run, naming the library, its conformance level, its spec kit, its `verify` command, its version, its `exports` and where it is published; the library MUST give the decoder of that manifest and the check that the manifest and its folder agree (the name of the folder is the package's name, the version is the package's and the record's, the `exports` are the package's, a registry of `distribution` is one of the two kinds), as commons 0027-commons-libraries FR-011 to FR-018 require.
- **FR-002**: The library MUST make, from the manifests, the section "The libraries" of commons 0027-commons-libraries (one requirement for each library, numbered from FR-101 for the life of the library) and the rows of those requirements in `enforcement.tsv`, and MUST fail with `--check` where either is not what the manifests make (commons 0027-commons-libraries FR-011).
- **FR-003**: The library MUST say which libraries a change affects: from the files of a change (since a revision, or named) it MUST give the libraries whose folder, or whose dependencies (the `link:`, `file:` and `workspace:` entries of `package.json` and the packages their imports reach through `exports`), changed, as a matrix a workflow reads, and for a library the folders and files it reads, one a line (commons 0027-commons-libraries FR-019 to FR-022).

## The workflows

- **FR-004**: The library MUST model a workflow of GitHub Actions as typed values (the triggers, the jobs, the steps, the strategy, the permissions, the concurrency and the composite action), give `validateWorkflow` and `validateAction` (an action with no version, a job that needs a job that is not there, a step of no script) and render the YAML of a workflow and of an action as the same bytes for the same values, each beginning with a line that says it is generated and by what (commons 0030-generated-workflows FR-002 to FR-006).
- **FR-005**: The library MUST make, with one command, the files `.github/workflows/<name>.auto.yml` and `.github/actions/bun/action.yml` of a repository from the manifests of its libraries and the facts of their CI, MUST fail with `--check` where a file is not what the model makes, where a workflow is written by hand or where a library that is published to npm has no `tools/pack.ts` for its publish workflow to run, and MUST make the publish workflow of such a library idempotent: it checks the tag is the version, proves and packs the library, sends the tarball to the registries its manifest names unless the version is already there, and makes the tag of the version (commons 0030-generated-workflows FR-001, FR-004, FR-007 to FR-009).
- **FR-006**: The library MUST read the pins of commons (`commons/generated/pins.auto.env`) and install the pinned Bun on a runner: the release asset of the platform fetched with retries, kept only where its SHA-256 is the pinned one, unpacked by the zip reader of `formats` and put on the `PATH`, on Linux, macOS and Windows, with no shell script, no Python and no `unzip` (commons 0005-typescript-practice FR-026).

## The package

- **FR-007**: The library MUST give the packer of a library: from the manifest and the sources it builds the compiled modules and their declarations with the TypeScript 7 compiler, writes the `package.json` that is published (each entry with `types`, the source for Bun and the compiled file for the rest), inspects the package and packs it into `dist/<scope>-<name>-<version>.tgz`, and MUST fail where an export has no `types` condition or no `.d.ts` in the tarball, where a declaration imports a module that is neither in the tarball nor among the package's dependencies, or where a declaration names a `node:` module and the package has no peer of `@types/node` (commons 0032-libraries-by-concern FR-005 and FR-013).
- **FR-008**: The library MUST give the commands that hold a whole repository to Mizan, each reading every manifest, ontology and specification they need: `check` (a spec kit held to a conformance level, and with `--all` the `verify` of every library), `changes` (the change requests of a range and the rules of change control), `versions` (the records of the works and their versions, the tag and the ledger), `newer` (the standards that are newer than their pins), `oscal-register` (the register of requirements and proofs as OSCAL, current or not) and the generators of the ontologies of commons (their Turtle, OWL, RDF/XML, SHACL, JSON Schema, SSSOM, SKOS, SQL and HTML) (commons 0003-mizan, commons 0018-standards-first, commons 0020-ifccm, commons 0026-works-versioning, commons 0028-conformance-levels and 0012-ontology).
- **FR-009**: The library MUST keep the importers of standards, each a module that fetches or reads a standard at a pinned address and writes the typed module and the provenance of what it read, with `--check` for whether what is committed is what the standard gives (commons 0019-mizan-integrations).
- **FR-010**: The library MUST be published to npm as compiled modules with their declarations, one entry for the package and one for each tool above, and each of its commands MUST run as `bun commons/libraries/src/<command>.ts` in this repository.

## The development loop, the plan of CI and the release

- **FR-011**: The library MUST give a development loop, one command (`bun run dev:check` at the root), that finds the libraries the working tree changes since a revision (origin/main by default, the files not yet committed included) or that are named, and the libraries whose own sources import them, from the same planner as `affected` with the narrower reach of a library's own code (its folder and the packages its `about.ts` and `src/` import); that links the libraries of the repository under `commons/node_modules` so that a library imports another by its package name and reads the checkout's source, installs the packages that the root shares once and those a library has of its own; that type-checks each affected library with TypeScript 7, several at a time, and runs the tests of each in a `bun test` process of its own, several at a time; and that prints a short summary in the marks and colours of the terminal library (what it looked at, one line for each stage, what failed under it) and exits 1 where a stage failed. It MUST prove less than `verify` and say so, and never be the release.
- **FR-012**: The library MUST give the plan of CI, `plan.ts`: from the same planner (the reach of `verify`: what a library's `verify` reads and what depends on it) and the record of CI of each library, the cells of a matrix on Linux, one for each library affected, and the cells of a matrix on the systems besides Linux, one for each affected library whose record names one, as the outputs of a step a workflow reads; and the one workflow `ci` of this repository MUST be made from it (commons 0030-generated-workflows FR-006, FR-007), so that a push or a pull request runs `verify` and the tests on Node 26 for the libraries it affects, on Windows and macOS only for the libraries that have code of their own for them, and nothing else. The packing that `verify` ends with MUST be checked in a push only for the libraries that changed their `exports` since the base (a new library included) or where the packer changed, and in every cell of a run of everything; the release packs every library.
- **FR-013**: The library MUST give the one command of the release, `releasing.ts` (`bun run release` at the root), whose `plan` writes nothing and says what a release does and whose `apply` does it, with the rules of commons 0026-works-versioning FR-041: from the tags of each library and its files since its last tag (its folder and the paths its record adds) a library MUST be raised by the greatest of the `Impact:` of its commits since the tag (a patch where none states one) and the floor of FR-027, a breaking impact (`major`) raising the minor while the major version is 0 (SemVer 2.0.0 item 4) and the major from 1.0.0, a library that imports a library that is raised MUST be raised by at least a patch, a version that has no tag, or is ahead of its tag, MUST be released as it is only where npm does not hold it or holds it with the same files (the sources the package carries by their SHA-256, and the keys of its `exports`), and MUST be raised like a changed library where npm holds it with other files, or, where npm cannot be asked (`--offline`, or no answer), where files changed since the commit that raised its version; `--raise NAME[=IMPACT]` MUST raise a library whatever its state says, and `plan` MUST say for each library whether it is released as it is, raised, left alone or not released, and why (FR-026), a version tagged and unchanged MUST be left alone, a version below its last tag and a cycle of imports MUST be errors, and the steps MUST be in the order of the imports. A library with no record of its own is released by its manifest and its package.
- **FR-014**: `apply` MUST write the new version into the record, the manifest and the package of each library it raises, then refresh the lockfile of every library it releases (an install in its folder that may change the lockfile, never a frozen one), then make the generated files once (the section of the libraries, the packaging tables, the ontologies, the workflows and the register) and run `repoctl sync`, then run the tests that pack every library, install it from its lockfile and type-check a consumer (`tests/release/`) unless it is told not to, and write the record `commons/generated/release.auto.json` (the libraries to publish and tag, in order, with no day and no person), so that a version change never leaves a stale lockfile or a stale generated file for the tests to find; it MUST NOT publish, tag or commit; `matrix` MUST read the record and give the workflow what is not tagged yet.
- **FR-015**: The library MUST make, with the generator of its workflows, the one release workflow `release.auto.yml` (commons 0030-generated-workflows FR-009): run by hand from main, it plans from the record, proves and packs each library in a matrix, and, only where asked to publish, sends the tarballs in the order of the record to npm (trusted publishing with provenance, or the secret `INFRO_NPMJS_TOKEN` where the repository has it) and to the GitHub package registry, skipping a version a registry has, and makes the tags with the runner's token.

## Families and reserved names

- **FR-016**: The decoder of the manifest MUST read the optional field `family` (a `host`, a library name, and a `role` of `host`, `dialect` or `plugin`), and the check of the manifests MUST find, as one sentence each: a library whose name a reservation holds and whose family is not the host the reservation names (the reservations are data of the library, an exact name or a prefix with the host that may hold it, and hold `archon`, `archon-*`, `signing`, `gitops` and `estate`, with no folder); a host that is not named as its family; a dialect or plugin whose host is not a library that declares role `host` and a `kanon` table; a name the host's family rule does not read as its role; a member the host's table does not declare, and a member the host's table declares that no library declares; a member whose `kanon` table does not extend the host; and a library whose name the family rule of a host reads as a member and that declares no family.

## The map of the libraries in the README

- **FR-017**: The library MUST make, from the manifests and the `summary` of each library's `about.ts` (read as data, no library run), the table of the libraries in the root `README.md` between the markers `<!-- libraries-map:begin -->` and `<!-- libraries-map:end -->` (`readme.ts`, exported as `./readme`): one row for each library, sorted by role (foundation, pattern, program, standard) and then by name, with the package (linked to npm where it is published there), the first clause of the first sentence of its summary, its Kanon shape where its manifest declares a table, its level and its registries; it MUST name a library that has no role as a problem, MUST fail with `--check` (and write nothing) where the README is not what the manifests make, and `verify` and the tests of the repository MUST run that check.
- **FR-018**: The root `README.md` MUST describe what is and nothing that was: it MUST NOT contain the words formerly, previously, legacy, deprecated, backward, migration, UAT, acceptance test or agora, and every link of it whose target is a path in the repository MUST name a file or folder that exists.

## The license

- **FR-019**: The library MUST make and check the license files of the repository (`license.ts`, exported as `./license`; commons 0035-licensing FR-004 to FR-007 and FR-010, FR-012): the `LICENSE` of the root and of every library folder from the one official text in `src/license/` and the required notice, and `THIRD_PARTY_NOTICES.md` from the record of what is vendored; `--check` MUST write nothing and exit 1 naming each file that is not what they make, a library with no `LICENSE` among them and the command that writes it; its `verify` and the development loop MUST run it; and the packer MUST write the identifier of the library's license as the `license` of the package it publishes and MUST pack its `LICENSE`.

- **FR-020**: A manifest MAY declare `versionConstants`, a list of the constants of the library's sources that say its own version, each a `file` from the library's folder and the `name` of the constant (`ERGONEX_VERSION`); `apply` MUST write the new version into each of them, together with the record, the manifest and the package, and MUST stop with a sentence naming the file where it is missing or does not say the constant as `NAME = "<version>"`, so that no constant is left behind at the version a library had.

- **FR-021**: A number of the section of the libraries MUST belong to one library: where two libraries hold the same number in the specification (two branches each gave the next number to a library and a merge kept both), the first in the section MUST keep it and the second MUST be given the next number after the greatest, so that the generator makes the section and the rows again with one number for each library.
- **FR-022**: A manifest MAY declare `publishes`, a package of commons (`@intellectual-frontiers/<name>`), and `bundle`, one of `commons`, `foundation`, `patterns`, `programs` and `standards`, equal to the library's own name; the decoder MUST refuse a `publishes` that is no package of commons, a `bundle` that is not the library's name and a manifest that has both. The release (the plan, the record and the publication) MUST use the package the manifest publishes (commons 0036-distribution FR-005, FR-009).
- **FR-023**: The library MUST make the metapackages of commons (`metapackages.ts`, `pack-metapackage.ts`, exported as `./metapackages` and `./pack-metapackage`): the members of each set from the manifests and `ROLE_OF`, their exact dependencies written to `dependencies.auto.json` (`--check` writes nothing and exits 1 where a file is stale), and the tarball of a package with no code, which passes the inspection of every library's package; and the release MUST raise a metapackage after the libraries it depends on whenever one of them is raised (commons 0036-distribution FR-006 to FR-008).
- **FR-024**: A manifest MAY declare `held`, the one typed reason not to release the library, an object of a closed set of kinds with a required text on one line: `{ kind: "tests-only", reason }` (a tool of tests that nothing depends on at run time), `{ kind: "unfinished", reason, missing, liftedWhen }` (`missing` names at least one part that is not done, `liftedWhen` the condition that lifts the hold) and `{ kind: "owner-blocked", reason }` (a decision of the owner that the text states); the decoder MUST refuse any other kind, any other field, a text that is empty, padded or of more than one line, a bare sentence in place of the object, and `held` together with `publishes` or `bundle`, and MUST accept any `distribution` with it (the rule of FR-015 of commons 0027-commons-libraries, at least one registry including `github`, holds only where `held` is absent). A held library MUST be left out of the facts of the release (so of the record, of `apply` and `publish` and of the tags), out of every set of the metapackages, and shown as not released with its kind in the README table; it MUST still be verified, packed and proved like any other library, and `repoctl status` MUST show it as `held`.
- **FR-025**: The check of the manifests (`libraries.ts --check`, which `repoctl check`, `repoctl sync` and CI run) MUST fail where a library that declares a spec kit is not listed in `specKits` of `commons/docs.config.ts`, naming the library and the line to add, and `repoctl new library` MUST list the spec kit of the library it makes, so that the site and the tests that read the configuration are not found red after a push; a repository with no such file is asked nothing.
- **FR-026**: A library MUST be released unless its manifest carries a hold (FR-024): `release plan` MUST say for each library with a hold that it is not released, with the kind and the sentence of its hold (what is missing and what lifts it, where it is unfinished), for each of the others whether it is released as it is, raised, or left alone, and why, and `--raise` of a library with a hold MUST be refused with its reason.
- **FR-027**: The plan MUST give each raised library a floor read from the keys of `exports` of the version npm holds (the last tag of a changed library, the version itself of one that is ahead of its tag and that npm holds with other files) against the keys of its package now: a key removed or renamed MUST raise it by at least the breaking level (`major`: the minor while the major version is 0, the major from 1.0.0), a key added by at least the feature level (`minor`), the greater of the floor and the `Impact:` of its commits MUST win, and the plan MUST state the reason; where npm does not hold the version, cannot be asked (`--offline`) or does not answer there MUST be no floor, never a guess. The floor sees the keys of `exports` and nothing behind them: a type, a signature, a default or a behaviour that changed under an unchanged key, a key that now points elsewhere, and an export of a file the package does not list are not seen, so that the `Impact:` of the commits remains how a breaking change under a key is declared.

## Acceptance scenarios

1. **Given** a folder `commons/x/` with a manifest, **When** the section of the libraries is made, **Then** it holds one requirement for `x` and its row, and `--check` fails where either differs, per FR-001 and FR-002.
2. **Given** a change to a file of one library, **When** the affected libraries are asked for, **Then** that library and each that depends on it are in the matrix and no other, per FR-003.
3. **Given** the typed workflows of the repository, **When** the generator runs with `--check`, **Then** each file is what the model makes and a hand-written workflow is a finding, per FR-005.
4. **Given** a library that is published to npm, **When** the packer runs, **Then** every export has its declaration in the tarball and a consumer type-checks against it, per FR-007.
5. **Given** a change to a file of one library, **When** `bun run dev:check` runs, **Then** that library and the libraries whose own sources import it are type-checked and tested, and nothing else, per FR-011.
6. **Given** a push, **When** the workflow `ci` runs, **Then** its plan names the libraries the push affects, a library that is not affected has no job, and the systems besides Linux are asked for only by a library whose record names them, per FR-012.
7. **Given** libraries tagged and unchanged, a library whose files changed since its tag and one that imports it, **When** `releasing.ts plan` runs, **Then** the first two are raised and the importer by a patch, and the unchanged are left alone, per FR-013.
8. **Given** a release made by `apply`, **When** the release workflow is run from main and asked to publish, **Then** the libraries are published in the order of the record, skipping what a registry has, and tagged, per FR-014 and FR-015.
9. **Given** the repository, **When** `check --all` runs, **Then** the `verify` of every library runs and a failing one fails the run, per FR-008.

10. **Given** a library named `archon-dialect-x` that declares no family, **When** the manifests are checked, **Then** a sentence names the library and the host it may be held for, per FR-016.
11. **Given** a host whose table declares a dialect and a library of that dialect's name that declares its family, **When** the manifests are checked, **Then** there is no finding, and for a dialect nobody registered or a registered one nobody declared there is one, per FR-016.
12. **Given** a folder `commons/x/` with a manifest and no `LICENSE`, **When** `license.ts --check` runs, **Then** it exits 1, names `commons/x/LICENSE` and the command `bun commons/libraries/src/license.ts`, and running that command writes the file, per FR-019.
13. **Given** a library whose manifest names the constant `X_VERSION` of `src/v.ts` and is raised by `apply`, **When** its version is written, **Then** the constant holds the new version, and a missing file or constant is a sentence that names it, per FR-020.
14. **Given** a section in which two libraries hold one generated number, **When** the section is made again, **Then** the first keeps it and the second has the next number after the greatest, per FR-021.
15. **Given** a manifest with `publishes: "@intellectual-frontiers/arcactl"` and a manifest whose `bundle` is not its name, **When** they are read, **Then** the first gives its package to the release and the second is refused, per FR-022.
16. **Given** the manifests of this repository, **When** the metapackages are made, **Then** each set holds the libraries of its role at their versions and the files are what the manifests make, per FR-023.
17. **Given** a manifest with a typed `held` and `distribution: []`, **When** it is decoded, the plan of a release is made and the sets are made, **Then** it decodes, the library is in no fact of the plan and in no set, the plan names it as not released with its kind and reason, and `held` with `bundle`, a bare sentence or an unknown kind is refused, per FR-024 and FR-026.
18. **Given** a library whose `package.json` gained a `link:` dependency its lockfile does not have, and a library it imports that changed, **When** `apply` runs, **Then** the lockfiles of the libraries it releases are refreshed before the tests that install from them, which pass, per FR-014.
19. **Given** a library with a spec kit that `commons/docs.config.ts` does not list, **When** the manifests are checked, **Then** the check fails naming the library and the line to add, per FR-025.
20. **Given** a library tagged at `0.3.1` whose last published version has the key `./old` that its package does not have, and commits that state a patch, **When** `release plan` runs, **Then** the library is raised to `0.4.0` and the plan says that an export was removed or renamed, per FR-027.

## Out of scope

- The harness, its rules and its levels: `mizan`; the ontologies: `ontology`; the Git hosts: `githost`; the test evidence: `quality` and `test`.

## Edge cases

- A manifest that is not a literal, has two exports or an unknown field: refused naming the field, per FR-001.
- A library with a dependency that is not a library of the repository: not in the matrix, per FR-003.
- A workflow file written by hand under `.github/workflows/`: a finding, never deleted, per FR-005.
- A runner with no network for the pinned Bun: the installer fails with the pinned address and the SHA-256 it wanted, per FR-006.

## Assumptions

- Every library of the repository is a folder of `commons/` with a `package.json` of the same name.

## Open questions

- None.

## Key entities

- **Manifest** - the data `library.ts` holds about a library.
- **Matrix** - the libraries a change affects, as a workflow reads them.
- **Model** - the typed values a workflow is written in.
- **Packer** - the program that builds, inspects and packs a library.

## Success criteria

- **SC-001**: A person adds a library by adding a folder and running one command, and the workflows, the requirements and the package of it follow.
