# Feature Specification: IFC Mizan Integrations

**Spec ID:** 0019-mizan-integrations
**Status:** Draft
**Owner:** if
**Domain:** commons
**Part of:** 0003-mizan

**Input:** IFC Mizan Integrations (`commons/ts/mizan/integrations/`) is the module of Mizan's extensions and plugins that brings outside ontologies and schemas into Intellectual Frontiers' typed TypeScript form, and turns ours into reusable, well-known ontologies, so that a harness takes standards instead of coining terms (`0018-standards-first`), and a consumer that is not TypeScript reads standard forms of what we state.

## The module

- **FR-001**: The module MUST live in `commons/ts/mizan/integrations/` and be exported as `@intellectual-frontiers/commons/ts/mizan/integrations`, in two layers: `pure/`, functions over text with no effect on the host, and `host/`, which fetches, reads and writes files and checks pins.
- **FR-002**: An integration MUST be a typed record: its id, its direction (`import` or `export`), the formats it reads and writes, the `Standard` it handles, and a `run` that returns a `Result` of its output or its findings; a registry MUST look integrations up by their formats. There MUST be no `any` and no non-null `!`, and a `switch` over a union MUST be exhaustive.
- **FR-003**: Mizan's own checks (the requirement syntax, the standards-first rules) MUST be plugins through the same extension point, so that a harness can add its rules without a fork.
- **FR-004**: The kernel MUST stay free of readers (0012-ontology FR-007); every reader of an RDF syntax or of a schema language MUST be in this module.

## Import

- **FR-005**: An import MUST be made only where a term or schema a specification uses is not already available, and MUST name the slice it needs (a manifest of terms, with an optional closure), never a whole standard.
- **FR-006**: An import MUST refuse a source whose SHA-256 or license differs from its `Standard` record, and MUST write a generated `.auto.` TypeScript module (a typed vocabulary, class schemas and code lists) whose header names the source, version, hash, license and generator, and whose terms have the basis `adopts`.
- **FR-007**: An import MUST report what the typed form cannot hold (a blank node, an RDF list, a restriction) as a finding, and MUST NOT drop it silently.
- **FR-008**: The graph a generated module writes, in canonical N-Triples, MUST equal the source's graph for the imported slice (0012-ontology FR-013).
- **FR-009**: Each import MUST leave its provenance as PROV-O Turtle beside its manifest (the module a `prov:Entity` generated by an import, a `prov:Activity` that used the source, a `prov:Entity` named by its SHA-256 with its title, publisher, version, location and license): what was imported, from where, by which generator and with which hash, and no date or host, so that the same import gives the same text.

## Export

- **FR-010**: The module MUST write our ontology as Turtle, N-Triples, N-Quads and JSON-LD (the kernel's writers), and as SHACL shapes and JSON Schema (from class schemas), SKOS concept schemes (from code lists), SQL code-list tables, SSSOM mappings (from terms that name a standard's term and the relation to it, each justified as manual curation), an HTML view of an ontology (its classes, properties, code lists and the basis of each term, one self-contained page, so that it can be read without TypeScript), and OWL, RDF/XML and a DCAT entry for each published ontology (FR-016 to FR-019).
- **FR-011**: Each export MUST be read or checked by an independent tool in a test (an RDF parser for the RDF forms, a SHACL validator for shapes, a JSON Schema validator for schemas).
- **FR-012**: The module MUST NOT publish anything to an outside project; where one of our terms could improve a standard, it MUST only prepare a proposal bundle for a person to decide on.

## Languages

- **FR-013**: The module's code MUST be TypeScript 7 where it can be, and the best stack for the job through a typed `Exception` where it cannot (0017-two-languages FR-003, FR-004); a TypeScript part MUST run on Bun and on Node 26, and an exception's tests run on the platforms it names.
- **FR-014**: An import's source MAY be a URL (`https://`, or `http://` on the loopback address for a test), fetched once and held to the SHA-256 pin of its manifest; the manifest names the version in the URL, never `latest`. `--check` MUST compare, offline, the manifest's pin and slice to the module's header and terms and the presence of the provenance file; with `--fetch` it MUST fetch the source and compare the module and the provenance fully, and it MUST exit 2, naming why, where the source cannot be fetched.
- **FR-015**: The module MUST import a slice of an OSCAL control catalog (NIST SP 800-53, FedRAMP baselines) from its JSON as a generated TypeScript module of a typed code list whose keys are the control identifiers (`ac-2`, `ac-2.1`), each with its title, its group and, for an enhancement, the control it enhances, and the type of those identifiers; the catalog's JSON MUST be read once into typed records, its title, version and OSCAL version MUST be in the module's header, and the refusals and the determinism of FR-006 apply. It MUST take identifiers and titles only, never the prose of a control, and a control the catalog lacks MUST be named.
- **FR-016**: The module MUST write an ontology's triples as RDF/XML 1.1 in one canonical form (each subject once as an `rdf:Description`, `rdf:type` first and the other predicates by IRI, objects in the order of their N-Triples terms, the same bytes whatever the order the triples were stated in), such that an RDF/XML parser reads the same graph as the Turtle; what XML 1.0 cannot say (a predicate whose IRI has no XML name at its end, a control character in a literal) MUST be a finding and never silently changed.
- **FR-017**: The module MUST write an ontology's classes and properties as OWL 2 in functional syntax, deterministically: a declaration of each class, object property and data property (and of each class or datatype they name that the ontology does not define, and of each annotation property OWL 2 does not build in that is used), `SubClassOf`, the domain and the range of each property, and the annotations `rdfs:label`, `rdfs:comment` and `skos:definition`, with the ontology's label, description, version information and version IRI. It MUST state only what the typed schemas state (no restriction, disjointness or cardinality), and a datatype property whose range is a class, or an object property whose range is a datatype, MUST be a finding.
- **FR-018**: The module MUST write a DCAT 3 catalog as Turtle for the ontologies a repository publishes: a `dcat:Catalog` of one `dcat:Dataset` for each ontology (title, description, its IRI as `dcterms:identifier`, `dcat:version`, `dcterms:license`, publisher), each with one `dcat:Distribution` for each generated file (title, `dcat:mediaType` and `dcterms:format` as the IANA media type's URI, `dcat:downloadURL`, `dcat:accessURL`, `dcterms:license` and, where a standard names the file's form, `dcterms:conformsTo`), with no date, so that the same catalog gives the same text; an IRI that does not parse and a media type that is not one MUST be findings.
- **FR-019**: Mizan's generator (`generate-ontology.ts`) MUST write the RDF/XML, the OWL and the catalog of the Mizan ontology as `commons/generated/mizan.auto.rdf`, `mizan.auto.ofn` and `mizan-catalog.auto.ttl`, each saying it is generated, which `--check` MUST find current; the catalog MUST list the distribution of every file the generator writes for the ontology, and a refusal of an exporter (FR-016 to FR-018) MUST stop the run with exit 2, naming it.

## Importers of JSON-LD, RDF/XML and JSON Schema

- **FR-020**: The module MUST read JSON-LD, in its expanded and its compacted form with an inline `@context`, into the same triples the Turtle reader gives: `@id`, `@type`, `@graph` and `@included`, the terms of a context given as an IRI, a compact IRI or an object (`@id`, `@type`, `@language`, `@container`, `@reverse`), `@vocab`, `@base` and `@language`, aliases of keywords, language-tagged and typed values (numbers and booleans as typed literals, a number's text deciding `xsd:integer` or `xsd:double`), `@list`, `@reverse` and nested node objects (blank nodes where there is no `@id`). Its JSON MUST be read once, by a reader that keeps each number's text and each object's line.
- **FR-021**: The JSON-LD reader MUST name, with its line, each construct it cannot hold and MUST NOT drop it silently: a remote context (a string, which the pure layer does not fetch), `@import`, a scoped context, a named graph, `@nest`, a JSON literal, a container of `@graph`, `@id` or `@type`, and a key that expands to no IRI; the rest of the document is still read.
- **FR-022**: The module MUST import a slice of the `$defs` of a pinned JSON Schema (draft 2020-12) as a generated TypeScript module in which each `enum`, `const` or `oneOf` and `anyOf` of constants is a typed code list (a `const` tuple and the union type of its members) and each object's properties, its own and those of its `allOf` branches and the definitions they `$ref`, are a typed object keyed by field name (the field's type, whether it is required, what it refers to) with the union type of the field names; an `enum` or an object inside a property is lifted to a code list or fields of its own. The slice names definitions, never the whole schema, a definition the schema lacks MUST be named, the refusals, the header (which also names the slice and the schema), the provenance and the determinism of FR-006 and FR-009 apply, and a definition with no enum and no properties MUST end the import.
- **FR-023**: The JSON Schema importer MUST name, with the definition and the path it is in, what a typed union of names cannot hold, and MUST NOT drop it silently: composition other than `allOf` of objects and references and other than constants (`anyOf`, `oneOf`), `patternProperties`, `additionalProperties` as a schema, `propertyNames`, `dependentSchemas`, `dependentRequired`, `if`, `not`, `unevaluatedProperties`, a `$ref` that is not into the schema's `$defs`, a schema of another draft (read as 2020-12) and the value constraints (`pattern`, `format`, bounds and lengths). Annotations (`title`, `description`, `default`, `examples`) are prose a person reads in the schema and are not carried.
- **FR-024**: The module MUST read RDF/XML into the same triples, as hand-written TypeScript: node and property elements, `rdf:about`, `rdf:ID`, `rdf:nodeID`, anonymous nodes, `rdf:resource`, `rdf:datatype`, `rdf:parseType` `Resource` and `Collection`, property attributes, `rdf:li`, `rdf:ID` reification, `xml:lang`, `xml:base` and relative IRIs resolved against it (RFC 3986), and of XML the entities a `<!DOCTYPE>` internal subset declares, character references, CDATA, comments and namespaces. It MUST refuse what is not well-formed XML with the line.
- **FR-025**: The RDF/XML reader MUST name, with its line, each construct it cannot hold and MUST NOT drop it silently: an XML literal (`rdf:parseType="Literal"` and the other parse types, whose canonical form it does not compute), an external or parameter entity, and an attribute with no namespace.
- **FR-026**: The vocabulary importer MUST take its source in Turtle, N-Triples, JSON-LD or RDF/XML (the manifest's `format` is `turtle`, `n-triples`, `json-ld` or `rdf-xml`), with the checks, the findings and the determinism of FR-005 to FR-009 unchanged; a relative IRI of JSON-LD or RDF/XML resolves against the location the standard is published at.
- **FR-027**: The manifest's `format` MUST also name `json-schema`, whose `slice` is `$defs` names and which needs no `namespace` and no `rdfImport`; `--check` MUST compare the slice a JSON Schema module's header names to the manifest's.
- **FR-028**: Each of the three readers and the JSON Schema importer MUST be checked in a test against an independent tool: the graph of a JSON-LD or an RDF/XML source equal to the graph rdflib reads from the same text, and the code lists and field names of a JSON Schema import equal to what `jsonschema` accepts and an independent resolution of the schema gives; where Python and these tools are not installed that test is skipped and says so.
- **FR-029**: A reader of an XML-based format MUST be hand-written TypeScript where it reads the real files of its format to the graph an independent tool reads, and MUST otherwise be the best tool for the job recorded as a typed `Exception` (0017-two-languages FR-003 and FR-004). The decision for RDF/XML is: no `Exception`, because the reader of FR-024 read twelve W3C RDF/XML files (the RDF syntax namespace, RDF Schema, OWL, SKOS core, PROV-O in two files, the organization ontology, DCAT 2, SHACL, OWL-Time, SSN and WGS84 position, 33 to 1,719 triples each, 8,848 in all, with `<!DOCTYPE>` entities, `rdf:ID`, `parseType` `Resource` and `Collection`, `xml:base` and datatypes) to a graph isomorphic to rdflib's, with the same triple count in each; an RDF/XML source it reads differently, or a format such as XSD that needs more of XML, MUST be taken to a pinned reader as an `Exception`.
- **FR-030**: Where a specification cites a control of NIST SP 800-53, the control MUST be imported, never typed by hand: the OSCAL catalog of the standard's tagged release MUST be fetched from its versioned URL, held to a pinned SHA-256, and sliced to the controls the specifications of commons cite, so that a control identifier a specification names is a key of the generated `controls` module; the first such import MUST be the slice of Rev. 5.2.0 for IFCCM, IFQS and IFWS (CM-2 to CM-10, SA-10, SI-7, IA-5).

## Out of scope

- What is standard: `0018-standards-first`.
- The RDF kernel's writers: `0012-ontology`.

## Edge cases

- An import that needs three terms of schema.org: only those, per FR-005.
- A source whose hash differs from its record: refused, per FR-006.
- A source with an OWL restriction: the term is written, and a finding names the restriction, per FR-007.
- A source with an RDF list in a field: a finding, per FR-007.
- A round trip that adds or loses a triple: the import fails, per FR-008.
- A slice that names `ac-2.1` and a control the catalog lacks: the missing control is named and nothing is written, per FR-015.
- A source whose bytes changed under the same URL: refused as a pin mismatch, with the pinned and the actual hash, per FR-006 and FR-014.
- `--check` with no network: compared to the header offline, per FR-014.
- A term of ours whose basis is `maps` to a NIST term: an SSSOM row, per FR-010.
- An exporter whose output no independent tool reads: not shipped, per FR-011.
- A term that could be proposed to schema.org: a bundle is prepared and nothing is sent, per FR-012.
- A JSON-LD file whose `@context` is a URL: the context is named as a finding and the terms it would define are not read, per FR-021.
- A JSON Schema definition that is a plain `{ "type": "string" }`: the import ends and names it, per FR-022.
- A JSON Schema property that is an `anyOf` of two schemas: named as a loss, the field name is still in the union, per FR-023.
- An RDF/XML property with `rdf:parseType="Literal"`: named and not read, the rest of the document is, per FR-025.

## Assumptions

- Hand-written parsers cover Turtle, N-Triples, JSON, JSON-LD and RDF/XML (FR-029 records the evidence for RDF/XML); XSD may need an `Exception` for a reader, decided when it is needed.
- The first sources are candidates until Phase 0 of issue #10 confirms their format, version and license: schema.org, DPV, PROV, OSCAL (NIST and FedRAMP), FHIR and US Core, NIEM, SPDX and CycloneDX.

## Open questions

- **OQ-1**: Which XML reader, if one is needed for XSD, becomes the first `Exception` (RDF/XML needed none, FR-029).
- **OQ-2**: Whether imports are kept in this repository or in the importing harness, per standard.

## Key entities

- **Integration** - an import or an export, typed.
- **Registry** - the lookup of integrations by format.
- **Slice** - the named part of a standard that an import takes.
- **ImportRecord** - the provenance of one import.

## Success criteria

- **SC-001**: A standard we use is imported, never hand-copied, and its generated module says where it came from.
- **SC-002**: Each export is read by an independent tool in a test.
