# Reuse audit: telemetry and reach

**For:** 0041-telemetry-and-reach. **Read:** this repository at the commit that carries this file, on 2026-11-26, by reading the code (manifests, exported names, the specifications beside them), not summaries. Nothing was run. Each row says what commons already has (with the file and the exported names), what is missing (the gap), and a decision: **reuse** (use it as it is), **extend** (the library that has it gains a requirement) or **new** (nothing exists). A requirement of 0041 and of every specification it governs cites the row it relies on (0041 FR-016).

Paths are under `commons/`. A name in backticks is an export. "Spec" names a specification of the library, as `0003-estate-logical FR-009`.

## The duplications to remove

None of these is a change of a wire unless it says so.

1. **`pae`**: `crypto/src/dsse.ts` `pae(payloadType, payload)` and `grc/src/signers/sshsig/mod.ts` `pae(payloadType, payload)` both write `DSSEv1 <len> <type> <len> <payload>`. Keep the first; `grc` imports it.
2. **Hash chain**: `ssh-server/src/logical/chain.ts` `chainNext`, `verifyChain`, `canonical` and `ssh-server/src/governance/session.ts` `GENESIS`, against `grc/src/logical/ledger.ts` `appendEntry`, `verifyLedger`, `GENESIS` (and `quality/src/pure/chain.ts` `verifyChain`, `data` `lifecycle/ledger.ts`). The audit log of the server becomes ledger entries; the audit event stays the `evidence` of an entry. No wire change (the chain is stored, not sent).
3. **Facts**: `ssh-server/src/governance/facts.ts` `Facts`, `decodeFacts`, `NicFact`, `HostKeyFact`, `DiskFact` and the two collecting scripts `ssh-server/src/logical/script-sh.ts`, `script-ps.ts`, against `machine-probe` `Observed`, `parseProbe`, `toObserved` and `physical/scripts/machine-probe.sh`, `.ps1`. `Observed` gains the identity facts; `Facts` is derived (`factsOf(observed)`); the bootstrap script text may be replaced by the probe's, which changes the script and not the conversation.
4. **Pins**: `ssh-server/src/logical/pins.ts` `OSQUERY_PINS`, `Pin`, `defaultPlan` against `toolchain` pins, the pins of the ontology (`pins.ts`) and `pinned-downloads`. One catalog.
5. **Identity resolution**: `ssh-server/src/logical/decide.ts` `resolveIdentity` against `estate/src/logical/discovery.ts` `unexpectedDevices` (MAC only). One function in `estate`.
6. **Rows of osquery**: `machine-probe/src/physical/run.ts` `query`, `Row` against `desired-os-state/src/logical/osquery.ts` `decodeRows`, `OsRow`.
7. **State store**: `ssh-server/src/physical/store.ts` `stateStore`, `fileStore` (one JSON file, whole rewrite, audit capped) against `anyfs` stores with `cas` and `append`, and the fleet store of `estate` (`openFleetStore`).
8. **Canonical JSON**: `ssh-server` `canonical`, `grc` `canonicalize`, `workload` `canonicalJson` (`governance/events.ts`). One.
9. **Observation and cadence**: two `Observation` types (B6) and two `Cadence` types (B7): bridged, not merged.
10. **Signature formats**: `grc` SSHSIG and DSSE envelope, `crypto/dsse`, and `anyfs/src/merge/signing.ts` (`ed25519:<key id>:<base64>` over a digest with a domain). Telemetry uses the first and creates no fourth.
11. **SSH signature verification**: `change-control/src/physical/keys.ts` (`ssh-keygen -Y verify`, namespace `git`) against `grc` pure SSHSIG verification (namespace `grc-evidence`).

## Where commons already covers something, and where it does not

Already covered, which a plan might have assumed missing: SSHSIG and DSSE signing and pure verification (`grc`); a hash-chained ledger (`grc`); an append capability (`anyfs`); a YAML writer (`formats` `toYaml`); identity resolution by machine id, serial, MAC and host key (`ssh-server`); the pins of osquery (`ssh-server`) and a pinned Collector (contrib, Linux x64, CI only); typed SNMPv3 transport policy and the class `network-device` (`integrations`); the reserved `tether`, forward policies and osquery `query` conversation (`ssh-server` 0006-reserved); a Windows probe script and a Windows enrollment script; promotion states and approvals (`estate`).

Assumed present and absent: any SSH forward (the server refuses them all; `headless` cannot write one); SNMP code (a type and a plan only); a UDP listener; client certificates (mTLS) and TLS in `serve`; protobuf; a semantic-convention table; a durable queue; MIME, RFC 5322 and SMTP; a Kanon `family` for `integrations`; machine id, MAC and host key in the probe's `Observed`; osquery tables for memory, load, uptime and interfaces; a Kanon table for `telemetry` (it is an L1 library with a pure entry and a host entry, not yet in the three layers).

## UNVERIFIED

- OpenTelemetry semantic conventions: many are `Development` and change between versions; the table pins one version and a policy (0041 spec, telemetry 0003).
- The OpenTelemetry Collector is 0.x: configuration keys and component names change between versions; the pin is exact.
- gNMI: not documented here and not relied on. No native OTLP export from network gear is confirmed for any device class.
- OpenSSH `permitopen` together with `restrict` and `port-forwarding` in `authorized_keys`, `ExitOnForwardFailure`, and `-L` on Windows OpenSSH: read from the OpenSSH manual, not run on a real host.
- Bun `fetch` with a client certificate and the same on Node 26.
- The names of osquery tables and columns for memory, load, uptime and interfaces: from the osquery schema, not read against the pinned version 5.24.1.
- Redfish telemetry and event models: not read; only the HTTPS JSON service root and the standard collections are assumed.
- That the custom `ocb` build of the relay can be published as our release and installed by `pinned-downloads` (F3).
