# Feature Specification: Commons libraries

**Spec ID:** 0027-commons-libraries
**Status:** Draft
**Owner:** if
**Domain:** commons
**Part of:** 0003-mizan

**Input:** Each top-level folder of commons that is a library (`commons/data` first) is independent: it keeps its own specifications in a spec kit of its own, numbered from 0001, its own package, its own documentation and its own checks, and it imports what it uses of commons by package name. A library declares itself with a manifest, `commons/<name>/library.ts` (its name, its conformance level, its spec kit, its verify command, its version and its exports); this repository knows a library as exactly one requirement, made from that manifest, whose proof is the library's own `verify`; every requirement under that one belongs to the library and is never numbered, listed or proved here. A library can therefore grow, be checked and be published on its own, while this repository still says that it exists, where it is and how to prove it, and registering one is adding a folder with a manifest.

## What a library is

- **FR-001**: A library of commons MUST be a top-level folder `commons/<name>/` that holds a spec kit of its own at `commons/<name>/spec-kit/` in the form 0003-mizan gives every harness (`registry.tsv`, `enforcement.tsv`, `mizan.baseline.txt` and `specs/NNNN-slug/spec.md`), a `package.json` whose name is `@intellectual-frontiers/<name>`, an `about.ts`, a manifest `library.ts` (FR-012) and a `verify` script, so that it is checked, tested and documented with nothing of commons but the packages it imports.
- **FR-002**: A library's specifications MUST be numbered from 0001 in its own registry, and its requirements MUST belong to it: this repository's registry (`commons/spec-kit/registry.tsv`) MUST NOT list a specification of a library, and a library's `enforcement.tsv` MUST have one row for each of its own requirements and none for a requirement of this repository.
- **FR-003**: A citation in a library's files (a `// Spec:` line, a `proves(` call, the `spec` of an ontology term) MUST be read against that library's spec kit alone, so that a slug both have (their numbers are independent) means the library's.
- **FR-004**: A library MUST import the packages of commons it uses by package name (0005-typescript-practice FR-076), and MUST NOT import by a relative path a file outside its own folder.
- **FR-005**: A library's `verify` script MUST run from the library's folder with no argument, and MUST fail if any of its parts fails: the TypeScript compiler on the library, the specification checker on its spec kit (`bun ../tools/mizan-check.ts --root spec-kit`), the Mizan rules on it at the level its manifest declares (`bun ../libraries/src/check.ts --root spec-kit`, with `--level` where the level is below L3, 0028-conformance-levels FR-013) and the library's tests.
- **FR-006**: A library's `verify` script MUST also run `tools/check.ts`, the trace of its sources and tests to its own specifications (0015-trace) and the check of its layers, whose findings are held by a baseline of its own (`trace.baseline.txt`).

## What this repository knows

- **FR-007**: This repository MUST know each library by its manifest (FR-012) as exactly one requirement of this specification, in the section "The libraries", named by the library's folder, whose enforcement is the library's own `verify` (a `check` row that runs `cd commons/<name> && bun run verify`); no requirement of a library MUST be a requirement of this repository (amended 2026-11-18: the requirement is made from the manifest, FR-011, and no longer written by hand).
- **FR-008**: A test of this repository MUST find every folder `commons/*` that has a manifest or a spec kit and fail where a spec kit has no manifest, where the section "The libraries" or its rows are not what the manifests make (FR-011), where a manifest and its folder disagree (FR-013), where a library lacks a part FR-001 names, where its `verify` lacks a part FR-005 names, where a file of the library imports by a relative path outside its folder (FR-004), or where the specification checker finds anything in its spec kit (amended 2026-11-18).
- **FR-009**: The documentation of commons (`commons/docs.config.ts`) MUST name each library's spec kit among its spec kits, so that the specifications of a library are published with those of commons and none is published twice.
- **FR-010**: Each library MUST be proved by the one workflow `.github/workflows/ci.auto.yml`, made from the manifests (0030-generated-workflows FR-006): it plans which libraries a push or a pull request affects and runs the `verify` of each of those, on every push and pull request that changes commons, on Linux and the runtimes 0005-typescript-practice names, and on Windows and macOS for the libraries whose record of CI names them; a library MUST NOT have a workflow of its own.

## The manifest

- **FR-011**: The section "The libraries" of this specification, and the rows of its requirements in `enforcement.tsv`, MUST be generated from the manifests by `commons/libraries/src/libraries.ts`: one requirement and one row for each library, numbered from FR-101 and keeping the number a library was given, between the markers `<!-- libraries:begin -->` and `<!-- libraries:end -->`; with `--check` it MUST write nothing and exit 1 where either file is not what the manifests make.
- **FR-012**: A library MUST declare itself with `commons/<name>/library.ts`, whose only export is `library`, an object literal of data that a program reads as data and never runs (0026-works-versioning FR-008 reads a record so): `name` (the last segment of its folder, FR-026), `level` (`L0`, `L1`, `L2` or `L3`; `L1` where it declares none, 0028-conformance-levels), `specKit` (the path of its spec kit from its folder, which a level above L0 MUST have), `verify` (the command that proves it, `bun run verify`), `version` and `exports` (the keys of the package's `exports`), and it MAY carry `summary`, `distribution` (FR-015), `kanon` (0033-kanon FR-010) and `family` (FR-023); an unknown field or a wrong type MUST be an error that names the field.
- **FR-013**: A manifest MUST agree with its folder: its `name` is the last segment of its folder or, for an extension of a host, its host's name and the folder's name joined by a hyphen (FR-026), the package is named `@intellectual-frontiers/<name>`, its `version` is the package's, its `exports` are the keys of the package's `exports`, its `verify` is a script of the package, its `specKit` has a `registry.tsv`, and the `verify` script runs the Mizan check with `--level` of its level where the level is L1 or L2; a test MUST fail where any of these differs.
- **FR-014**: Registering a library MUST be adding a folder `commons/<name>/` with its manifest, its package, its spec kit and its workflow, and running the generator (FR-011): no requirement of this specification is written by hand for it.

## Where a library is published

- **FR-015**: In `per-library` distribution mode (0036-distribution FR-019) a library MUST be published as a package of the GitHub package registry of this organization, public or private, named `@intellectual-frontiers/<name>`, and its manifest MUST declare it in `distribution` with the registry `github`; in `single` mode, the mode of this repository, every library MUST be published inside the one package `@intellectual-frontiers/commons` under its name (`@intellectual-frontiers/commons/<name>`, 0036-distribution FR-021), to the GitHub package registry, and its manifest MUST still declare its `distribution`, which the mode of the repository does not change.
- **FR-016**: In `per-library` mode a library MAY also be published to npm, which a decision about that one package makes, when it needs what npm gives and the GitHub package registry does not (installation with no token, discovery, trusted publishing); the library MUST remain published to the GitHub package registry as well, so that every package is available there. In `single` mode the one package is sent to the registries of `SINGLE_TARGETS` (0036-distribution FR-028), which is the GitHub package registry alone while the npm target is off.
- **FR-017**: A manifest MUST declare where its library is published in `distribution`, a list of registries from `github` and `npm`, each once, which is `["github"]` where the manifest declares none, and the section "The libraries" MUST name the registries in each requirement.
- **FR-018**: A manifest and this specification MUST name a registry by its kind alone (`github`, `npm`) and MUST NOT name the host of a private registry, a token or a credential; the configuration a consumer needs to install from a registry belongs in the consumer's own repository.

## What a change affects

- **FR-019**: A library's dependencies on other folders of commons MUST be read from its `package.json`, a dependency whose version is a `link:`, `file:` or `workspace:` path, and MUST NOT be written a second time in its manifest.
- **FR-020**: The inputs of a library, the files its checks read, MUST be its folder, `commons/tools/**`, `.github/actions/**`, the workflow `ci`, the entries of each dependency that its sources import (the file that the dependency's `exports` gives each import) and the paths to other folders that its scripts run, and every file that those files import by a relative path, followed file by file; an import that the dependency's `exports` does not give MUST take the whole dependency. The planner MUST recognize module references by syntax and conservatively include declared linked dependencies for unresolved computed imports.
- **FR-021**: `commons/libraries/src/affected.ts` MUST print, for the files changed (`--base REF` from Git, from the merge base with the head, or `--files`), the libraries they affect as `{"include":[{"name","folder","verify"}]}` in the order of the folders' names, where a library is affected if a changed file is among its inputs, and MUST print every library with `--all` and where Git cannot say what changed. What a library reads as an input includes, through the libraries it imports by package, every file they import in turn (and the whole folder where an import cannot be resolved), so that a library that depends on one that changed is affected by the files it reads and not by the dependency as a whole: a change to a file that nothing a library reads imports does not reach it, and the nightly run of every library is the backstop for what is read in a way no import shows.
- **FR-022**: The libraries that CI runs for a change MUST be the libraries this planner affects (0030-generated-workflows FR-006, FR-007), so that what CI runs and what the planner affects are the same, and the development loop (commons 0001-libraries FR-011) MUST read the same planner with the narrower reach of a library's own code: its folder and the packages its own sources import, which is what its types and its tests read.
- **FR-023**: A manifest MAY carry `family`, the `host` (a library's name) and the `role` of the library in that family (`host`, `dialect` or `plugin`), which is how a family of libraries (a host, a dialect for each tool and a plugin for each noun, 0033-kanon FR-019 to FR-021) is one thing to the register: the check of the manifests MUST hold the two sides of a family together, a member named as the host's `kanon` table's family rule reads it and declared by that table and registered by a manifest that names the host, a host named as its family and a member whose own table says `extends` the host's package.
- **FR-024**: The names that no library may take until the library they are held for exists MUST be reserved as data of the check of the manifests, each an exact name or a prefix with the host whose family may hold it, never by an empty folder: a library whose name a reservation holds MUST be refused by the check unless its manifest declares that host's family. The names held are `desired-os-state`, `desired-os-state-*`, `signing`, `gitops` and `estate` (intellectual-frontiers/.github#11). `content` and `content-*` are held for the host `content`, Kanon for content, until it exists (intellectual-frontiers/.github#22).
- **FR-025**: A library MAY have a folder named `acceptance`, `oat`, `uat` or `aat` of acceptance kits (testing by people or by agents acting as people, for the experience beyond the code, with synthetic data), each kit a folder of it and the folder having a spec kit of its own at `<folder>/spec-kit`. Such a folder is not a library: the check of the libraries, the documentation's list of spec kits and the library's trace MUST NOT treat it as one, and no specification of the repository or of the library MUST name a specification of a kit. The folder's own checks are run apart from the library's `verify`.

- **FR-026**: The folder of a library MUST follow from its manifest: where `family.host` names a host that has a folder of its own and the library is not that host, the library's folder is `commons/<host>/<extension>/`, `<extension>` being the library's `name` without its first segment `<host>-` (the plugin `anyfs-s3` of the host `anyfs` is at `commons/anyfs/s3/`, the dialect `desired-os-state-apt` of `desired-os-state` at `commons/desired-os-state/dialect-apt/`); any other library is at `commons/<name>/`. The `name` of a library is what the package, the exports and the importers use and MUST NOT change with its folder. Every program of this repository that needs the folder of a library MUST ask the one resolver of `commons/libraries` (`libraryDir`), which reads it from where the manifest is, and none MUST build `commons/<name>` from a name; a check MUST name a library that is not in the folder this requirement derives, and a library whose name starts with a host's name and declares no family.
- **FR-027**: The documentation site, the list of libraries of the repository and the page of the package MUST group the libraries: a host with its extensions as one family, and the libraries that belong to no host under the named `group` of their manifest where they declare one (`catalogs`, `linux`, `lab`), the group being a presentation only that moves no folder and changes no name. The libraries of Estate, Integrations and Planning are grouped in the documentation only, and their folders are not moved: the owner's rule is to move folders only where a real host exists, and their extensions (`estate-endpoints`, `estate-iac`, `estate-query`, the `integrations-*` libraries and `planning-query`) are not Kanon plugins of their hosts, whose tables declare no plugin; a library of such a group moves into the folder of its host only when its host's table declares it as a plugin or a dialect (0033-kanon FR-020).

- **FR-028**: Commons MUST hold no product code (IF Commons holds none): no tracked file of `commons/` (source, test, specification, documentation, example or fixture, but for generated tables and lockfiles) MAY name a product built on it, in any letter case. A product gives a library what it needs to say or create (a program name, an environment prefix, a state folder, an endpoint host, a user agent, a wire format) as a typed parameter such as a `Brand`, with a neutral default only where one is safe and none where the name is part of a protocol the product must choose; what a command line, an MCP server, a REST API, a terminal or a GUI shows of a product is in the product's own repository.
- **FR-029**: Accountability MUST have a boundary: every asset that a fleet holds MUST have a disposition (in scope in a role, inherited, external, out of scope with a justification, or undecided, which is a finding) in every boundary the fleet declares, and a boundary MUST be a typed, versioned, approved declaration of a kind that a regime defines (0045-boundaries); and every library that performs an active action on an asset (a scanner, a penetration test, an applier of state, an installer) MUST refuse a target that is not in scope of an approved boundary that allows the action, or that an approved boundary excludes, before it sends a packet or makes a change (0045-boundaries FR-090 to FR-094). The word `boundary`, unqualified, means this accountability scope in every specification, ontology term, type and test of commons; where a specification needs the place at which a program decodes its input it says `decoding edge`, and where it needs where assets are found it says `realm` (0044-asset-connections).

## Edge cases

- A folder `commons/<name>/spec-kit/` with no `library.ts`: found by the test, per FR-008.
- A manifest that names another folder, another version than the package's, or exports the package does not have: found, per FR-013.
- A manifest with a field it does not know, or `level: "L9"`: refused with the field named, per FR-012.
- A library at L0 with no spec kit: accepted, per FR-012.
- A manifest at L1 whose `verify` script runs the Mizan check at L3: found, per FR-013.
- The section "The libraries" edited by hand: `libraries.ts --check` names the file, per FR-011.
- A new library with a manifest and no generated requirement: found and written by the generator, per FR-014.
- A generated requirement that names `commons/nope`, which does not exist: not what the manifests make, found per FR-011.
- A specification of a library listed in this repository's `registry.tsv`: found, per FR-002.
- An `enforcement.tsv` of a library with a row for a requirement of this repository: the specification checker names it as a row for a requirement that does not exist, per FR-002.
- A library specification whose slug is also a slug here, cited by a library file: it means the library's, per FR-003.
- A library file that imports `../../core/src/mod.ts`: found, per FR-004.
- A library whose `verify` leaves out the specification checker: found, per FR-005.
- A library whose `verify` does not run `tools/check.ts`: found, per FR-006.

- A dependency by a registry version (`^1.0.0`) or outside commons: not a dependency on a folder of commons, per FR-019.
- An import of a dependency that its `exports` does not give: the whole dependency is an input, per FR-020.

## Assumptions

- `tools/check.ts` of a library is the library's own: `commons/data` reads its trace and layers with commons' kernel and runtime, and another library may keep a different check as long as its `verify` runs it under that name.
- A library imports another by package name through a path link (`link:../<name>` in its `devDependencies`): `link:` makes a symbolic link, which Node resolves to the real path, where `file:` makes a copy under `node_modules`, which Node 26 refuses to strip types from.
- Publishing is to the GitHub package registry for public and private libraries alike, and to npm as well only by a decision about one package; every consumer today is inside the organization, and installing from the GitHub package registry needs a token even for a public package, which is the reason a package that outsiders install is put on npm too (FR-016).

## Open questions

## Key entities

- **Library** - a top-level folder of commons with a manifest, a spec kit, a package, documentation and checks of its own.
- **Manifest** - `commons/<name>/library.ts`: the library's name, level, spec kit, verify command, version and exports, read as data.
- **Library spec kit** - `commons/<name>/spec-kit/`, numbered from 0001, whose requirements belong to the library.
- **Verify** - the one script that proves a library, which this repository's enforcement register names.

## Success criteria

- **SC-001**: A library can be checked, tested and documented from its own folder, and this repository's checks never read inside its spec kit except to run the specification checker on it.
- **SC-002**: This repository's register names every library as one requirement, and no requirement of a library appears in it.
