# Feature Specification: Documentation

**Spec ID:** 0011-documentation
**Status:** Draft
**Owner:** if
**Domain:** commons

**Input:** One documentation site for commons, published on GitHub Pages and read by developers, DevOps and other engineers, made entirely from what the code and the specifications already say: the module documentation and TSDoc of IFC TypeScript and the libraries built on it, their typed values (the models of a library built in layers, the programs built on headless, an `About` value for each area) and the spec kit. Nothing is written for the site alone except the guides (FR-032), and commons keeps no README: a module's documentation is its TypeScript, kept with the code in the same commit. The generator knows what each library is for and shows it: a data model is shown as a model in layers, with its entity-relationship diagram, its tables, the SQL of each dialect and its data governance, and a program as its verbs for each tier of its audience. It reads the code through the TypeScript 7.1 programmatic API and writes static HTML with no framework. The generator is the library `@intellectual-frontiers/docs`, which other repositories (a fleet repository, a company's monorepo) install from npm (0036-distribution), so that they build their own sites with it: each gives a typed configuration that names its packages, its spec kit and how its specifications are cited, and commons is built by the same package from its own configuration.

## The generator

- **FR-001**: The generator MUST be kept in `commons/docs/`, as the library Docs (docs 0001-docs, which is where its package, its command and its publication are specified): its sources in `src/`, its package `@intellectual-frontiers/docs`, and `dependencies` that are exactly `typescript` at `7.1.0-beta` (the first release with a programmatic API since 7.0, which the generator uses when it runs), `shiki` (which colours code when the site is built, FR-037) and `beautiful-mermaid` (which draws diagrams when the site is built, FR-037), the root package's `dependencies` carrying the same, pinned exactly with the lockfile `bun.lock` holding the integrity of each. Nothing outside `commons/docs/` MUST import a file of it but commons' own configuration, `commons/docs.config.ts` (FR-023); another repository installs the package from npm and runs its command `ifc-docs` (docs 0001-docs FR-003).
- **FR-002**: The generator MAY import the libraries `core`, `system` and `test` of commons by package name, `typescript/async` (the asynchronous client of the programmatic API, whose channel to the compiler runs under Bun and under Node; the synchronous one reads Node's own stream internals), `shiki` and `beautiful-mermaid` (FR-037), and, when it runs, the configuration and the modules it documents, and nothing else. The lenses commons' configuration passes (FR-026) are kept in `commons/docs/lens/`, MAY import the public entry points of the libraries whose models and programs a lens shows (`commons/data`, `commons/headless`) from commons' source, import the generator only through its library entry point (`mod.ts`), and are reached from none of the package's entry points (`.`, `ifc-docs`). It MUST be held to the rules of commons' TypeScript (0005-typescript-practice): only erasable syntax, no `any`, no non-null `!`, an expected failure as the kernel's `Result`, a tagged union matched by a `switch` that ends in `absurd`, `@module` on every file and TSDoc on every export, checked by the TypeScript compiler of the package.
- **FR-003**: `ifc-docs build [--out DIR] [--config FILE]` MUST write the site into DIR (by default the configuration's `out`, else `_site` at the repository's root, which Git ignores), and `ifc-docs check [--config FILE]` MUST build it into a temporary folder, report every finding of FR-018 as `where: message` on standard error, write nothing in the repository and exit 1 where there is one. Without `--config`, the configuration is the first `docs.config.ts` found from the working folder up to the repository's root (the first folder that holds `.git`). A command line or a configuration that is not valid MUST be refused with what is wrong and exit 2, before anything is read. In commons, `bun main.ts build` and `bun main.ts check`, run in `commons/docs/`, are the same commands from the source. The same sources MUST give the same bytes.

## The sources

- **FR-004**: Every page MUST be made from two sources alone: the repository's TypeScript, as its configuration names it (module documentation, TSDoc, `About` values, example files and the values of models and layouts), and its spec kits (in commons, `commons/spec-kit/`; FR-024 for the plain layout, whose constitution is a page). The site MUST NOT be made from a Markdown file written for it, and commons MUST NOT keep a `README.md` of its own, a library's `README.md` beside its `package.json` (`commons/<library>/README.md`, the page its package shows) being that library's, and the `README.md` of an acceptance kit (`commons/<library>/acceptance/README.md` and `commons/<library>/acceptance/<kit>/README.md`, 0027-commons-libraries FR-025, or the same under `oat`, `uat` or `aat`), a walk-through for a person that the site does not show, being that kit's; the root `README.md` of the repository (a short pointer to the site, kept by hand) and `profile/README.md` (the organization's page on GitHub) are not commons' and are not sources.
- **FR-005**: An area is a part of a library with an entry point. Each library MUST have an `about.ts` at its root that exports `about`, a value of the `About` type of the library `core` (`@intellectual-frontiers/core/about`): its title, a summary, the specification it implements, its folders with what each may import, its commands, its rules with what enforces each, and its areas, each with its entry points, its specification, its phases and its examples. No entry point MUST export `about.ts`, and commons as a whole MUST have `commons/about.ts`, with its summary and its folders. Another repository MAY keep `about.ts` files the same way, or give each package's `About` value in its configuration (FR-027).
- **FR-006**: The documentation of a module MUST be TSDoc: the module's comment (which says `@module`) begins with what the module is, and MAY go on with `@remarks` (the longer account), `@example`, `@see` and `@limits`, this repository's own block tag, which says plainly what the module does not do or does only in part. An export's comment MAY carry `@param`, `@returns`, `@example`, `@see` and `@deprecated`. Prose in TSDoc and in specifications is the Markdown of FR-016.
- **FR-007**: A limit, a guarantee or an account of how a part works MUST be written in the module of the code it is about, not in another file. A change to code MUST change its documentation in the same commit.
- **FR-008**: A fact with a shape (a table of folders, of commands, of rules, of phases, of what a dialect's catalog compares) MUST be a typed value, in `about.ts` or in the module that uses it, not a table written in prose, so that a test can hold it to the code.

## The pages

- **FR-009**: The site MUST have four sections, and leaves out one that has no page (Models, where the configuration passes no lens). Overview: a home page from the configuration's home (in commons, `commons/about.ts`) with a card for each capability (its specification's title, `**Input:**` and `**Part of:**`), and a page for each area from its entry point's module comment and its `about`, with the limits of the area's modules gathered from their `@limits`. Specifications: FR-015. API: FR-010 to FR-012. Models: FR-013, FR-014, FR-029 and FR-030. Libraries: FR-031 and FR-033. Guides: FR-032. Code and diagrams: FR-037.
- **FR-010**: The API of an area MUST be read through the TypeScript 7.1 programmatic API (`typescript/async`) from the area's entry points: every export, an alias followed to what it names, a namespace walked into, with its kind (function, constant, type, interface, class or namespace), its signature as the checker prints it, and its TSDoc. The area MUST have a page for each source file its exports come from, in the order the entry point exports them, with an anchor for each export.
- **FR-011**: A citation in documentation MUST become a link to the specification's page: the repository's own prefix and a specification of its spec kit (`commons NNNN-slug` in commons), a bare id of the repository's own form (a number of the digits its configuration gives, four in commons and three in a repository of three digits, then a slug: `096-bun-runtime`), `FR-nnn` after either, and a bare `FR-nnn` in an area, which names a requirement of the area's specification. A specification of a repository the configuration lists as linked MUST become a link to its page on that repository's site (FR-025); a specification of any other repository (in commons, `erga 009-machine-bootstrap`) MUST be shown as text and never linked: a site may be public where the others are not.
- **FR-012**: `{@link name}` MUST become a link to the export of that name in the same area, or to the export of an area that is named (`{@link data!table}`), or, where no area is named and the same area has no such export, to the one export of that name in any area; a name that is unknown, or that more than one other area exports, is a finding.
- **FR-013**: A lens MUST be a typed value (the package's `Lens` type, FR-026) that a configuration passes, which reads what is its library's and makes its pages in the Models section after the order it is given; a lens that has nothing to show makes none. Commons passes the guides lens (FR-032), the releases lens (FR-035), the layered-model lens for the data models (FR-029) and the program lens (FR-030).
- **FR-014**: What a lens cannot describe (an entity with no description) MUST be a finding of the build that names the entity.
- **FR-015**: The spec kit MUST give a page for each specification in force, with its title, status, owner, domain and part (where its layout has them), an anchor for each requirement and each success criterion, beside each requirement its row of `enforcement.tsv` (mechanism and who) or, in the plain layout, of its `reviewed.tsv` (FR-024), each edge case linked to the requirements it cites, and for each requirement the pages that cite it; a page of the register; and a matrix of every requirement with its mechanism and who enforces it.

## The output

- **FR-016**: The generator MUST turn the Markdown of TSDoc and of specifications into its own page model, a tagged union of blocks and inlines, and MUST read only this subset: paragraphs, headings, lists, emphasis, code, fenced code with its language, links, and tables. Anything else is shown as its text.
- **FR-017**: Every page MUST be a static HTML file whose links are relative, so that the site works under any path (it is published at `https://intellectual-frontiers.github.io/.github/`). A page MUST NOT request anything from another host: its stylesheet, its one script and the search index are files of the site, and a diagram is drawn into the page. The text people read MUST be on white (`#ffffff`) in the light theme (FR-034 gives the dark one); the navigation is on a neutral grey; it MUST be read on a screen 360 pixels wide with nothing scrolling sideways but code and wide tables; code is highlighted when the site is built; a search over titles, headings, exports, tables, columns and requirements is opened with `/`.
- **FR-018**: `check` MUST find: an export of an area with no TSDoc; a package with no `about.ts`, or whose `about` names a folder that does not exist, a command that is not a script of its `package.json`, or a rule enforced by a test or lint rule that does not exist; a citation of a specification or requirement that is not in the spec kit; a `{@link}` to an unknown name; a table or view of a model with no description; a module of a lens that cannot be imported; a specification two spec kits both hold; and a link or anchor of the site that leads nowhere.
- **FR-019**: The generator's tests MUST cover the Markdown subset, the highlighter, every case of the page model as HTML, the API reader on a fixture module, each lens on a fixture, the configuration's validation, the plain spec kit's reader, the citation rules of a configuration, and the build of a fixture repository (a package with no `about.ts` and a plain spec kit), and MUST compare the fixtures' HTML with HTML committed under `commons/docs/suite/golden/`, written again with `IFCDOCS_UPDATE_GOLDEN=1`.
- **FR-020**: A workflow, `.github/workflows/site.auto.yml`, MUST run the generator's tests and `check` on every pull request and push that touches commons or the workflow, and on `main` MUST build the site and publish it to GitHub Pages with GitHub's own actions (`actions/upload-pages-artifact`, `actions/deploy-pages`) once for each push: when the workflow `ci` of that push finishes (so that the site shows its result), and not again for each of the other workflows; a push that touches only the workflow itself builds it directly, and the workflows `evidence` and `release` and the night refresh it. A build in progress on `main` is finished and only the newest waiting one is kept. The site MUST NOT be committed. The site workflow MUST ask for the open issues and for the runs of the workflows at the same time, and `tools/ci-runs.ts` MUST ask about the workflows at the same time and keep them in the order of their files.

## The package

- **FR-021**: The generator MUST be consumed as the package `@intellectual-frontiers/docs` (docs 0001-docs FR-002 to FR-005): its entry exports the configuration's types, `Lens`, what a lens uses, `loadConfig`, `buildSite`, `writeSite` and `main`, and its command `ifc-docs` runs on Bun and, where Node 26 reads the configuration, on Node. In this repository the command is `commons/docs/ifc-docs.mjs`, which runs `src/cli.ts` as it is (Node 26 strips its types); the packed package is proved by installing it into an empty project (docs 0001-docs FR-005).
- **FR-022**: No workflow MUST make a GitHub release or attach a tarball of the generator, and the write permission to the contents is the tag job's of the workflow a library is published by, which makes the tag of the version it published, and the job `keep-findings` of each workflow, which adds the findings of a run to the history branch on the default branch only and never after a pull request (commons 0038-build-policy FR-012); and the job `tag` of the workflow `maintenance`, which makes the tag of a version by hand, only for a commit on the default branch and never replacing a tag that is there; the generator is published to npm by the release of the libraries, like every library of commons that has `npm` in its distribution.

## The configuration

- **FR-023**: A repository MUST configure its site with a TypeScript module (`docs.config.ts`) whose default export, or export `config`, is a value of the package's `DocsConfig` type: the site's name, how its prose names the repository, its root (from the configuration's folder), its address on GitHub and branch, its home (a folder and its `About`), its packages (each a folder, a name in the site's addresses and an `About`: the path of its `about.ts`, `about.ts` by default, or the value itself), its spec kits and the layout of each (FR-024), its citations (FR-025), its lenses (FR-026), the folder of its lint rules, and where the site is written. The value MUST be checked once, when it is loaded, into a resolved configuration (paths made absolute or relative to the root, defaults filled), and every problem with it named; nothing else reads the raw value. Commons' configuration is `commons/docs.config.ts`, and the site it makes MUST be the one commons had before the configuration.
- **FR-024**: A spec kit MUST be read in one of two layouts. Commons' layout: `registry.tsv`, `enforcement.tsv` and `specs/NNNN-slug/spec.md`, the specifications in force in the register's order (FR-015). The plain layout of Spec Kit: every folder `specs/NNN-slug/` that holds a `spec.md`, in the order of their names; the title from its first heading (after `Feature Specification: ` or `NNN: `, where it has one); its status and input from the lines `**Status**:` and `**Input**:` where it has them; requirements written as `- **FR-001** text` or `- **FR-001**: text`, on one line or more, and numbered with a letter after the number where one was inserted (`FR-005a`); an optional `reviewed.tsv` beside the specification, whose rows (a requirement, a tab, a reason; `#` begins a comment) are the requirements proven by review; and, where it exists, the constitution (`.specify/memory/constitution.md` by default), shown as a page of the Specifications section.
- **FR-025**: The configuration's citations MUST give the repository's own prefix (`commons`, `fleet`) and the number of digits of its specifications' numbers, the repositories whose specifications MAY be linked (each by its name, the address of its site and the digits of its numbers: a public repository built with this generator, whose pages are `specs/<id>.html` with an anchor `fr-nnn` for each requirement; such a link is not checked), and the repositories whose citations are only shown as text. A qualifier is matched whatever its case and with a possessive `'s` or `'` taken off; a qualifier the configuration does not name is read as a word before a bare citation. A number of the repository's digits alone, after `spec` or before a requirement (`spec 004`, `038 FR-014`), MUST become a link to the specification with that number where there is one, and the requirement after it is that specification's; where there is none, it and the requirement after it stay text.
- **FR-026**: The package MUST depend on no library it shows: a lens is a value of its `Lens` type that the configuration passes (its name, and a function that reads the areas and their API, registers the pages its entities are shown on, and returns what makes its pages once every other page is registered). The package ships no lens; commons' configuration passes none (FR-013), and another repository passes the lenses it has, or none.
- **FR-027**: A repository with no `about.ts` MUST still be documented: its configuration gives each package's `About` value (its title, summary and areas, each area with its entry points), and the home's, and the pages are made from them as from an `about.ts`; a finding about such a value names the configuration's file.
- **FR-028**: Every page of the site MUST also be written as Markdown beside its HTML, with the same path and `.md`, made from the same page model (every case of a block and an inline has a form in Markdown, matched with an exhaustive `switch`; a link to a page goes to its Markdown twin), and the site MUST have `llms.txt` at its root: its name and every page by section, as a link to its Markdown twin with its description, and the files a lens adds (the JSON of a model), so that a program reads the words and the structure and not the markup. The same sources give the same bytes.
- **FR-029**: The package MUST ship, beside the lenses of commons' configuration, a layered-model lens (`commons/docs/lens/layered.ts`) that knows no library: given a function that makes `LayeredModel` values (the package's types-only contract, `layered.ts`: layers, elements with a stable id, kind, name, definition, source location and properties, trace edges from an element of one layer to what it is made into, and findings) and the files that export the values the models are made of, it MUST make, in the Models section, a page of the layers (what each is for, which code writes it, what may be edited, how to change a model and regenerate what follows, and what an agent reads), a page for each model with a diagram of its concepts, a page for each concept (its definition, where it is written as a link to the file and line, its attributes and relationships, what it projects to and what it is written as), a page for each code list, and registers of what the models annotate; and it MUST add the JSON of each model and of the list of models to the site. It MUST find where an element is written from the identity of the values the given files export, so that a project's own models are documented the same way, and it MUST name in a finding a file that it cannot read.
- **FR-030**: The package MUST ship a program lens (`lens/program.ts`) that is given a function making `LayeredModel` values for the programs of a library built on commons headless (one model for each tier of a program, with the same element ids in each) and knows nothing of headless: it MUST make a page set for each model and never merge two models by id, a page of the programs with a card for each, for each model a page of its verbs (what each does, its effect, the surfaces that draw it and the reasons it is not drawn), its plugins, problem codes, exit statuses and findings, for each verb a page of its action as governance says it, its operands, options, examples and the command, tool and route it is drawn as (or that it is drawn by no surface for the tier), and the JSON of each model and of the list, the same models giving the same pages.
- **FR-031**: Every library of commons (a folder with a manifest, a `package.json` and an `about.ts`) MUST be a package of commons' site, with one area whose entry points are the files its `package.json` exports and whose folder is their longest shared folder, so that the site has a page and an API reference for each library; a page of a library MUST show its manifest's facts (version, conformance level, distribution) and the specifications of its own spec kit; the register and the pages of the specifications MUST be grouped by the library whose spec kit holds them; a module comment MUST be found after any `//` lines (such as a `// Spec:` header); and a namespace export MUST count as documented by the module comment of the file it names.
- **FR-032**: The package MUST ship a guides lens (`lens/guides.ts`) that is given Markdown files with the address, section, group and order of each, and makes a page of each, its first heading being its title, with its citations of a specification and its links to a file or a folder resolved like those of every page and a guide that cannot be read a finding; the sections of the site MUST be, in order, Start here, Concepts, Libraries, How-to, Specifications, API and Models, each shown where it has a page; and commons' site MUST have a path for each kind of reader (a new developer, a contributor, an agent, an auditor), a page for each concept the repository is built on, and the how-to pages for finding where something lives, adding a library, adding a command to the workspaces program and cutting a release.
- **FR-033**: The site MUST have a page of the library map, with a diagram and a table of what each library of the site imports and what imports it, read from the packages its own sources (not its tests, tools or manifest) import by name, and the page of each library MUST list what it imports and what imports it.
- **FR-034**: The site MUST follow the reader's system between a light and a dark theme with every colour a token, MUST let the reader choose one with a button and with `t` and keep the choice in the reader's browser only, MUST set the theme before the page is drawn so that it does not flash, MUST have keyboard navigation (`/` for the search, `[` and `]` for the previous and next page of the side navigation), and MUST have a print style that leaves out the navigation and prints the address of each external link.
- **FR-035**: Under each requirement of a specification the site MUST say which files prove it (the test files that name it in a quoted string) and which are written to it (the files whose `// Spec:` header names it), as links to the files; the page of a library built in layers MUST show its layers and the folders of each from its manifest; the package MUST ship a releases lens that reads the record of the next release and makes a page of each library it publishes, with its version, its tag and its place in the order, and a record that cannot be read is a finding; and the search MUST be filterable by the kind of what it finds.
- **FR-036**: A configuration MAY name `retired` (names that no page of the site may have) and `forbiddenInGuides` (words that no page of the sections Start here, Concepts and How-to may have), and a page that has one is a finding, so that the site names no library that is gone and the pages people write say what is and nothing that was; commons' configuration MUST name both, and the site MUST answer from itself, by its search and its pages, the newcomer's questions of what to run first, what a library imports, where a requirement is proved, where a command is described and how a release is made.
- **FR-037**: Code MUST be coloured and diagrams MUST be drawn when the site is built, so that a page shows both with no script and no request: code with Shiki, on its Oniguruma engine, for TypeScript, SQL, shell, TOML, JSON, Turtle and YAML, each run carrying its colour for the light scheme and for the dark as custom properties that the stylesheet picks between by the rule of FR-034, the same text always giving the same runs whichever grammar was read first, code longer than 6000 characters and the text of other languages left plain; and diagrams as SVG with `beautiful-mermaid`, in the page's own colour tokens, so that the dark scheme needs no second drawing, and, where a diagram cannot be drawn, its source in a code block; the source of every diagram stays on its page, and the Markdown twin keeps it as a Mermaid fence.
- **FR-038**: The How-to section MUST have a group "With an AI assistant" of guides in files named `ai-*.md`: a start page, and a guide for each common task that a person asks an assistant to do. Each task guide MUST have, in order, the headings `When to use it`, `What to give the assistant`, `The prompt`, `Check the result` and `Common mistakes`, and `The prompt` MUST hold a fenced block tagged `prompt`. Every path in a code span of these guides MUST exist, every `repoctl` command MUST be one the program lists, every `bun run` script MUST be one of the root or of a library, and every specification cited by its number MUST exist; and each guide MUST name the command that proves the result (`bun run verify`, `bun run dev:check` or `bun run repoctl check`), so that a prompt guide cannot go stale without the tests saying so.
- **FR-039**: The site MUST be easy to move around in: the navigation groups its pages under collapsible headings that open on the page's own trail, the Models section groups its models by subject (a subject being named by the data library's governance), the Programs have a tab of their own, and the specification matrix is split by library into pages of at most `ROW_BUDGET` rows with a summary page, each table filterable.
- **FR-040**: Commons' configuration MUST name the five volumes of the series Commons Manuals (`commons-guide`, `commons-api-reference`, `commons-data-models`, `commons-specifications`, `commons-programs`), the pages of the site as the generated chapter sources of books of `erga` (docs 0001-docs FR-008): the data models in a part for each subject, the API and the specifications in a part for each library, and neither the specification register nor the traceability matrix, which are for the screen. Every cross reference of a volume MUST have its anchor in the volume.
- **FR-041**: Commons' configuration MUST give `evidence` (docs 0001-docs FR-009 to FR-012): the results of the tests in `_evidence/` (not committed; CI leaves them there, and a build made by hand has none, which the pages say), the snapshot of the open GitHub issues in the same folder, and the issues of `commons/data`, each set with its scope, read from the library. The site MUST have the Quality section and, beside each requirement, library and module, what the tests and the open issues say.
- **FR-042**: The workflow `site` MUST run the tests of every library that has a suite and of the repository's own `tests/` on a push to `main` (a job for each, in parallel), keep each run's CTRF report with `tools/evidence.ts` of docs, fetch the open issues of the repository, and build the site from them, and it MUST publish the site whether or not a test failed, the banner of the Quality section being how a failure is seen; a run that cannot be made for a library MUST leave that library with no run recorded and not fail the publication.

## Out of scope

- The ontology (`commons/ontology/`): it moves to TypeScript, and is then shown by a lens of its own.
- A link from a type in a signature to its page, versions of the API for each tagged commit, D2 diagrams, Rust and Zod output, and languages other than TypeScript.

## Edge cases

- An export whose TSDoc was removed: `--check` names it, per FR-018 and FR-010.
- A module of a model that throws when imported: `--check` names the module and the site is not published, per FR-018 and FR-013.
- A documentation comment that cites a requirement of `erga 009-machine-bootstrap`: the page shows the text, with no link, per FR-011.
- A comment that cites a requirement number its specification does not have: `--check` names it, per FR-018 and FR-011.
- A package's `about` whose command was renamed in `package.json`: `--check` names it, per FR-018 and FR-005.
- A table of a model with no description: `--check` names it, per FR-018 and FR-013.
- A signature thousands of characters long (a model's computed row type): it is shown whole and folded, per FR-010 and FR-017.
- The site published under `/.github/`: every link is relative, so it works there and at a custom domain alike, per FR-017.
- A README added to commons: the tests of the layout fail, per FR-004.
- `ifc-docs check` run by Node 26 from a repository's `node_modules`: the package ships compiled modules, so it runs as on Bun, per FR-021.
- A lens that imported a data library from the generator's library entry point: the test of FR-026 names it, since `./docs` and `ifc-docs` must reach no library they show, per FR-026 and FR-002.
- A configuration that names a package with no `slug`, or a spec kit of an unknown layout: the command names each problem and exits 2, per FR-023 and FR-003.
- A repository of three digits citing `commons 0011-documentation FR-003`: with commons listed as linked, the citation goes to commons' published site; with commons not listed, it is text, per FR-025 and FR-011.
- A plain spec kit whose requirement is written `- **FR-001** text` over two lines, or numbered `FR-005a`: it is one requirement, with its anchor, per FR-024.
- A `spec 004 FR-015` in the text of spec 005: the requirement is spec 004's, not 005's, per FR-025.
- Two spec kits that both hold `001-platform`: `check` names the second, per FR-018 and FR-024.
- A repository with no lens: its site has no Models section, per FR-009 and FR-026.

## Assumptions

- The TypeScript 7.1 programmatic API, in beta, keeps the shape it has in `7.1.0-beta`; the generator is pinned to that version and moves to the stable 7.1 when it is released.
- GitHub Pages serves a repository named `.github` under `/.github/`; where it does not, the site is published at a custom domain with no change to it.
- A model module only defines values when it is imported, which is how the models of commons data are written.
- A repository that uses the package runs it where its own dependencies are installed, so that the modules it documents and its `@types/node` resolve as they do for its own compiler.

## Open questions

- **OQ-1**: Whether the root `README.md` should also be made from `commons/about.ts` once the site is the only documentation people read.
- **OQ-2**: Whether the documentation of a tagged commit of commons should be kept beside the latest, under its tag.

## Key entities

- **Area** - a part of commons with an entry point, named by its package's `about`, and its pages.
- **About** - the typed facts of a package: summary, specification, folders, commands, rules, and its areas with their phases and examples.
- **Page model** - the tagged union of blocks and inlines every page is made of before it is HTML.
- **Lens** - what the generator knows of one library: which exports are its, and the pages their values make.
- **Finding** - a place and a sentence saying what `check` found there.
- **Configuration** - the typed value a repository gives (`DocsConfig`), checked once into the resolved configuration the build reads.

## Success criteria

- **SC-001**: `cd commons/docs && bun run verify` (the compiler, the tests, then `check` on commons) passes.
- **SC-002**: The published site has a page for every export of every area, for every table of Arca's party model with its diagram and its SQL for the three dialects, and for every specification in force.
- **SC-003**: `bun run smoke` (FR-021) passes on Bun and on Node 26 from a `git+file:` URL of a commit, and a repository's site builds from a copy of it with a configuration and no `about.ts`.
