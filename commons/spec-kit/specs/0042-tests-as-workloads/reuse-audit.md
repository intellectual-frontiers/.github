## Where the mapper lives (row C12)

Three places can hold the code that turns a run of a case into a record.

1. **In `quality`, importing the types of `workload`.** Refused. `workload` imports `libraries` (`workflows/model`, `workflows/render`, for the emitter of GitHub Actions), and `libraries` imports `quality` (`src/changes.ts` reads a record). The edge `quality` to `workload` would close a cycle of packages, which 0032-libraries-by-concern FR-003 forbids (the modules of `libraries` that `workload` imports do not import `quality`, so no file imports in a circle, and the packages do; workload 0016-ci-on-graph FR-001 already keeps `libraries` from importing `workload`).
2. **A thin package that imports both.** Not needed. Nothing else would import it, and it would add a manifest, a registry and a release for one function.
3. **In `workload`, importing `quality`, as the producer of a record does.** Chosen. The precedent is `libraries/tools/changes.ts`, which builds a `CheckInput` and calls `checkRun`: the producer imports `quality` and gives it typed data. No library that `quality` imports imports `workload`, so the graph stays acyclic. The format-neutral part (the input type `CaseRunInput`, `caseRun`, the grades, the writers) is in `quality`, which imports nothing of `workload`; the translation of a run state, a receipt and a result file into `CaseRunInput` is in `workload`, in one physical entry (`./acceptance`) that only the consumers that run cases import, so the core and the forms of `workload` import nothing of `quality`. If the layers test of 0032 refuses this edge, the same file moves to a package of its own with no change to either library.

## Summary of decisions

There are 48 rows in six groups (A to F): **reuse 22, extend 24, new 1, decision 1**. The counts are of the first word of the decision column. The one new row is the ingest of the receipt line of a script (C9); the decision row (C12) says where the mapper lives; a test of the counts is deferred (0042 FR-056).

## The duplications to avoid

1. **Citations of a requirement.** Four readers of `NNNN-slug FR-NNN` exist: `mizan` `trace.ts` (`REQUIREMENT`, `parseCitation`), `workload` `ids.ts` (`parseCite`), `quality` `ledger.ts` (the `requirement` refinement) and `quality` `test-report.ts` (`parseRequirementList`). A case uses `SpecCite` and writes the text of `citeText`; it makes no fifth reader.
2. **Two TAP writers.** `tap14` and `tapSteps` (`test-report.ts`) and `tap` (`pure/render.ts`). The case run extends them; it does not write a third.
3. **Two EvidenceKind.** `workload` `EvidenceKind` (`digest`, `record`, `measure`) and `quality` `EvidenceKind` (`run`, `statement`, `review`, `probe`) are different things with one name. The typed reference to a file is named `EvidenceRef` and the declaration `EvidenceDecl`, and neither reuses either name.
4. **Two OSCAL assessment-results writers.** `grc` `serializers/oscal` and `quality` `oscalAssessmentResults`. A case run uses the second, because it writes from a record.
5. **Four hash chains and three manifests.** Chains: the files of the `quality` branch (`ifc.quality.previous.sha256`), the records of the ledger (`LedgerFile`), the entries of `pure/primitives.ts` (`LedgerEntry`), and the ledger of `grc`. Manifests: `grc.evidence-manifest`, the bundle of `evidence-capture`, and `ManifestFile` of the pack. A case adds neither: its files are listed in the manifest of the pack and their digests are in the record.
6. **Four places for a person's word.** The `answered` event of a run, a `grc.attestation`, a `statement` or `review` of the ledger and a Tier 2 `SampleAttestation`. A step's word is a `grc.attestation`, and the `answered` event cites its digest; the ledger gets a `review` only by a person's explicit act, and a result is never copied into it.
7. **Declared platform against observed platform.** `Installation` (os, arch) is what the machine says; a parameter `os` is what the case asks for. The check compares them and does not keep a second platform record.
