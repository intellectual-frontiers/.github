# Feature Specification: Planning

**Spec ID:** 0037-planning
**Status:** Draft
**Owner:** if
**Domain:** commons
**Part of:** 0033-kanon

**Input:** Planning content (an issue, a task, a to-do, a finding) lives in many places at once: files of a repository, comments in source, lists in Markdown, a Git host, a tracker, a table. Each place has its own form, its own identity and its own idea of what "done" is, so no one place says what is planned. This specification names the library **Planning** (`commons/planning`, the package `@intellectual-frontiers/planning`), a Kanon library that collects planning content from many places in a configurable way, keeps one item with one stable identity for each thing planned, keeps its history as append-only events, remembers every place the item was seen, and writes a change back to a place in that place's own form, or renders the items in any format. The first version generalizes the issue records that exist today (`inventory.md` lists every one, in this repository and in the company's monorepo, and how each maps onto the model); findings of the Quality System and pen test findings are a later phase and are not modeled here. The name `planning` and the prefix `plan:` are confirmed by the owner. The status stays Draft, which Mizan defines as written and not yet built (0003-mizan FR-010): it becomes Active when every requirement is proven. The owner confirmed the custom types of OQ-9 on 2026-11-21 (the item kinds roadmap item, question and decision, the event `seen`, the link kind `derived from` and the locator kind `row` are cut; every other proposed type is kept), and the library is built in the phases of `plan.md`.

## Governance: what an item is and what may happen to it

- **FR-001**: The library MUST model an item (`plan:Item`) as a sum of kinds (`plan:Issue`, `plan:Task`, `plan:Todo`, `plan:Finding`, the four members of `plan:ItemKind`) over one shared core that every kind has: an id, a kind, a title, a body, labels, assignees, an optional severity, an origin, the external ids of FR-044, the links of FR-009 and the optional fields the sources carry (the motivation, the blocker flag, the target and the source of a record, and the priority, size, goals, engines, citations and evidence of a typed issue, FR-046); a kind MAY add fields of its own and MUST NOT remove any field of the core.
- **FR-002**: A severity MUST be exactly one of the three members of `plan:Severity` (`plan:Error`, `plan:Warning`, `plan:Note`), the values of the SARIF result `level` that apply where the `kind` of a result is `fail` (SARIF 2.1.0 section 3.27.9, 3.27.10), and a verdict of a `plan:DecidedEvent` exactly one of the four members of `plan:Verdict` (accept, minor revision, major revision, reject), and each closed list MUST be a union of literals with one registry entry for each case, so that a value outside the list does not compile and a parsed value outside it is an error value; WHERE a source has a severity of more levels (the typed issues of data 0044 have critical, high, medium and low), the item MUST carry the source's own value and the matrix of FR-015 MUST say that the three levels are not an exact expression of it.
- **FR-003**: The history of an item MUST be a set of events, each one case of the closed union `plan:EventType` (opened, commented, edited, labeled, assigned, severity set, blocker set, started, deferred, closed, reopened, decided, linked, confirmed), each with an id (FR-007), a time in UTC to the second (`YYYY-MM-DDTHH:MM:SSZ`) and an actor (FR-005), and holding the data its source wrote; the ten types of the monorepo's issue files (opened, commented, edited, labeled, assigned, severity, blocker, closed, reopened, decided) MUST each be a case of the union with the data that record holds; an event MUST be immutable once written, and the library MUST have no operation that changes or removes an event.
- **FR-004**: The state of an item (`plan:State`: proposed, open, in progress, deferred with an `until` day, closed with a `plan:CloseReason`) MUST be the result of `fold`, a pure and total function from the events of the item to its state, with the events taken in the order of their id (FR-007: a UUID version 7 sorts as text in the order its time and its counter give), the first event of an item being its opening; a state MUST NOT be stored as a fact, and WHEN two histories hold the same events in any order or with any repeats, `fold` MUST give the same state.
- **FR-005**: An actor (`plan:Actor`, a `prov:Agent`) MUST be of one of the three members of `plan:ActorKind` (person, agent, tool) with an id and a name; WHERE an agent (an AI agent such as `claude`) authors an item or an event, its actor MUST be of kind agent and MUST name, in the same actor value, the person on whose behalf it acted, its principal, and how the principal was established (FR-045), by `prov:actedOnBehalfOf` (PROV-O section 4.1: delegation is the assignment of authority and responsibility to an agent while the agent it acts on behalf of retains some responsibility for the outcome), the principal being an actor of kind person; an event or an item of an agent with no principal MUST be refused when it is built and found as invalid when it is read; an event of a person MUST NOT name an agent and MUST NOT name a principal; a tool MAY name the person who ran it and need not; and a library function MUST refuse to build an event whose actor is a person from a context that has no person's credentials, configuration or argument (FR-045).
- **FR-006**: An item MUST have an origin (`plan:Origin`: declared, derived or inferred); WHEN an item is inferred by a heuristic or an agent, it MUST start in the state `plan:Proposed`, MUST NOT be counted by any derived view (FR-021) or any query that is not told to include proposals, and MUST leave `plan:Proposed` only by a `plan:ConfirmedEvent` whose actor is of kind person with no principal; an agent MUST NOT confirm any item, its own or another's, and WHEN the configuration (FR-037) says `confirmers: "principal"` only the principal of the event that proposed the item MUST confirm it, and otherwise (the default) any person MAY, because a proposal belongs to the plan and not to the one who ran the agent.
- **FR-007**: An item id and an event id MUST each be a UUID version 7 (RFC 9562 section 5.7) as 36 lower case characters, branded by a smart constructor that returns a `Result` and made by the hybrid clock of AnyFS's merge (`@intellectual-frontiers/anyfs/merge`: `nextTime`, `seeTime`; `@intellectual-frontiers/anyfs/governance`: `makeVersionId`, `parseVersionId`, `timeOfId`, `randomIdBytes`, `randomCounterSeed`), reused and not made again, so that the clock of a replica holds the replica as a field of its own and the id holds nothing of it (the `rand_b` of an id is random for each id, RFC 9562 sections 5.7, 6.9), every id a replica makes is after every id it has seen, and two stores merge by the union of their events; an id MUST be minted once, MUST NOT change when the item is seen in another place or moves inside a place, and MUST NOT be reused for another item, even after the item is closed; WHEN an event is taken from another store, the next id made MUST come after it (`seeTime`), and an id whose time is further ahead of the clock than the limit of the configuration (five minutes by default, as AnyFS) MUST be refused.
- **FR-008**: An observation (`plan:Observation`) MUST be what one source read in one place at one time: the content as the source read it, a locator (`plan:Locator`, one of the three kinds of `plan:LocatorKind`: file span, URL, commit), the SHA-256 of the bytes it was read from (`plan:contentHash`) and a fingerprint of the identity of the thing read (`plan:fingerprint`) that does not depend on where in the place it is, as a SARIF result's fingerprint is a stable identifier the same for logically identical results and resistant to a change of line number (SARIF 2.1.0 section 3.27.16, 3.27.17).
- **FR-009**: Every item MUST carry a trace (`plan:Trace`, a PROV-O derivation) to each observation it was derived from, so that every place an item was seen (file and line, URL, commit) can be found from the item, and WHEN an item has no trace to any observation, it MUST be one declared directly in the store; a link (`plan:Link`) MUST be one of the four `plan:LinkKind` (blocks, same as, relates to, parent of), and the links of kind blocks MUST make a graph with no cycle: WHEN a link would close a cycle, the library MUST refuse it with the items of the cycle named.
- **FR-010**: A patch (`plan:Patch`) MUST be a value of a closed union (add an item, add an event, change a state, link, confirm), made for one explicit source, and MUST do nothing until it is applied; a function that makes patches MUST be pure.
- **FR-011**: A preview (`plan:Preview`) MUST say exactly what applying a patch would write, to which source and place, with a hash of itself (`plan:previewHash`); WHEN a write is asked for without a preview that it names by its hash, the library MUST do a dry run and write nothing, and WHEN the preview it is given differs from what the patch would now do, it MUST refuse and write nothing.
- **FR-012**: The authority over each field of an item MUST be one of the members of `plan:FieldAuthority` (source wins, store wins, latest wins, person only), set for a source and a field in the typed configuration (FR-037), and the library MUST apply it in `fold`, over events, and not by overwriting a field: WHERE the authority of a field is person only, an event of an agent or a tool that changes it MUST wait as a proposal and MUST NOT change the state, and an agent that acts on behalf of a person MUST NOT be counted as that person, so that only the person's own event changes the field.
- **FR-013**: A source (`plan:Source`) MUST be a typed lens over one kind of place with two functions: `acquire`, which reads a place and returns observations or an error value, and `write`, which takes a patch and returns the observations the place now holds or an error value; a source MUST declare its name and its capabilities (FR-014), and MUST NOT write unless it was given an explicit target.
- **FR-014**: A source MUST declare its capabilities as a set of the members of `plan:Capability` (read, create, append event, edit, close, assign, delete), and WHEN a patch needs a capability the source does not declare, the library MUST NOT apply the patch to that source and MUST put it in the outbox (FR-033), with the capability named.
- **FR-015**: Nothing MUST be dropped silently between what an item says and what a source can hold: each field of an item MUST end, for each source, expressed (the place holds it), carried (it travels in a form the place keeps, such as an anchor or the observation's content as read) or unexpressed with a reason, and a field that ends in none MUST be a `kanon/dropped` finding of the Kanon check, with the matrix of field by source given as in 0033-kanon FR-023.

## Logical: reconcile, merge, query and views

- **FR-016**: WHEN observations are reconciled with the store, `reconcile` MUST match each observation to an item in this order: the id an anchor in the place carries, then an external id (FR-044), then the fingerprint, then the locator; WHEN none matches, it MUST make a new item whose origin is derived or inferred as the source says, and it MUST return events and links as data and write nothing.
- **FR-017**: WHEN a place and the store disagree, `reconcile` MUST do a three-way merge of the observation last taken (the base), the observation now read and the store, MUST class each observation against the base as new, unchanged, updated or absent (the four values of the SARIF result `baselineState`, section 3.27.24) and MUST express each difference as an event whose actor is the source (a tool), so that the field authority of FR-012 decides the result in `fold`; a difference that no authority decides MUST be a conflict value that names the field, the three values and the sources, and MUST NOT be settled by taking either one silently; two events with one id and different content MUST be a conflict value.
- **FR-018**: WHEN a thing an item was derived from is no longer found in the place (a removed comment, a deleted line: an observation `absent` in the words of FR-017), `reconcile` MUST add a derived close, a `plan:ClosedEvent` with the reason `plan:Completed`, the origin derived and a tool as actor, and WHEN the same fingerprint is read again, it MUST add a `plan:ReopenedEvent`; an event by a person MUST win over a derived close.
- **FR-019**: The library MUST find likely duplicates by a similarity of titles, bodies and locators with a threshold set in the configuration, and MUST propose each as a link of kind `plan:SameAs` in the state proposed that a person confirms, and MUST NOT merge, close or hide an item because of a likeness; the same items and the same threshold MUST give the same proposals in the same order.
- **FR-020**: The library MUST give a query as a typed algebra over the items, the events, the links and the traces (select, filter by state, kind, label, assignee, severity and origin, join, order, limit), pure and read-only, and a surface (FR-036) MUST be a projection of it and not a second definition.
- **FR-021**: The library MUST derive these views by pure functions of the items: the roadmap (the items that are counted, in an order that puts an item after every item that blocks it), the graph of blocks and blocked by with its cycle check (FR-009), the matrix of requirement by source that links each item to the requirement it cites (a citation such as `FR-014` or `0037-planning FR-014`), so that a requirement with no item and an item that cites a requirement that does not exist are each found, and the view of responsibility: for each person, the events their agents authored, by agent, and the proposals of those agents that still wait.
- **FR-022**: The governance and logical code MUST be pure: it MUST read no file, call no network and take no clock; the time of an event or an observation, and the time the hybrid clock of FR-007 is given, MUST come from a value the caller passes in, and the last time of the clock MUST be a value taken and returned.

## Physical: the sources

- **FR-023**: Every source MUST keep the laws of a lens, proved by property tests over generated places: `acquire` then `write` of the observations it returned writes nothing and changes no byte; `write` of a patch then `acquire` returns the observations with the patch applied and no other change; and `acquire` twice of an unchanged place returns the same observations in the same order with the same fingerprints.
- **FR-024**: The source for typed issues in code MUST read the folder `issues/` of a library as data 0044-issues FR-002 lays it out (`NNNNN-slug.ts`, listed in order by `mod.ts`) as items, keeping every field of an issue (its severity, priority, goals, size, engines, citations, evidence, links, status and day raised) in the observation's content, MUST find a file the barrel does not list and a name the barrel lists with no file, and MUST write a patch back as a change to that file that keeps the rest of it as it was.
- **FR-025**: The source for a folder of event files MUST read each JSON5 file of the monorepo's issue schema `erga/issue@1` (and each event object of its store, `erga/issue-event@1`) as one item with its events, MUST read all ten types of event and all fields of the opening (title, body, labels, assignees, severity, the Web Annotation motivation, blocker, target and source), MUST find a file it cannot read and name why, and MUST write a new event by the rules of that schema, keeping every other byte of the file.
- **FR-026**: The source for Markdown MUST read each task list item of GitHub Flavored Markdown as an item: a list item whose first block is a paragraph that begins with a marker (optional spaces, `[`, one whitespace character or `x` or `X`, `]`) and at least one whitespace character before any other content (GFM 0.29-gfm section 5.3), under any list marker the list allows (`-`, `+`, `*`, or an ordered number with `.` or `)`), unchecked where the character is whitespace and checked otherwise, nested items as sub-items linked `plan:ParentOf`, in any Markdown file, in a Spec Kit `tasks.md` and in a task list of the body of a GitHub issue, and WHEN an item is closed, `write` MUST change the one character between the brackets to `x` and WHEN it is reopened, to a space, and no other byte of the file.
- **FR-027**: The source for comments in source files MUST read a comment that carries one of the markers set in the configuration (`TODO`, `FIXME`, `XXX` and `HACK` by default, the markers the documentation scan of Docs reads) as an item, with the fingerprint of the comment's normalized text and the symbol that encloses it, so that the id survives a move of the line; WHERE a marker is written back, `write` MUST insert an anchor of the form `TODO(#id)` and MUST do so only for the files the configuration lists, and never in a generated or a vendored file.
- **FR-028**: The source for a Git host MUST read the issues of a repository (the number, title, body, state, url, labels, parent and children that the host contract holds) and the references of its commits (the line `Refs #N` that `repoctl commit` writes and the closing keywords of the host: `close`, `closes`, `closed`, `fix`, `fixes`, `fixed`, `resolve`, `resolves`, `resolved`) as items, links and traces, through the Git host contract of the library `githost` and never a client of its own, and MUST write only what the host's capabilities and the token's grants allow; a field the contract does not hold (the close reason, the assignees, the comments, the events) MUST be unexpressed with that reason until the contract holds it.
- **FR-029**: A source that reads files MUST be written against a store of AnyFS (`@intellectual-frontiers/anyfs`) whose capabilities are in its type, so that the same source works over a folder, Git, S3, SSH and SQL; WHEN it writes, it MUST state the revision it read as the expectation of the write, and a write that finds the file changed MUST be a conflict value and change nothing.
- **FR-030**: The library MUST give `defineSource`, which makes a source from a typed record (its name, its capabilities, `acquire` and `write`) and refuses a record whose `write` is present when `capabilities` says it cannot write, so that a person can add a source (a SQL table, a tracker) with no change to the library.
- **FR-031**: The library MUST reserve the names of the sources that are not yet written (SARIF files, skipped and todo tests, Dependabot and Renovate pull requests, iCalendar to-dos, Linear, Jira, and the findings of the Quality System and of pen tests), and a source of the list MUST NOT be written before the specification of the standard or the service it reads has been read and cited.
- **FR-032**: A write MUST need an explicit target (a source and a place), MUST be a dry run unless it names a preview by its hash (FR-011), and the command in check mode MUST print the hash of the preview and exit with a status that says whether anything would change, so that a headless run applies exactly the plan a person looked at.
- **FR-033**: The library MUST keep an outbox of the patches that no source could apply (FR-014), each with the reason, as items of the store that a person can read, and MUST offer each again WHEN a source that can apply it is given as a target.

## Physical: surfaces, configuration and formats

- **FR-034**: The program `planctl` MUST be a headless program of the library Headless (`commons/headless`) with the verbs `collect`, `show`, `query`, `views`, `confirm`, `plan` and `apply`, each returning a typed outcome and printing through a surface, and `plan` and `apply` MUST be the dry run and the write of FR-032.
- **FR-035**: The library MUST give a tool server of the same verbs, as a surface that is a projection of the same program, in which a tool that writes MUST take the target and the preview hash as arguments, an agent that calls it MUST be an actor of kind agent with its principal (FR-005), the principal MUST be the person the server's session was launched for (FR-045), and a call with no principal MUST be refused.
- **FR-036**: The library MUST give the items as relations of SQL, read-only, in a plugin `planning-query` in the way `estate-query` and `anyfs-query` do, with the relation `issues` having a column for each field of the core of FR-001 and the state of FR-004 (and the columns the monorepo's relation of that name has, `id`, `title`, `state`, `reason`, `severity`, `blocker`, `labels`, `assignees`, `comments`, `opened_at` and `updated_at`, where the item has the field), so that the statements of the SQL of `lang-sql` and `agora query` read it; the relations MUST be made from the same types and not written a second time.
- **FR-037**: The configuration MUST be a typed value in `planning.config.ts`, made by `definePlanning`, that names the sources and their places, the markers, the threshold of FR-019, the authority of each field for each source (FR-012), the files that anchors may be written to (FR-027), the principal of a run (FR-045), the rule that makes an actor an agent acting for a person (FR-044), `confirmers` (FR-006), the clock's limit (FR-007) and the formats to render; a configuration MUST NOT be read from JSON or YAML, and a configuration that does not satisfy its type MUST be an error value naming the field.
- **FR-038**: The store and the published edition MUST be files in a format that the library encodes and decodes at its boundary, JSON5 by default (the codec of `formats`, JSON5 1.0.0), the store with one file for each event (`<item>/<event>.json5`, so that two stores merge by the union of files) and the published edition with one file for each item that holds its events in the order of `fold`, each with an order of keys that does not change (the order of RFC 8785 section 3.2.3: by property name, recursively), so that a diff of two stores is a diff of events; decoding MUST be total and give an error value for a file that is not an item or an event of the schema.
- **FR-039**: The library MUST render items in a format by a function from items to bytes that is pure (Markdown, JSON5, SQL, and later iCalendar), and a renderer MUST be given by the configuration; WHEN a format cannot hold a field, the rendering MUST say so by the rule of FR-015 and MUST NOT drop it silently.

## The library and how it is built

- **FR-040**: `commons/planning` MUST be a Kanon library (0033-kanon FR-009, FR-010) whose table has the layers governance (the kinds, the events, the states, the severities, the patches, the capabilities), logical (`fold`, `reconcile`, the merge, the query, the views), and physical (the surfaces and the sources' port), with the sources as plugins of the family `planning-<noun>` whose contract is the export that says what a source is (0033-kanon FR-020, FR-021), and its `verify` MUST run the check of `@intellectual-frontiers/kanon`.
- **FR-041**: The governance and logical code MUST be typed as an algebra (0033-kanon FR-018): a closed union for each thing with a fixed set of cases, a product type for each record, every field `readonly` and every optional field exact (`exactOptionalPropertyTypes`), a branded id for each kind of id made by a smart constructor that returns a `Result`, every `switch` over a union exhaustive and ending in `default: return absurd(x)`, errors as values of `Result`, and no `any`, no non-null `!`, no `enum` and no cast but `brand`.
- **FR-042**: A source MUST be a package of its own, `planning-<noun>`, importing the host only by its public exports and no other source, and MUST pass the conformance suite of the host, which runs the laws of FR-023 over its generated places.
- **FR-043**: A term of the model MUST be one of the ontology `plan:` before a specification or code names it, with its basis (0018-standards-first FR-003), and a name taken from a standard MUST be one read in the standard's own text and cited with its version and section (the table of Standards considered); WHERE a term needs a custom type that no standard or existing type carries, it MUST be listed as an open question and confirmed by the owner before it is written.
- **FR-044**: WHEN a record is read that has an id of another scheme (a ULID, an id of a build finding, a number of a host or of a library's issues), the source MUST carry that id as an external id of the item or the event, as the source named it (the source's name and the value), and MUST NOT write history into the id's wording; an external id that is a valid ULID MUST give its item or event id by a pure function: the 48-bit time of the ULID as the `unix_ts_ms` of a UUID version 7 and the first 74 of the 80 random bits as `rand_a` and `rand_b` (RFC 9562 section 5.7; ULID, 48 bits of time and 80 of chance), so that two stores that read one file make the same ids and merge with no duplicate; an id that is not a ULID MUST give its id by the same function from the time of its event and the SHA-256 of the external id; and WHEN the configuration says that an actor id is an agent acting for a person, the source MUST read the actor so, and otherwise MUST read the actor of the file as the file says and report each agent recorded as a person as a finding.
- **FR-045**: The principal of an agent's event MUST be established from who is running the work and never guessed: from the person whose credentials, session or argument launched the program (a tool server's principal is the authenticated person of its session) or, for a headless run, the `principal` of the configuration; a source MAY derive the principal from the author of a commit (a commit whose author is a person and whose trailer `Co-Authored-By` names an agent, as the rule of `repoctl commit` of this repository makes it) only WHERE the configuration names that rule, and the actor MUST record how its principal was established, one of the four members of `plan:PrincipalBasis` (session, argument, configuration, commit author), stored with the actor and not only checked when the event is written; WHERE no principal is established, the library MUST refuse to write the event and MUST say so.
- **FR-046**: Every field of a record that a source reads MUST be kept: a field that the core of FR-001 holds MUST be in the item, as the source wrote it, and WHERE the core has no field for it, the observation MUST keep it as read (FR-008) and the matrix of FR-015 MUST say it is carried, so that nothing of the issue records of `inventory.md` is dropped.
- **FR-047**: A journal (the hash-chained entries of a day's file `journal/YYYY/MM/DD.jsonl` of Evidence Capture) MUST NOT be read as items by any source and MUST NOT be changed; an item MAY cite an entry by a locator of kind file span that names the day's file and the line, with the entry's `digest` as the fingerprint of the observation, and a finding of a check MAY be an item of the kind `plan:Finding` through a source of its own (FR-031).

## The existing records and what is deliberately more general

The monorepo's issue record (entries 1 to 6 of `inventory.md`) has: ten event types; the states open and closed with three reasons; an actor of `type` person, agent or tool, an `id` and a `name`; a ULID for an issue and for each event; a time to the second; a fold in the order of time and then id with the first event an opening; the union of events by id and the smaller canonical text where two differ. Planning covers all of it and differs in these places, each deliberate.

| Place | The monorepo | Planning | Reason |
| --- | --- | --- | --- |
| Event types | Ten, named `severity` and `blocker` for two | Fourteen: the ten (the two as `plan:SeveritySetEvent` and `plan:BlockerSetEvent`) and `started`, `deferred`, `linked`, `confirmed` | `started`, `deferred` and `linked` for the places that hold them (`inventory.md` 7, 10); `confirmed` for the owner's rule on proposals |
| States | open, closed | proposed, open, in progress, deferred, closed | `in progress` and `deferred` (with its `until` day) are data 0044's; `proposed` is the owner's rule |
| Actor | `type`, `id`, `name`; the existing agent `claude` is written as `type` person | Adds the principal, `prov:actedOnBehalfOf`, a person, for an agent | The owner's decision; the monorepo's decoder and encoder read and write `type`, `id` and `name` only, so a Planning write through them would lose the principal: the matrix says unexpressed until that schema gains the field (OQ-10) |
| Ids | A ULID; `f-` and hex for a finding; `ev-...` for a tool | UUID version 7 by the hybrid clock; every other id an external id | The owner's decision; FR-007, FR-044 |

## Acceptance scenarios

1. **Given** a history of events in one order and the same events in another order with one repeated, **When** each is folded, **Then** the two states are equal, per FR-003 and FR-004.
2. **Given** an item an agent inferred from a heuristic, **When** the roadmap is derived, **Then** the item is not in it, and **When** a person's confirmed event is added, **Then** it is, per FR-006 and FR-021.
3. **Given** an event built by the agent `claude` for the person who launched the session, **When** its actor is made, **Then** the actor is of kind agent and names that person as its principal, and an agent with no principal is refused, per FR-005.
4. **Given** an event of a person that names an agent, **When** it is built or read, **Then** it is refused as invalid, per FR-005.
5. **Given** an item proposed by an agent for a person, **When** the agent tries to confirm it, **Then** it is refused, and **When** a person confirms it, **Then** it leaves the state proposed, and **When** the configuration says `confirmers: "principal"`, **Then** only the principal's confirmation counts, per FR-006.
6. **Given** a field whose authority is person only and an event of an agent that changes it, **When** the item is folded, **Then** the state is unchanged and the change waits as a proposal naming the agent and its principal, per FR-012 and FR-021.
7. **Given** a headless run with no principal in the configuration and no argument, **When** an agent's event is to be written, **Then** the library refuses and says that no principal is established, per FR-045.
8. **Given** a Markdown file with a task list item nested under another, **When** it is read and the item is closed and written back, **Then** only the character between the brackets of that line became `x` and the item is a sub-item of the first, per FR-026 and FR-023.
9. **Given** a comment `TODO: tidy` inside a function, **When** the function moves down the file and the file is read again, **Then** the item keeps its id, per FR-016 and FR-027.
10. **Given** an item derived from a comment, **When** the comment is removed and the file is read, **Then** the item is closed as completed by a tool, and **When** the comment is restored, **Then** it is reopened, per FR-018.
11. **Given** a patch that closes an item in a source that cannot close, **When** the patch is applied to it, **Then** nothing is written and the patch waits in the outbox with the capability named, per FR-014 and FR-033.
12. **Given** a write with no preview hash, **When** the command runs, **Then** it prints the preview and its hash and writes nothing, and **When** it is run with that hash, **Then** it writes exactly that, per FR-011 and FR-032.
13. **Given** a link of kind blocks that would close a cycle, **When** it is added, **Then** it is refused naming the items, per FR-009.
14. **Given** a file read over a store of Git and written back after another change to it, **When** the write states the revision it read, **Then** the write is a conflict and the file is unchanged, per FR-029.
15. **Given** two items with nearly the same title, **When** duplicates are sought, **Then** a proposed link of kind same as is made and both items stay open, per FR-019.
16. **Given** a field that a source cannot hold, **When** the matrix is made, **Then** the cell says unexpressed with its reason, and with no reason it is a finding, per FR-015.
17. **Given** two stores that each made events of one item with their own replica, **When** they are merged, **Then** the union of the events is the history, with no conflict and in any order, and the next id made after the merge is after every id taken, per FR-007.
18. **Given** an issue file whose ids are ULIDs, **When** two stores read it, **Then** they make the same item id and the same event ids, each ULID is an external id, and no id's wording says where it came from, per FR-044.
19. **Given** an issue file in which the agent `claude` is written as a person, **When** it is read with no rule in the configuration, **Then** the actor is read as the file says and a finding names each such event, and **When** the configuration says the id is an agent acting for a person, **Then** it is read as an agent with that principal, per FR-044.
20. **Given** an entry of a journal, **When** an item cites it, **Then** the locator names the day's file and the line, its fingerprint is the entry's digest and the journal is unchanged, per FR-047.
21. **Given** a typed issue of data 0044 with the severity `high`, the priority `P2` and the status `deferred`, **When** it is read, **Then** the item holds the fields as read, the state is deferred with its `until` day, and the matrix says the severity is carried as the source's own value and not expressed by the three of the model, per FR-002, FR-004 and FR-046.

## Out of scope

- A user interface, a calendar, a time tracker and estimates: Planning holds what is planned, not who does it when.
- The typed issues of the weaknesses of a library of `commons/data` and their copy in a database (data 0044-issues and data 0045-issues-model): they are a source of Planning (FR-024) and are not changed by this specification; the database copy stays as data 0045 has it.
- The findings of the Quality System, pen test findings of Opsfolio and the like: a later phase, after experience with the library; `inventory.md` says where each would attach and nothing is modeled for them now.
- The monorepo's issue schema: Planning reads and writes it as it is; a change to it (OQ-10) is the monorepo's.
- The release, the version and the publication of the package: the release of commons.

## Edge cases

- A comment written twice with the same words in one function: the fingerprint is the same, so the order of the two in the function is part of the identity, per FR-016 and FR-027.
- A line of a task list edited in a place and its item edited in the store at the same time: a conflict value naming the title and its three values, never a silent choice, per FR-017.
- A source that cannot write at all (a SARIF file, a read-only host): every patch for it goes to the outbox, per FR-014 and FR-033.
- A person closes an item and a later read of a place finds its text again: the person's event wins over the derived reopening, per FR-018.
- An item seen in three places: it has three traces and one id, and a close in one place is a patch to the other two, per FR-009 and FR-010.
- A requirement cited by no item: found by the matrix, per FR-021.
- A format that cannot hold links (a plain list): the rendering says so and the links are unexpressed with that reason, per FR-039 and FR-015.
- A configuration in JSON beside `planning.config.ts`: not read, per FR-037.
- A write to a file in a vendored folder that the configuration does not list: refused, per FR-027.
- A task list item whose character between the brackets is a tab or an uppercase `X`: read as unchecked and as checked, and written back as the library writes it, per FR-026.
- An event whose id is further ahead of the clock than the limit: refused when it is taken, per FR-007.
- An agent acting for a person who is later removed from the configuration: the events keep their principal as written; only a new event needs one that is established, per FR-005 and FR-045.

## Assumptions

- The library is Kanon (0033-kanon), uses AnyFS for every file, `githost` for Git hosts and Headless for its program, as the libraries of commons do.
- Items are public text unless a store is private: Planning holds no secret, no token and no person's data of its own, and its fixtures are made-up or public.
- A dataset of audit findings that a person offers is a candidate fixture, never assumed to be available.
- The monorepo's issue files are private and are not copied here: a test of the source for them (FR-025) runs over made-up files of the same schema.

## Key entities

- **Item** - one thing planned, of one of the kinds, with a stable id and a history of events.
- **Event** - one immutable thing that happened to an item, by an actor.
- **Actor** - a person, an agent or a tool; an agent names the person it acts for.
- **Observation** - what one source read in one place, with its locator and hash.
- **Patch** - a change to write back to one source.
- **Preview** - what a patch would write, with the hash a write is held to.
- **Source** - a lens over one kind of place, with its capabilities.

## Success criteria

- **SC-001**: One thing planned is one item with one id however many places it is in, and every place it was seen can be found from it.
- **SC-002**: A write changes only what the preview said, in the form of the place, or it changes nothing and says why.
- **SC-003**: A person can add a source in a typed configuration and a typed function, with no change to the library.
- **SC-004**: Every event an agent wrote names the person responsible for it, and no agent's event is counted as a person's.
