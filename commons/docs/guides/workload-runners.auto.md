# Runners: how a plan is carried out

Generated by `commons/workload/tools/pages.ts` from the code of the library `workload`; do not edit it.

A **runner** is how a plan is carried out. The **form** says what the work is, the **dialect** says how a harness or a person receives it, and the **runner** says what carries it out. A **native** runner is the TypeScript of the library: it interprets the plan on Bun or Node, is interactive, is the default and records the events of a run directly. An **integration** runner compiles the plan into an artifact, a script, that a foreign system runs, and then hands it off: the library keeps the plan, the policy and the evidence, and not the run. (Where this documentation names the machines of GitHub it calls them **hosts**, so that they are not confused with runners.)

A workload never names its runner. A fleet owns a `RunnerPolicy` (a default, which is `native`, a choice by workload, a choice by form and a preference by operator); a run resolves its runner as the explicit choice, then the operator's preference, then the choice for the workload, then the choice for its form, then the default. A runner that lacks something the workload needs is refused with `E-WL-RUNNER-UNSUITABLE`, and the run is never moved to another runner by itself. The autonomy derived for each node is the same under every runner.

| Runner | Kind | What it is | What it can carry |
|---|---|---|---|
| `bash` | integration | Bash 5 or later | `calls`, `fan-out` |
| `github-actions` | integration | GitHub Actions: a workflow of jobs that GitHub executes | `calls`, `fan-out`, `approval` |
| `native` | native | Native: the TypeScript of the library | `calls`, `fan-out`, `interactive`, `judge`, `approval`, `logic`, `compensate`, `destroy` |
| `pwsh` | integration | PowerShell 7 or later | `calls`, `fan-out` |

## What a workload needs of a runner

A form derives the needs of its workload from its nodes, and never has them declared:

- `calls`: a call of a verb by its id, with typed inputs.
- `fan-out`: a loop over a fixed list.
- `interactive`: a stop for a person.
- `judge`: a bounded judgement of an agent.
- `approval`: the approval of a gate by a person, ingested as evidence.
- `logic`: a computation of typed TypeScript: a branch, a diff, a plan.
- `compensate`: the undo of a step that succeeded.
- `destroy`: a destroy of a durable, git or external store.

A call of a verb or a check needs `calls`; an `each` needs `fan-out`; an `ask` needs `interactive`; a `judge` needs `judge`; a gate needs `approval`; a `branch`, a diff and a plan need `logic`; an `undo` needs `compensate`; a destroy of a durable, git or external store needs `destroy`, unless a gate guards it and then it needs `approval`; any other node that is `human-only` and that no gate guards needs `interactive`. Only the native runner has `interactive`, `judge`, `logic`, `compensate` and `destroy`, so a workload with an ask, a judge or an ungated destroy of a durable store is run by the native runner.

| Workload | Form | `bash` | `github-actions` | `native` | `pwsh` |
|---|---|---|---|---|---|
| `restore-drill` | runbook | lacks judge, approval | lacks judge | can carry it | lacks judge, approval |
| `converge-settings` | reconcile | lacks logic, approval, interactive | lacks logic, interactive | can carry it | lacks logic, approval, interactive |
| `synthetic-graph-01` | graph | lacks approval | can carry it | can carry it | lacks approval |
| `synthetic-graph-02` | graph | can carry it | can carry it | can carry it | can carry it |
| `synthetic-bootstrap-01` | runbook | can carry it | can carry it | can carry it | can carry it |

## What an artifact is

An artifact obeys the thin emit rule: it is only a sequence of calls to the pinned verb command by verb id, a loop over a fixed list and the order of the steps. It holds no expression, no inline logic, no `eval`, no command built from a string and no secret; a credential is only a name, and the verb command reads it from the environment. All meaning stays in typed TypeScript. The emitters target only Bash 5 or later, PowerShell 7 or later and the workflow of GitHub Actions. The artifact carries the hash of its plan, the same for every emitter, and writes one receipt line when it ends; ingest pulls the receipt and the library records it as a `receipt` event beside the `handoff` event that carried the same plan hash. `bun commons/workload/tools/runners.ts --check` regenerates the artifacts and compares: a hand-edited artifact is `E-WL-RUNNER-DRIFT`.

## The artifact of `synthetic-bootstrap-01` for `bash`

```bash
#!/usr/bin/env bash
# Generated by commons/workload from the plan of synthetic-bootstrap-01 0.1.0 (the form runbook); do not edit it: regenerate it.
# It is only calls to the pinned verb command by verb id, loops over fixed lists and the order of the steps.
# plan: 700d2ac5a01d61868d98c4179ddb14ba4711c53e58237bc8af4c2ac8c8ef1cc9
# credential: SYNTHETIC_TOKEN_01 (a name only: the verb command reads it from the environment)
# input: order (read from WORKLOAD_INPUT_ORDER)

if ((BASH_VERSINFO[0] < 5)); then
  printf 'workload: this script needs bash 5 or later\n' >&2
  exit 70
fi
set -Eeuo pipefail
shopt -s inherit_errexit

readonly plan_hash='700d2ac5a01d61868d98c4179ddb14ba4711c53e58237bc8af4c2ac8c8ef1cc9'
readonly workload_id='synthetic-bootstrap-01'
readonly runner_id='bash'
readonly cli=('workload')
current_step='none'

on_exit() {
  local status="$1"
  printf 'workload.receipt/1 plan=%s workload=%s runner=%s status=%d step=%s\n' "${plan_hash}" "${workload_id}" "${runner_id}" "${status}" "${current_step}" >&2
}
trap 'on_exit "$?"' EXIT

run_verb() {
  current_step="$1"
  shift
  "${cli[@]}" verb "$@"
}

# step install-check: check, agent-autonomous
run_verb 'install-check' 'workbench.ready' --in 'task=run'
# step claim-order: verb, agent-acts-human-reviews
run_verb 'claim-order' 'work.claim' --in "order=${WORKLOAD_INPUT_ORDER}"
# step record-hosts: each over hosts, agent-acts-human-reviews
members=('synthetic-host-01' 'synthetic-host-02')
for member in "${members[@]}"; do
  # step record-host: verb, agent-acts-human-reviews
  run_verb 'record-host' 'work.record' --in "order=${WORKLOAD_INPUT_ORDER}" --member "${member}"
done

current_step='done'
```

## The artifact of `synthetic-bootstrap-01` for `pwsh`

```powershell
#Requires -Version 7.0
# Generated by commons/workload from the plan of synthetic-bootstrap-01 0.1.0 (the form runbook); do not edit it: regenerate it.
# It is only calls to the pinned verb command by verb id, loops over fixed lists and the order of the steps.
# plan: 700d2ac5a01d61868d98c4179ddb14ba4711c53e58237bc8af4c2ac8c8ef1cc9
# credential: SYNTHETIC_TOKEN_01 (a name only: the verb command reads it from the environment)
# input: order (read from WORKLOAD_INPUT_ORDER)

Set-StrictMode -Version Latest
$ErrorActionPreference = 'Stop'

$PlanHash = '700d2ac5a01d61868d98c4179ddb14ba4711c53e58237bc8af4c2ac8c8ef1cc9'
$WorkloadId = 'synthetic-bootstrap-01'
$RunnerId = 'pwsh'
$Cli = 'workload'
$script:CurrentStep = 'none'
$script:Status = 0

function Invoke-Verb {
    param(
        [Parameter(Mandatory)] [string] $Step,
        [Parameter(Mandatory)] [string] $Verb,
        [string[]] $VerbArguments = @()
    )
    $script:CurrentStep = $Step
    & $Cli 'verb' $Verb @VerbArguments
    if ($LASTEXITCODE -ne 0) {
        $script:Status = $LASTEXITCODE
        throw ('workload: the step {0} failed with status {1}' -f $Step, $LASTEXITCODE)
    }
}

try {
    # step install-check: check, agent-autonomous
    Invoke-Verb -Step 'install-check' -Verb 'workbench.ready' -VerbArguments @('--in', 'task=run')
    # step claim-order: verb, agent-acts-human-reviews
    Invoke-Verb -Step 'claim-order' -Verb 'work.claim' -VerbArguments @('--in', ('order=' + (Get-Item -LiteralPath 'Env:WORKLOAD_INPUT_ORDER').Value))
    # step record-hosts: each over hosts, agent-acts-human-reviews
    foreach ($member in @('synthetic-host-01', 'synthetic-host-02')) {
        # step record-host: verb, agent-acts-human-reviews
        Invoke-Verb -Step 'record-host' -Verb 'work.record' -VerbArguments @('--in', ('order=' + (Get-Item -LiteralPath 'Env:WORKLOAD_INPUT_ORDER').Value), '--member', $member)
    }
    $script:CurrentStep = 'done'
}
catch {
    if ($script:Status -eq 0) { $script:Status = 1 }
    [Console]::Error.WriteLine($_.Exception.Message)
}
finally {
    [Console]::Error.WriteLine(('workload.receipt/1 plan={0} workload={1} runner={2} status={3} step={4}' -f $PlanHash, $WorkloadId, $RunnerId, $script:Status, $script:CurrentStep))
}
exit $script:Status
```

## GitHub Actions: a graph, a gate and a receipt

The runner `github-actions` writes a graph (the form of nodes with edges, `after`, which the platform calls `needs`) as a workflow whose jobs GitHub runs. Each step is one call of a pinned command by verb id; the workflow holds only what GitHub requires to wire the jobs (`needs`, a matrix over a fixed list, `permissions` that are the least the node asks for, `concurrency`, and references to the inputs and to the names of secrets), every action is pinned to a tag or a commit, and a node that a gate guards runs in a GitHub environment that a person approves. The library hands the workflow off with the hash of its plan and ingests what the run did, as a pure function of the result a caller pulled: the run, its conclusion, the conclusion of each job and the digest of its log become a `receipt` event matched to the hand-off by the plan hash, and an approval counts only where a person gave it and a person records it. The repository's own workflows are not made this way yet, and `commons/spec-kit/specs/0030-generated-workflows` keeps them byte for byte (the workload specification `0016-ci-on-graph` says why).

## Schedules

A trigger of kind `schedule` is a cadence (`hourly` to `yearly`) and a slot in UTC. For GitHub it is `on.schedule` inside the workflow. For `bash` and `pwsh` it is a cron line and a systemd timer with its service, for Linux, which only start the same artifact by its path; Windows Task Scheduler is not supported yet and a Scheduled Job is not in PowerShell 7, so a target of Windows is `E-WL-RUNNER-EMIT-UNSUPPORTED`. A trigger of kind `event` or `alert` is not realized by any runner: it is a statement of the specification.
