# Feature Specification: Docs

**Spec ID:** 0001-docs
**Status:** Draft
**Owner:** if
**Domain:** commons

**Input:** The generator of a repository's documentation site, as a library of its own that any repository installs from npm: a typed configuration (`docs.config.ts`) that names the packages, the spec kits, how specifications are cited and the lenses, the command `ifc-docs` that builds or checks the static site, and the factories of the lenses (layered models, programs, guides, releases) that a configuration passes. What the site is, and what it shows, is the documentation capability of commons (commons 0011-documentation); this specification is what makes the generator a package that other repositories, including a private one whose site is never published, depend on by name.

## Requirements

- **FR-001**: Docs MUST be a library of commons: the folder `commons/docs/` with a spec kit of its own, a manifest `library.ts`, an `about.ts` and a package named `@intellectual-frontiers/docs`, its sources in `src/`, proved by `bun run verify` in its folder.
- **FR-002**: The package MUST export, by package name, the entry of the generator (`.`: the types of the configuration, `DocsConfig`, `About`, `Lens`, `Page`, `Block` and the functions that build and check a site) and the factories of the lenses a configuration passes: `./lens/layered`, `./lens/program`, `./lens/guides`, `./lens/releases` and `./lens/repo-ops`, so that a repository's `docs.config.ts` imports them and nothing else of this library.
- **FR-003**: The package MUST have the command `ifc-docs` (`bin`): `ifc-docs build [--out DIR] [--config FILE]` writes the site, `ifc-docs check` builds it into a temporary folder and exits 1 where there is a finding, and both find the first `docs.config.ts` from the folder they run in up to the root of the repository.
- **FR-004**: The package MUST be built, inspected and packed by `tools/pack.ts` through the packer of commons: compiled modules and their declarations beside the sources (which Bun reads), the files of the theme beside the modules that read them, the command as a launcher of the compiled module, a `LICENSE`, and `dependencies` that are all real packages of npm (`typescript` at `7.1.0-beta`, `shiki`, `beautiful-mermaid` and the libraries of commons that are published) and none that is a link.
- **FR-005**: The packed package, installed into an empty project beside a small repository (a spec kit in the form of Mizan or of Spec Kit and a `docs.config.ts` that imports the package by its name), MUST build that repository's site with `ifc-docs build` and with `ifc-docs check`, with no finding, with every page a static file whose links are relative and that asks nothing of another host. In `single` distribution (commons 0036-distribution FR-019 to FR-024), the mode of the repository, Docs is a library of the one package `@intellectual-frontiers/commons` and not a package of its own: the package that is installed is that one, packed by `commons/commons`, the configuration imports `@intellectual-frontiers/commons/docs` and the command is its `bin/ifc-docs.mjs`; in `per-library` mode it is the package of Docs by itself.
- **FR-006**: A configuration MUST give the address and the branch of the repository (`repository`, `branch`), and the generator MUST make every link to a source file from those and from nothing else, so that a repository that is private, or hosted anywhere, has a site whose links go where its configuration says and whose pages name no other host.
- **FR-007**: The pages MUST be one model that more than one presentation writes: `web` (the static site), `markdown` (the Markdown twin of each page and `llms.txt`), `data` (the JSON the lenses add) and `book` (FR-008). Each presentation makes its files in memory as a list, so that the same list is written by `ifc-docs build` into the output folder, or compared with the folder by `ifc-docs build --check`, which writes nothing and exits 1 where a file is missing or differs. A configuration names the presentations it writes (`presentations`; `web`, `markdown` and `data` by default, which is the site as it has always been) and the command line overrides them with `--presentation NAME[,NAME]`; a name that is not one, `book` with no volume configured, and `--presentation` or `--check` with `check` are refused. The folder is emptied before a write only where `web` is written, so that a book is written into a folder that holds other things.
- **FR-008**: The `book` presentation MUST write each volume that the configuration's `books` names as one AsciiDoc file, `<volume>/generated/<volume>.adoc`, which a book of `erga` (kind `book`) includes as a generated chapter source, and `books.json`, which lists the volumes, their parts and their page counts. A volume has parts, and a part selects pages by section, group and path prefix (`exclude` leaves some out; `perGroup` makes a part of each group); a page is in the first part that selects it, is a chapter of its part, and is a section of its parent's chapter where its parent is in the part. The file MUST begin with the line that says it is generated and how to write it again, hold no date and no revision (the same pages give the same bytes), and use only what AsciidoctorJ reads as it is: parts and chapters with anchors that no volume has twice, source blocks, admonitions, tables, lists, cross references to pages of the volume and, for a page that is not in it, a link to the site where `books.site` names one and its text where it does not. Text that AsciiDoc would read as markup is passed through, and a diagram is shown as its source. A part that selects no page is a finding.
- **FR-009**: A configuration MAY give `evidence`: a folder of test results (`results`: CTRF, one `<library>.ctrf.json` for each library, with the requirements each test proves in `extra.requirements`, and `meta.json` with the commit and when), a snapshot of the GitHub issues of the repository (`github`: the JSON of the API, pull requests left out) and the issues of the libraries kept as typed code (`issues`: a library and its issues, with a `scope` where a library keeps more than one set). The generator MUST read them as files, import no library that makes them and reach no network; a folder that is not there MUST be no run recorded, a file that is not JSON or not CTRF a finding, a test's path a path from the repository's root made with the library's folder, and a ticket tied to a library by a label `lib:<name>` or a path `commons/<name>/` and to requirements by the ids in its words.
- **FR-010**: Where `evidence` is configured, the site MUST have a Quality section: a dashboard with a row for each library (tests, passed, failed, skipped, requirements proved, open issues, open tickets) that says which commit and when the results are of, and a banner where a test failed; a page for each library (its failing tests with why, its skipped or planned, its slowest, the requirements no passing test proves, its open issues and tickets); the register of the issues and tickets; and a page for each issue kept as typed code (its facts, the requirements it cites as links where a specification of the kits has them and as code where none does, its evidence, its related issues). With no run recorded the pages MUST say so and nothing MUST be shown as passed; with no `evidence` there MUST be no section.
- **FR-011**: The evidence MUST also be beside the code: each requirement of a specification with a badge (`passing` where every test that names it passed, `failing`, `partly run`, `no test run`), its tests with their results and the open issues and tickets that name it; each library's page with its tests, requirements proved and open issues; each area's and module's page with the requirements its code is written to and what the tests of them say; and the numbers as `quality.json`. A test that names a requirement that its specification does not have MUST be a finding. A failing test MUST NOT be a finding of `check`: it is what the site is to show.
- **FR-012**: The package MUST have a tool, `tools/evidence.ts` (`bun tools/evidence.ts --library NAME [--out DIR]`), that runs a library's suite with `ifc test run`, as a program and not as an import, and keeps its CTRF report as `<DIR>/<library>.ctrf.json` with a `meta.json` where there is none, whether the tests pass or fail; it MUST refuse, with exit status 2, a library with no suite.
- **FR-013**: The package MUST have a tool, `tools/ci-runs.ts`, that asks the GitHub API (through `gh`) for the last runs of each workflow of the repository on `main` and, for the latest failed ones, which jobs failed and at which step, and writes them as `runs.json`; where the API cannot be reached it MUST write a file that says so and exit 0.
- **FR-014**: The package MUST have a tool, `tools/status-site.ts`, that writes one self-contained page from the evidence alone (the end of the build's log, the commit and when, the tests library by library, why a library has no report, the workflows' latest runs), for a build that failed; it MUST use no part of the generator and exit 0 whatever is missing.
- **FR-015**: A configuration MAY give `problems` (what could not be read while it was made) and the generator MUST make each a finding, and a lens that throws, in its reading, its pages or its files, MUST be a finding and not stop the site: one library or one lens MUST NOT keep the site from being made.
- **FR-016**: The site MUST show how quality moved, from a history of the evidence: the package MUST have a tool, `tools/history.ts`, that adds one run (for each library the counts of its tests, how long they took, and the identity and name of each test that failed, and the libraries that left no report) to the files `history/runs/<time>-<run>.json`, adds a run once, keeps the newest and refuses evidence with no time; the generator MUST read those files beside the results and show, on each library's page, trends of its tests, pass rate and time as lines drawn in the page, the tests that began to fail in the latest run with the range of commits since the run before, the tests that were fixed, those that failed in more than one separate stretch and pass in the latest (flapping), and its failures grouped by cause; and, on the dashboard, a pass-rate trend and the count of flapping tests for each library.
- **FR-017**: A configuration MAY give a gate (`evidence.gate`: `ran`, `tests-pass`, `no-blocking-issues`, and `requirements-proved` with a minimum percent; the first three where none is given), and the site MUST show for each library which conditions it holds and why not, and a mark for it on the dashboard, and MUST enforce nothing: the gate is shown and the site is published whatever it says. The site MUST also have a page of the requirements by specification (how many are proved, partly, failing, with no test) and, for each library, a JSON file of its quality (`quality/<library>.json`: tests, failing tests, requirements not proved, gate, history, what began to fail, was fixed or flaps, open issues and tickets).
- **FR-018**: The site MUST have a page of the dependencies of the libraries, read from their `package.json` files (what each imports of the others and of npm, who imports it, its licence, and the external packages with who uses each), and an SBOM, `sbom.cdx.json`, in CycloneDX 1.5 with a component for each library and each external package version and the dependencies between them, the same for the same files; and a page of the TODO, FIXME, XXX and HACK notes left in the sources, with the file and line as a link.
- **FR-019**: The site MUST have a page of the acceptance kits of the libraries (a folder `acceptance`, `oat`, `uat` or `aat` with kits that have a README), with each kit's kind and its known and fixed findings from its `FINDINGS.md`; and the page of the workflows MUST say for each workflow the share of runs that passed, the median minutes a run takes and the median time from a failure to the next pass, from the runs it reads.
- **FR-020**: The site MUST have a page of hotspots and ownership read from `git log` at the build in one pass: for each library its commits and authors in the last 90 days and its bus factor (how few authors made half of its commits), counted and never named; the files changed in the most commits; and the specifications changed after the newest test that proves them, with the days between. Where the history is not there the page MUST say so and show nothing made up, and a short history MUST be said to be short.
- **FR-021**: The site MUST have a page of the repository's health made from its own files, naming for each check the OpenSSF Scorecard check it answers: whether the workflows declare their token's permissions, how many outside actions are pinned to a commit, that none runs untrusted code with secrets, the security policy, the licence, a tool that updates dependencies, a lockfile, CODEOWNERS, contributing guidance and tests in CI; it MUST say that settings of the host (branch protection, required reviews) are not shown by files.
- **FR-022**: Where the evidence has the line coverage of a library (`<library>.coverage.json`, kept by `tools/evidence.ts --coverage` from the LCOV of the library's tests, source files only), the Quality dashboard MUST show its percent beside the pass rate and the library's page MUST show the percent, the number of lines and the least covered files; a library with no coverage shows none, and a coverage run that fails MUST NOT lose the test report.
- **FR-023**: The workflows page MUST give, from the runs of the workflow that publishes the site, the four measures of DORA (deployment frequency, lead time, change failure rate, time to restore), saying what each is taken from; cancelled and skipped runs are left out, and with fewer than two runs it shows none.
- **FR-024**: Code of the language `sql` MUST be coloured by the lexer of the SQL language library (`lang-sql/aide/text` `highlight`, in the PostgreSQL dialect) where it reads the text with no error, so that a word is a keyword where the dialect says so, a function is a word followed by `(`, a word in a string or a comment is none of them and a dollar quote is one string, with the same colours the other languages give a keyword, a call, a number, a string and a comment; where the lexer cannot read the text (a stray character, a string that is not closed) it MUST be coloured by the grammar of Shiki as before; no run of text is lost or changed.
- **FR-025**: Where a run is recorded, the entry of an export on its API page MUST say how many tests of the run, of its package, import it and how many of them failed (naming up to three failing ones), and link the library's results; an export no test imports MUST say so, and the module's page MUST say how many of its exports are imported by a test. It MUST say that importing is not calling.
- **FR-026**: The API page of a source file MUST list the open issues (kept as typed code, naming the file or a test of it in their evidence) and the open tickets (naming its path in their title or words) that name it, with a badge that counts them, and the file evidence of an issue MUST link to the file's page where it has one; a path that is only the beginning of another is another file, and with none the page says nothing of it.
- **FR-027**: Where the evidence has the mutation run of a library (`<library>.mutation.json`, kept by `tools/mutation.ts` from Stryker's report: the mutants of each source file that were killed, timed out, survived or were not run), the Quality dashboard MUST show its score (the share the tests detected, errors and ignored mutants not counted), the library's page MUST show the score, its weakest files and the changes no test noticed, and the API page of a mutated file MUST show the file's score; a library with no run shows none. The tool MUST leave the working tree as it found it.
- **FR-028**: The site MUST have a page of what changed since the commit the tests of the evidence ran on (or, where that commit is not in the history, in the last thirty commits): the changed files by library, and for each changed source file its line coverage, its mutation score and the open issues that name it, least covered first, with a file added since the tests ran shown as new; and the specifications changed. Without history it MUST say so and show nothing made up.
- **FR-029**: The site MUST have a section Repo Ops that explains how the repository is operated, made by a lens (`repoOpsLens`, `./lens/repo-ops`) from pages people write in Markdown and from typed facts the configuration passes, so that what can be generated stays true: a page of the workflows (each one's file, its triggers, its jobs and what it is for, read from the typed definitions the workflow files are made from), a page of the commands of the repository's operations program (each verb's words, summary, effect, tier, whether it previews, checks and is safe to repeat, its options and its examples, read from the program's own typed verb definitions, with a link to the page of the verb in Programs), and a page of the facts of the release (the distribution mode and its targets). The pages written by people link to the details elsewhere in the site and do not copy them (a Markdown link written `site:<path>` goes to that page of the site, and the check of the links finds it where the page is not there). A page the lens cannot read is a finding and the other pages are made; a section with no page is not in the top bar.
- **FR-030**: The Quality section MUST have a page of the build's findings, `quality/build-findings.html`, made from the findings of the runs of the workflows that the evidence holds (`findings-history/runs/**/*.json`, the files of commons 0038-build-policy FR-006, laid out from the history branch by the workflow `site`) and from the accepted risks (`accepted-findings.json`, read from the typed files by `ci/accepted.ts --json`): the policy it states MUST be written from the typed values the workflows are made from (the red causes with their reasons and the release policy with its day), so that the page and the pipeline cannot disagree; it MUST show the counts (open, new in the latest run, fixed in it, accepted), the findings by module with the age of the oldest, the trend by workflow, each open finding with its tool, code, place, severity, age and stable id, and each accepted risk with its owner, reason, end and approver, an acceptance that has ended being shown as ended and its finding as open again; it MUST carry the banner `Owner review due` where the release policy has ended on the day of the latest run; it MUST give every row as `quality/build-findings.json` and `quality/build-findings.csv`; and where no run has kept findings it MUST say so and show nothing as a pass. The page MUST identify observed Kanon import checks and their latest outcomes; where no check is recorded it MUST distinguish missing evidence from a clean run.
- **FR-032**: The site MUST have a page `quality/package` about the package `@intellectual-frontiers/commons`, made from the evidence: `package.report.json` (what the packer reports when it packs the package: the files and bytes of the package, of each library and of each kind of file, its dependencies and its optional peers with their ranges, and its budget) and `usage.<consumer>.json` (the answer of `repoctl usage --json` for a consumer repository). It MUST show the package against its budget with the share used, the sizes by kind of file and by library (filterable), what the package installs and what it asks of the consumer, and, for each consumer kept, the libraries imported, those reached through them and those never touched with their sizes; it MUST work out nothing but the share of the budget; a file that is not what its name says MUST be a finding of the generator and MUST NOT stop the page; and where no report is kept the page MUST say how to make one and show nothing as measured (commons 0036-distribution FR-032, FR-034).
- **FR-033**: Every page of the site MUST say which release of the package `@intellectual-frontiers/commons` it describes: the site's name at the top of every page, in the title of the tab and in the footer is followed by `v<version>` (for commons, `IF Commons v0.4.2`), and the footer says the release's date where it is known, the commit the site was built from and, where the release record is known and the history is whole, how many commits the branch is ahead of the commit that made the release record (a badge `N commits since the release` where N is not zero). The version MUST be the newest stable version the package registry holds (the evidence file `registry.json`: the versions with their dates, kept by the workflow that builds the site); where there is no such file (a build on a person's computer) it MUST be the version of the package's own `package.json`, and the footer and the tooltip of the version MUST then say it is not confirmed on the registry; a version ahead of the registry MUST never be shown as the registry's. A registry that could not be read (the file says it could not) MUST be a finding of the generator that says why, and MUST NOT stop the site.
- **FR-034**: The site MUST have a page of the package's packaging under Repo Ops (`repo-ops/packaging.html`), written by people and completed by the evidence, that explains the strategy (one package, a library per subpath, the distribution mode and the registry it goes to, the content policy and the budget, the optional peers and why they are declared where the registry keeps them, how a consumer pins an exact version, and that the superseded versions are deleted from the registry by the workflow `maintenance` and kept as tags) and shows what the evidence knows: the release now with the versions the registry holds and their dates, the package against its budget (files, apparent size and tarball), the sizes by kind of file, the largest libraries, what the package installs and asks of the consumer, with a link to `quality/package` for the whole report. It MUST work out nothing but shares; where no report is kept it MUST say how to make one and show nothing as measured; it MUST NOT show a trend over releases that no record holds.
- **FR-035**: The site MUST request nothing from another host and MUST depend on no stylesheet, script, font, image or package of another project, at run time or at build time (commons 0011-documentation FR-017): its typefaces MUST be files of the site, Latin subsets of the variable fonts Inter (text) and JetBrains Mono (code), both under the SIL Open Font License 1.1, whose license texts MUST travel beside the files and whose items MUST be in `THIRD_PARTY_NOTICES.md`; a character the subsets lack MUST fall back to the system's fonts and never to a font of another host. Its icons are the paths of the Lucide set (ISC), which `THIRD_PARTY_NOTICES.md` MUST list, drawn in the pages and never loaded.
- **FR-036**: The look of the site MUST be copied from the documentation theme of Fumadocs (MIT, Copyright (c) 2023 Fuma) and not invented: its colour tokens (`--color-fd-*`, light and dark), its widths, spacings, radii, type sizes, transitions and the classes of each of its components are the values of the version recorded in `src/theme/fumadocs.provenance.json` (the package `fumadocs-ui`, and the live documentation site where that package lacks the layout the site shows), and the stylesheet `src/theme/fumadocs.css` MUST be what Tailwind CSS makes of exactly the classes the pages use, compiled once by a development tool that is not a dependency of the library, of its package or of its build (`tools/fumadocs-css.mjs` says how, and `bun run verify` MUST find that the stylesheet and the provenance file agree). The one departure from the reference, listed in the provenance file and in `NOTICE`, is the reading area of the light theme, which is white (`#ffffff`) instead of the reference's off-white; the dark theme is the reference's. The text of every token pair that carries text (text on the page, muted text on the page and on the panels, the primary text, the current item of the navigation) MUST have a contrast of at least 4.5 to 1 against its background in both themes, which a test computes from the stylesheet, never from a screenshot.
- **FR-037**: A page MUST have the layout of the reference (its `spacious` layout, the one its own documentation shows): a grid of the side navigation (268 pixels), a panel with rounded corners that holds the page, and in the panel the article beside an outline of the page (304 pixels) that follows the reader and marks the heading being read; the panel's header holds the controls; the article's width is the reference's (`--fd-page-width`, 760 pixels) and the layout has no other width, so that it fills the screen of any size. The side navigation holds the name of the site with its version, a selector of the sections, the search, the groups of the section and their pages, with folders that open and close with a chevron where the group of the current page is open; the page has the title and its description, the actions row, the trail and the previous and next page as the reference draws them. On a screen narrower than 768 pixels the side navigation MUST be a drawer opened from a button of the header (it holds the sections, the theme and the width controls), the outline MUST be the reference's popover under the header, and nothing MUST scroll sideways on a screen 360 pixels wide but code and wide tables.
- **FR-038**: The components a page is made of MUST be the reference's, with its markup and classes: callouts of three tones (a note, a limit, a warning) with the colour of the reference's information, warning and error, cards for the pages of a section, tabs, code with a title bar and a button that copies it (highlighted in the dark and the light variants of the reference's two themes, as CSS variables, so that the theme needs no second drawing), tables in the reference's scrolling wrapper (with a filter where a page asks for one), a file tree, and on the first page of the site a short heading, the number of libraries, specifications, requirements and exports as tiles, and the sections as cards. A block with no component in the reference (the badges, the tiles, the trend lines, the entries of the API, the diagrams) MUST be drawn with the reference's tokens and classes of its nearest component and MUST be listed in the provenance file. The motion MUST stop for a reader who asks for less (`prefers-reduced-motion`), the keyboard MUST reach every control with a visible focus, and the print style MUST leave out the chrome and let the page flow.
- **FR-039**: The workflow that builds the site MUST keep the evidence the pages above need: `registry.json` (the versions of the package that the registry holds with their dates, read with the job's own token, which may read packages; or a file that says why it could not be read) and `package.report.json` (what the packer says of the package at the commit), and a step that fails to make either MUST end green and leave a finding and the page that says nothing was measured (commons 0038-build-policy).
- **FR-040**: A reader MUST be able to switch the layout between the reference's width (the default: the article is 760 pixels wide) and the full width (the article takes all that the screen leaves beside the side navigation and the outline, and a wide table or matrix uses it) with a button of the header, drawn like the button of the theme, with an accessible name that says what it does and its state (`aria-pressed`), reachable and operable by the keyboard; the choice MUST be kept in a cookie of the site (`ifc-docs-width`, `full` or `default`, `Path` the site's base path, one year, `SameSite=Lax`, and `Secure` where the page is served over `https`) and MUST be applied by a script in the head before the page is first drawn, so that nothing flashes; a reader whose browser blocks cookies MUST get a page that works, with the default width and a button that still changes it for the page being read.
- **FR-041**: The provenance file MUST record the package `fumadocs-ui` and the Tailwind CSS versions the stylesheet was made with, the address and the day of the live pages whose computed styles were read where they differ from the package, the list of the blocks the reference has no component for, and the one departure of FR-036; `NOTICE` and `THIRD_PARTY_NOTICES.md` MUST credit Fumadocs, say that its design (the values and the structure of its layout and components) is what was copied, and carry the text of its license.
- **FR-042**: The look MUST be checked against the reference, not by eye: for the first page of the reference's documentation and the matching page of the site, at widths of 1440 and 1920 pixels in both themes, the width, the padding, the font size, the line height and the colours of each region (the side navigation, the header, the article, the outline, the footer links, a code block, a callout, a table and the search dialog) are measured in a browser and the differences are recorded (`bun run verify` keeps the record of the last check in the evidence and does not run a browser); a difference that is not the white reading area, the typefaces or the content of the page is a defect of the site.
- **FR-043**: The site MUST have a page `overview/families.html`, "Libraries by family", that lists the libraries of commons by family: a host with its extensions (the host first, then plugins, then dialects), and, for the libraries of no host, the named group of their manifest; the `Family` and `Role` facts of each library's page MUST be written from its manifest (`family`, or `group`), and the page MUST change no folder and no name.
- **FR-044**: The side navigation of the libraries MUST nest: a family is one collapsible folder whose own page is its host's and whose extensions are beneath it under their short names (`Bridge` under `AnyFS`, and under `Archon`, `Boot` among the plugins and `Ansible` among the dialects), a named group of libraries of no host is one folder with a page of its own, and a library of neither stands alone; the folder of the page being read MUST be open and the others closed; the cards of the Libraries overview MUST be one for each family or group and one for each library that stands alone, and no two libraries of one family MUST stand side by side in the navigation.
- **FR-045**: The explanation of Mizan, the IF Spec Profile, MUST be pages of the documentation and no other document: the group `Mizan` of the Concepts section MUST hold the overview `concepts/mizan.html` and one page for each of the sixteen parts of the explanation (the idea in one page, the drift problem, the two languages, Spec Kit, how a specification is written, the ladder, standards first, the typed ontology, the integrations, IFCCM, IFQS, AI-first, the controls against drift, what is built and not verified, the decisions taken and the glossary), in that order, each as a guide in `commons/docs/guides/` named `mizan-*.md`; the diagrams MUST be Mermaid in the page; a link between the pages MUST be a link of the site; and the root of the repository MUST hold no `MIZAN.html`.
- **FR-046**: The explanation of Kanon MUST be pages of the documentation: the group `Kanon` of the Concepts section MUST hold the overview `concepts/kanon.html` and one page each for why Kanon exists, Kanon in one page, one rule through three layers, the trace graph and nothing silently dropped, imports run one way, families, hosts and plugins, content and renditions, adopting Kanon in a library, what consumers gain (with a one-page brief for technical executives), the weaknesses and how to avoid them, the decision guide and FAQ, and the glossary and sources, in that order, as guides in `commons/docs/guides/`, every link between them resolved by the site build and at least nine diagrams Mermaid. A code block that names its source (`source=<path>#L<a>-L<b>` after its language) MUST equal those lines of that file, so that a quoted block cannot drift from the code; a block of output (`output="<command>; <date>"`) MUST name the command that produced it and the day it was run; the pages MUST state what is built and what is a draft (commons 0033-kanon is a Draft) and MUST label each benefit as measured, shown or an expectation; and the group MUST hold at least eleven thousand words and no dash that is a long or a medium one.
- **FR-047**: The CI/CD page MUST have a section "Build time": for each workflow the median and the 90th percentile of the wall time of its runs on `main` that passed, held against typed targets (`BUILD_TIME_TARGETS` in `src/ci-timing.ts`), and for each the slowest jobs with the median, the 90th percentile and the slowest step of each, from the jobs of the latest runs that passed (`tools/ci-runs.ts --timing N`, which writes them with the runs). A workflow over its target MUST be named on the page as a finding and MUST NOT fail the build (commons 0038-build-policy); where no run was timed the section MUST be absent.


## Out of scope

- Publishing the site (GitHub Pages, a private artifact store): the consumer's; this library writes a folder.
- What the site of commons shows: commons 0011-documentation.

## Edge cases

- A repository with no spec kit: a site with its API reference and its overview, and no Specifications section, per FR-005.
- A configuration whose `repository` is not a GitHub address: links to files are made from it as given, per FR-006.
