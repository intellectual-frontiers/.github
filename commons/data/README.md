# @intellectual-frontiers/data

Governance (what a business domain is and what must be true of its data), a logical schema made from it, and a physical schema for PostgreSQL, SQLite or DuckDB made from that, with extensions to each, and the lifecycle that changes a database from one physical schema to the next. It is an independent library of commons with its own specifications (`spec-kit/`, 0001 to 0047).

**Full documentation: [README.html](https://htmlpreview.github.io/?https://github.com/intellectual-frontiers/.github/blob/main/commons/data/README.html)** (diagrams, every extension with an example, strategies, presets, limits and roadmap).

## Example

```ts
import { attribute, concept, domain, identifier, text } from "@intellectual-frontiers/data/governance";
import { projectDomain } from "@intellectual-frontiers/data/sql/logical";
import { bind, render } from "@intellectual-frontiers/data/sql/physical";
import { dialect } from "@intellectual-frontiers/data/sql/dialects/sqlite";
const book = concept("book", { definition: "A written work", identifiedBy: ["id"], attributes: {
  id: attribute(identifier(), { definition: "What identifies it" }), title: attribute(text(), { definition: "What it is called" }) } });
const d = domain("library", { definition: "Books", concepts: [book] });
const p = d.kind === "ok" ? projectDomain(d.value) : undefined;
const sql = p?.kind === "ok" ? bind(p.value.schema, { dialect }) : undefined;
if (sql?.kind === "ok") console.log(render(sql.value)); // CREATE TABLE IF NOT EXISTS "book" (...)
```

## Layers

Each layer imports only the layers below it and the engine; a check of the library holds every import to that table.

- `engine/`: the extension host (contribution points, manifests, `compose`, lazy activation).
- `governance/`: domains, code lists, annotations, the vocabularies (documentation, requirements, privacy, security, ownership, quality, usage, lifecycle), lint, the trace graph; Arca's party model is in `models/arca`.
- `sql/logical/`: tables, columns and keys made from governance by a projection.
- `sql/physical/`: a logical schema bound to a dialect and a case style, as statements.
- `sql/lifecycle/`: state and hash, diff and plan, the hash-chained ledger, `execute`.
- `sql/dialects/`: PostgreSQL, SQLite and DuckDB.
- `sql/extensions/`: documentation, views, access, routines, partitions, generators, idempotency, protected-access, safety, plan-report, rewrite, history, convergence, rollout, integrations (rows, CSV, an attached database or an adapter, loaded by append, upsert, replace or snapshot in one transaction, with a ledger), transforms (models built in order, each with its tests in one transaction, published only if they pass), queries (read-only, typed parameters, checked between schema versions), target (a database as a build product: one deterministic SQL file), kinds (reference data from CSV as typed rows and a TypeScript module), osquery-atc (the auto_table_construction configuration).
- Convergence reads column defaults (a default changed by hand is drift), can hold what a person made outside the model (`unmanaged: "hold"`), and a table made again on SQLite must keep its triggers or the step rolls back; the decision engine reads the kinds a role or permission is for and never allows under a caveat it does not evaluate.
- `sql/presets/`: reviewed-convergence (the default) and autonomous-convergence, which compute each database's plan from the state it is in; team-managed and dba-managed, which replay files that people prepared.
- Modules: `governance/module.ts` composes the subject areas a project lists into one domain, so a module that is not listed has no table.
- Models: `models/arca` (party), `models/arca-tenancy` (tenants, for B2B and B2B2C) and the identity modules (`models/identity`, `identity-access`, `-abac`, `-rebac`, `-pki`, `-machine`, `-device`, `-delegation`, `-agent`): one principal of five kinds (person, machine, device, AI agent, group) with roles, attributes, relationships, delegation and agent provenance, each a module a project composes only if it needs it. `sql/extensions/operations/identity` holds the decision engine (`decide`: roles, groups, relationships and policies; refusal wins, unknown never allows; a delegation never adds), the hash-chained audit sink and the operations of delegation and agents (tool calls with budgets and single-use approvals, the kill switch).
- Operations: contracts in `governance/operation.ts`, run by `sql/extensions/operations` in one transaction with typed row operations, an authorizer and an audit sink.
- Sealed scopes: `accessSource({ seal })` makes a row-security policy trust a scope only with the issuer's mark (`sealedScope`), with the key unreadable to application roles and a guard against weakening it; operations must say how access is decided (`requires`, `public` or `checkedBy`).
- Invariants and enforcement: `quality.appendOnly`, `transitions` and `atMost` say what must always be true of the records of a concept; `sql/extensions/invariants` writes them as triggers (PostgreSQL, SQLite); `enforcementOf` and `where` say, per dialect, what the database can enforce and what is left to the application (PostgreSQL all of it, with an event-trigger guard against dropping or disabling an invariant; SQLite triggers but no roles; DuckDB checks and keys only).
- `arcactl` (`sql/cli/`, 0046): the command that checks and maintains the arca models in PostgreSQL. `arcactl doctor` is read-only and runs nine checks (connection, initialised, drift, ledger chain, invariant triggers, the guard, row security and the seal, the recomputed audit chain, what the database enforces) with exit codes 0, 1 and 2 and `--json`; Bun's own client by default, `pg` on Node, libpq's environment and files for the password, which is never printed. `arcactl init` sets up your workstation (not a database): it finds the instances you can reach and what you could do to each, then, once you agree (`--yes`; `--dry-run` shows only), writes the service, the password (`.pgpass`, mode 0600), the psql files and a cached shell script sourced from your profile; idempotent, `--undo` removes only what it put in, refused on a server; `arcactl doctor --scope workstation` checks it. Published as `@intellectual-frontiers/arcactl` (a build target of this library: `bun tools/pack.ts`; `bunx` or `npx @intellectual-frontiers/arcactl doctor ...`). Tested on PGlite, in process and over a socket with both clients. Two models of running (0047): the workstation (a person at a terminal; `init` sets up their `.pgpass`, `pg_service.conf`, `.psqlrc` and shell profiles through managed blocks, never a database) and the server (pipelines and containers: nothing asked, no home file written, secrets as variables or `NAME_FILE`); `ensure` will keep an instance and its migrations current. `arcactl shell` prints one script per shell (bash, zsh, fish, PowerShell, nushell, sh) with the `ARCA_*`, `PGSERVICE` and `PGOPTIONS` setup, `arca-doctor`/`arca-psql`/`arca-use`/`arca-off` and completions; it holds no password and connects to nothing.
- Issues as code: `governance/issue.ts` makes an issue a typed value (a `fixed` status carries its proof, a duplicate its original, a refused one its reason), kept as `issues/00001-<slug>.ts` files listed by `issues/mod.ts` in the library and in each module, checked by `bun run verify` (numbers, moves, proofs that resolve); `models/issues` and `sql/extensions/issues` keep a copy in a database (`syncIssues`: add, rewrite by hash, withdraw, reopen, one transaction, a ledger).
- Typed tables, columns, rows and queries (`sql/typed`, 0053; ported from SQL Aide): `Expr<T>` expressions that only compile for the types they fit, tables with a typed column for each key, a query builder (`from(...).innerJoin/leftJoin/rightJoin/fullJoin/crossJoin`, where, groupBy, having, orderBy, limit, offset, distinct, union/intersect/except, `in`/`exists`/value subqueries, CTEs, derived tables, self-joins) whose rows have the type the select names (an outer join makes the other side nullable), and `insertInto`/`update`/`deleteFrom` with `returning` and upserts (an update or delete cannot be run without `where` or `all`). Each model gets its own generated file, `sql/typed/models/<model>.auto.ts` (`bun tools/typed.ts --write`; checked by `verify`): a row type, an insert type, a key type and a typed table for each table, with closed code lists as unions.
- Loads and extracts (`sql/loads`, 0054): ETL/ELT as typed values. Sources (rows, CSV with a typed parser for each cell and rejected lines reported by line, JSON lines, a select of another database), `runLoad` into a typed table in `append`, `skip-existing`, `upsert` or `replace` mode in one transaction with a ledger of runs (`load_run`), ELT through a staging table gated by SQL-DQ tests (merged only where they pass), a high-water mark for incremental loads (`watermarkOf`), `extractCsv` and `extractJsonLines`, and copies between any two engines. Dialect-native bulk paths, Parquet, HTTP and object-store connectors and orchestration are the rest of issue 10.
- Reading a live database (`sql/lifecycle`, 0055): `introspect(driver, dialect)` reads the tables, columns (type, nullability, default), keys, unique constraints, foreign keys and indexes of a SQLite, DuckDB or PostgreSQL database; `expectedOf(schema, dialect)` writes the same value from a model; `drift` names every difference (missing or stray tables and columns, types of another family, nullability, keys, missing foreign keys, uniques and indexes); `adopt` makes a logical schema of a database nobody modelled, which makes the same database again on any of the three engines.
- Driver adapters (`sql/drivers`, 0056): `sqliteDriver`, `pgDriver`, `pgliteDriver`, `duckdbDriver`, `bunSqlDriver` and `driverFor`, each typed by the shape of the client, so the library depends on none; a wide integer is a number and a row a plain object.
- Describing models in layers (`sql/describe`, 0057): `describeModels` gives, for each module, its governance (module, concept, attribute, relationship, code list, code), logical (table, column, keys) and physical (SQL for each dialect, the typed table) elements with stable ids, definitions, the trace from each element to what it is made into and findings (no definition, personal data held for no purpose). The documentation site (`commons/docs`, 0011 FR-029) turns it into the Models section: the layers and how to change a model, each model, concept (with a link to the file and line where it is written, its SQL and its typed table) and code list, the registers, a Markdown twin of every page, and the JSON of each model.
- SQL-DQ, the data quality library (`sql/quality`, 0052): dbt's data tests as an algebra of typed values. A generic test has a level (column or model) and the type of its arguments, so a test of a column does not compile on a model and missing arguments do not compile; built-ins (`notNull`, `unique`, `acceptedValues`, `relationships`) and package tests (`expressionIsTrue`, `uniqueCombinationOfColumns`, `acceptedRange`, `equality`, ...); singular tests; config (`severity`, `warnIf`/`errorIf`, `where`, `limit`, `failCalc`, `storeFailures(As)`, tags, enabled, name); selection; `runTests` through any driver on SQLite, DuckDB and PostgreSQL; results as TAP; `testsFromState` derives the tests a schema asks for.
- Ported from SQL Aide (0048 to 0051): `sql/extensions/objects` (sequence, enum, domain, schema and extension DDL), `sql/extensions/assertions` (pgTAP and TAP, structural assertions from a state), the typed PL/pgSQL body DSL in `sql/extensions/routines`, and the `sql`, `lint`, `generate` and `list` project commands of `arcactl`. Known gaps against dbt and for data loads (ETL/ELT) are issues 10 and 11.
- `sql/cli/`: the command line; in the layers table, not yet built.

## Verify

```sh
cd commons/data && bun run verify
```

This runs the TypeScript compiler, the specification checker and the rules on `spec-kit/`, the layers and trace check, and the tests, which run on real SQLite, DuckDB and PGlite engines.
