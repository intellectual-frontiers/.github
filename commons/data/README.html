@intellectual-frontiers/data

Governance in, SQL out, and a safe way to change the database

A library of Intellectual Frontiers commons. A governance layer says what a business domain is and what must be true of its data; a logical schema is made from it; a physical schema for PostgreSQL, SQLite or DuckDB is made from that; a lifecycle layer changes a database from one physical schema to the next; and extensions add the rest.

Version 0.0.0, conformance level L1, private package, Node ≥ 26 (Bun is the default runtime). Specifications 0001 to 0046 are in force, in spec-kit/.

Purpose

The summary the library gives of itself (about.ts): governance (what a business domain is and what must be true of its data), a logical schema made from it, and a physical schema for PostgreSQL, SQLite or DuckDB made from that, with extensions to each, and the lifecycle that changes a database from one physical schema to the next. It is a library of commons with its own specifications, and the manifest (library.ts) says the same: a governance layer, a logical schema and a physical schema, and the extensions to each, produce SQL for PostgreSQL, SQLite and DuckDB.

One source of truth
A domain is TypeScript. Documentation, privacy, security, ownership, quality and requirements are annotations on it, and they reach the database, the generated files and the plan report.
One direction
Each layer imports only the layers below it and the engine. A check of the library holds every import to that table.
Values, not side effects
Failures are Result values, a plan is a pure function, and nothing registers by being imported.

The package declares no dependencies; its devDependencies are the kernel of IFC TypeScript (@intellectual-frontiers/commons, linked), the compiler, fast-check, zod, and the engines the tests run on (DuckDB, PGlite; SQLite is the runtime's node:sqlite).

A first example

A domain of one concept, made into a logical schema and bound to the SQLite dialect. Every name below is an export of the package's exports map.

import { attribute, concept, domain, identifier, text } from "@intellectual-frontiers/data/governance";
import { projectDomain } from "@intellectual-frontiers/data/sql/logical";
import { bind, render } from "@intellectual-frontiers/data/sql/physical";
import { dialect } from "@intellectual-frontiers/data/sql/dialects/sqlite";

const book = concept("book", { definition: "A written work", identifiedBy: ["id"], attributes: {
  id: attribute(identifier(), { definition: "What identifies it" }),
  title: attribute(text(), { definition: "What it is called" }) } });
const d = domain("library", { definition: "Books", concepts: [book] });
if (d.kind === "err") throw new Error("domain");
const p = projectDomain(d.value);
if (p.kind === "err") throw new Error("projection");
const sql = bind(p.value.schema, { dialect });
if (sql.kind === "ok") console.log(render(sql.value));

This prints (checked against the real code):

CREATE TABLE IF NOT EXISTS "book" (
    "id" TEXT NOT NULL PRIMARY KEY,
    "title" TEXT NOT NULL
);

Swap the import for .../sql/dialects/postgres or .../sql/dialects/duckdb and the same domain makes the SQL of that engine.

The layers

IFC data is three layers and an engine that extends them (0001-layers). Governance knows no database. The logical schema knows the kind of database (relational), not an engine. The physical schema is the only layer that knows an engine. The lifecycle sits between the physical schema and the extensions that use it. The table of what each may import is data in tools/layers.ts (MAY_IMPORT), and bun run verify runs it.

Engine

The engine (0002) is the small part every layer and extension stands on, in the manner of an editor's extension host: a layer declares a contribution point, an extension declares in a typed manifest what it adds and what it needs, a project passes an explicit list to compose, and each extension starts only when wanted. It has no registry that code can reach without being handed it, and nothing registers by being imported. It does not sandbox code that runs in the same process (0002 FR-009).

Exports of ./engine: point, contribute, defineExtension, lazyExtension, extensionId, compose, provide, handle and CONTRACT. compose returns every mistake together as a ComposeError (duplicate, missing, cycle, contract, unprovided), and a lazy extension is activated once when fire is given one of its events.

import { contribute, defineExtension, extensionId, point } from "@intellectual-frontiers/data/engine";
const terms = point<{ readonly term: string }>("governance.vocabulary");
const id = extensionId("privacy");
export const privacy = id.kind === "ok"
  ? defineExtension({ id: id.value, version: "1.0.0", contributes: [contribute(terms, { term: "email" })] })
  : undefined;

The points the layers declare, as found in the code: logical.projection (projectionPoint), physical.caseStyle (caseStylePoint), physical.generators (generatorsPoint), statementsPoint and tableClausesPoint for statements and table clauses, lifecycle.transform (transformPoint) and lifecycle.fallback (fallbackPoint), plus vocabularyPoint and dialectPoint.

Governance

Governance (0003) is a business domain and what must be true of its data, in terms that name no database. A domain is made of concepts (with attributes, the attributes that identify them, and relationships), codeLists, and annotations on any of them. Every element has an identity that follows its names (conceptId, attributeId, relationshipId, codeListId, codeId, domainId), so the trace graph (traceGraph, elementsOf) can be drawn from a concept to a column to a table. A domain is TypeScript, not a syntax of its own.

Business datatypes: identifier, text, integer, decimal, boolean, date, instant, binary, structured, vector, and codeOf(list) for a code list.

Vocabularies

An annotation is a typed value of a kind that a vocabulary defines (annotationKind, annotate). defaultVocabularies holds eight, in the order lint runs them; a vocabulary is also what an extension can add (vocabularyExtension, vocabulariesFrom).

lint(domain, vocabularies) returns, as data, where the domain falls short of its own vocabularies: the core rules first (coreRules: an element with no definition, an annotation of a kind that no vocabulary given has), then each vocabulary's rules.

Names are TypeScript identifiers in lower camel case and nothing about a database (0005): words splits one into a list of words, which is how a name crosses the layers.

Arca

./models/arca (0004) is the first of Arca's typical data models, the party model, as governance. It exports partyDomain (a Result) and, among others, the concepts party, person, organization, partyRole, partyRelation, partyIdentifier, electronicContact and postalAddress, and the code lists partyKind, partyRoleKind, partyRelationKind, partyIdentifierKind, contactMedium and addressPurpose. Other models, such as products and orders, are later; Data Vault is not part of this library (0004).

Logical schema

The logical schema (0006) is a relational schema made from governance by a projection, in terms of tables, columns, keys, constraints and indexes, and of no engine. projectDomain(domain, projection = normalized) returns a Result of { schema, flow }, or every error together. A Projection is a value, so another can take the place of the default (normalized, from normalizedProjection(options)); one is contributed at projectionPoint.

  • One table for each concept and for each open code list; the columns, keys, constraints and indexes follow from the attributes, relationships and vocabularies (for example quality.unique, usage.lookup).
  • Every element carries the identity of the governance element it was made from (LogicalId, tableId, columnId, constraintId), so a column links back to its attribute.
  • Names are lists of words (Words), which the physical layer writes in a case style.
  • Nothing governance says is silently dropped (0001 FR-007): each annotation is expressed, carried (it stays on the table or column, read with carriedOf) or unexpressed, and the report of the flow (FlowEntry, Disposition) says which.
  • Row types are derived at the type level: RowOf, InsertOf, KeyOf, ValueOf and related types (sql/logical/rows.ts).

Physical schema

The physical schema (0007) is a logical schema bound to one engine. bind(schema, { dialect, naming?, sources?, schema?, tableClauses? }) returns a Result of Physical (the dialect, the naming and the ordered statements), or every PhysicalError together. render writes the statements as a script. A table follows the tables its foreign keys refer to, indexes follow tables and data follows both, every statement carries the logical elements it was made from, and what a dialect cannot express is an error value that names the element, never SQL that fails when loaded. The same input gives the same text.

Naming and case styles

The logical schema chooses the words, the physical schema writes them. snake is the default, with camel and pascal beside it; a case style is an extension (caseStylePoint), and naming(names, codes) chooses one for names and one for codes. The same domain therefore gives given_name in one database and GIVEN_NAME in another where an extension supplies that style. A name that is too long for the dialect, or two names that become alike, is an error value.

Schema-qualified names

Give schema to bind once (0013) and every table is made, referred to, indexed, loaded, described and changed there. Where the engine has schemas (PostgreSQL, DuckDB) the names are qualified ("data"."book", written by qualified(dialect, schema, name)) and the schema is made first; where it has none (SQLite) the schema's words are written before each table's own by the case style (data_book, dataBook). Nothing changes for a project that gives no schema.

References for text written by people

refsOf(schema, dialect, naming, inSchema?) (0007) gives the written, quoted, qualified name of a table or column from the words of its name, in any case style, and keeps what is not there as an error value. Transforms use it; so can any SQL a person writes.

Modules

Arca is one domain. A general-purpose business model is many subject areas, and a project wants some of them. A module (governance/module.ts, 0028) is one subject area as a value: defineModule({ name, requires, concepts, codeLists }), or moduleOf(domain) for a domain that is already valid (Arca). Its concepts may refer to the concepts of the modules it requires, so a module is not validated alone; composeModules(name, spec, modules) makes one domain of the modules a project lists, validated whole, and projecting that makes tables only for the listed modules, so there is nothing to prune and no dangling foreign key.

  • Nothing is added for the project. A required module that is not listed, a cycle, two modules with one name and a concept that two modules both define are error values. withRequired(all, ["invoicing"]) gives the closure in order, as a plain list a project can read.
  • References run down the requirement only. A concept may refer only to concepts and code lists of its own module or of one it requires, directly or through what those require; a reference sideways, even to a listed peer, is an undeclared-dependency error. An optional link between two peers is therefore a module of its own that requires both (a bridge), not an optional column in either.
  • Layers. A model may import the models it requires, through its entry of exports; the check reports a cycle among models (layers/cycle). The composed domain carries the project's name, so a project keeps one name for it.
const billing = defineModule({ name: "billing", requires: ["arcaParty"], concepts: [billingAccount], codeLists: [accountStatus] });
const app = composeModules("shop", { definition: "A shop" }, [moduleOf(partyDomain.value), billing]);

Tenancy and identity 0029 to 0040

Modules on top of Arca's party model, for a business that serves businesses (B2B) and the consumers of those businesses (B2B2C), covering people, machines, devices and AI agents with roles, RBAC, ABAC and relationship-based access for each. models/arca-tenancy is the tenant: a boundary with a hierarchy (platform, reseller, business, consumerPool), a unique slug and a constraint that it is not its own parent; a WorkOS organization or an Okta org is a business tenant.

One principal, five kinds (0032). A principal is a user, machine, device, agent or group, as a party is a person or an organization. What every kind has is attached to the principal once: a status (disabling it denies everything at once, the kill switch for any kind), an owner (a person or group accountable, never itself), credentials, roles, attributes, policies and a place in the audit trail. What is specific to a kind is in a concept of its own, in the module of that kind. A project composes only the modules it needs; the rest make no table.

The models are tested by composing them with the party model and tenancy, binding them for each dialect and loading them into SQLite, DuckDB and PostgreSQL (91 tables when everything is composed), where inserts that break a unique, a check, a foreign key or an ownership rule are refused for every kind of principal. A model-level test holds every module to the rules: every concept classified and citing a requirement, nothing named like a secret, a prompt or raw arguments in the clear, every secret-holding concept restricted. Federation, OAuth, privileged access, the decision engine and the operations that do the business of these modules are still to come.

Deciding, and the operations of agents 0041, 0042

decide(tx, { principal, action, tenant, resource?, context?, delegation?, now }) (in sql/extensions/operations/identity) is one decision for a person, a machine, a device, an AI agent or a group, made in the same transaction as the effect it guards. Permits come from roles (direct, through groups to depth five, through role inheritance), from relationship tuples joined to permissions, and from attribute policies; any refusal wins; and unknown never allows: a missing or stale attribute makes a policy that reads it unknown, an unknown allow allows nothing, and an unknown refusal refuses. A privileged role is never an agent's, and a permission that names a feature needs the tenant's entitlement. Every decision returns its reasons, the obligations (step-up, approval) and what decided. Policies are written in a small closed expression tree with no code in it (and, or, not, comparisons, in, contains, startsWith, exists) that answers true, false or unknown.

  • A delegation never adds. Under a delegation a principal can do only what every delegation of the chain passes on (in force, in the tenant, to the holder, for that resource, with its condition true) and what the person at the root can do themselves at that moment, asked again at every decision. delegate can only attenuate: a sub-delegation is for a subset, no later, no wider in resource, fewer times redelegable; revokeDelegation ends the delegation and everything below it at once.
  • A tool call is decided, budgeted and approved in one transaction (recordToolCall): the tool must be granted, the agent's version approved or active (revoking a version pulls it from every run), the decision engine must allow it under the run's delegation, a risky call waits for a person, and the run's budget is taken from by one conditional update so it is never exceeded and what is refused is not counted. Every call is a row with only a hash of its arguments.
  • Approvals are for a person, for one call, once. decideApproval refuses an agent (an agent never decides), anyone who does not answer for the agent (its owner, the person at the root of its delegation, or a holder of a named role) and anyone who cannot do the thing themselves, so approval never launders authority. An approval is bound to the hash of the arguments and the action and is consumed by one conditional update.
  • The kill switch (killAgent) disables the agent, stops its runs, ends its delegations and everything below them, revokes its credentials and cancels what waits for approval, in one transaction.
  • The audit trail is a chain. identityAuditSink writes each event in the transaction of what it records with the hash of the one before it (and who, on whose behalf, through which delegation and run, and what decided); verifyAuditChain reports a fork or a break, so a change to an event shows.

These run on SQLite and PostgreSQL (DuckDB cannot update a row another row refers to). The tests drive them through the operations runtime: delegation chains, attenuation, derived revocation, approvals, budgets, the kill switch and a tampered chain. Two calls at the same instant cannot be shown by these in-process engines; the single conditional update of each operation is what decides.

What the database enforces, and on which engine 0043

A guarantee enforced only by the application that is meant to keep it can be stepped around by any other client: a second service, a statement typed by hand, a table's owner. Where the database can refuse what is wrong, the library makes it refuse, for every client. Where the engine cannot, the library says so and the application's runtime enforces it. Engines differ, and the library judges each by what it can do:

MechanismPostgreSQLSQLiteDuckDB
Checks, foreign keys, uniqueness, transactional DDLyesyesyes
Triggers (append-only, chains, status moves, caps)yesyesno
Stored routinesyesnono
Row-level securityyesnono
Roles and grants (least privilege)yesnono
Event triggers (refuse weakening security)yesnono
Advisory locks (one runner)yesone writer at a timeone writer at a time
Tierfullstandardbasic
  • PostgreSQL can enforce all of it in the database, so any guarantee it does not enforce there is a defect of the library, and weaknesses in the PostgreSQL embodiment are the highest priority.
  • SQLite can enforce checks, keys and triggers, and has no roles or row security: row isolation and least privilege are the application's, and that is not a defect.
  • DuckDB can enforce checks and keys only: invariants are carried as data and enforced by the operations runtime, and DuckDB cannot update a row another row refers to. Neither is a defect of the engine or of the library, and the library says so.

The guard. On PostgreSQL the invariants come with event triggers that refuse to drop, disable, rename or replace an invariant's trigger or function (or its table) for any session that does not hold an unlock secret; the database holds only the secret's hash (guardKeyOf), a migration unlocks its own transaction (unlockStatement), and with no secret given only a superuser can open it. The owner of a table, the usual attacker, cannot weaken what the database enforces.

A sealed scope. A row-security policy that reads a plain setting trusts any session that sets it, so a statement injected into the application could read another tenant. With accessSource({ seal: { key } }) (PostgreSQL) the policy trusts a scope only with the mark that only the issuer holding the key can make (sealedScope, scopeStatement); the key is in a table no application role can read, row security is forced on the table's owner, and an event-trigger guard refuses to disable it or drop its policies or tables without the unlock secret. The protected-access layer's migration flag can be sealed the same way (migratingSecret).

The quality vocabulary says what must always be true of the records of a concept: appendOnly (never changed or removed; optionally a hash chain, where each record is the next in number and names the hash of the one before it, so that none is left out, put between or forked), transitions (a status moves only along the moves it may make; a code with no moves is terminal) and atMost (a number is never above another of the same record). invariants() writes them as triggers for PostgreSQL and SQLite; on a dialect without triggers it is an error value unless the project says to carry them. enforcementOf(dialect) gives a dialect's tier and what it can and cannot do, where(dialect, need) says whether the database or the application enforces a guarantee, and placed(tables, dialect) says it for each invariant of a schema. The identity model declares its invariants this way: the audit trail is append-only and a chain, a budget never exceeds its limit, an approval, a delegation, a run, an agent version and a principal move only along their moves. The tests attack the database with raw statements that never pass through the application, on SQLite and PostgreSQL.

arcactl 0046

arcactl is the command that helps initialise, manage and maintain the arca models in PostgreSQL. It is for the arca family (the party, tenancy and identity models; the issues model is available too) and lives in sql/cli/. The first command is doctor; init and shell follow.

arcactl doctor --models identityAgent            # or write arca.config.ts: export default defineArca({ models: ["identityAgent"] })
arcactl doctor --json --check ARCA-D005,ARCA-D006
  • Read-only. It writes nothing. Each check is pass, warn, fail or could not check (a check that lacks a privilege never passes by default), with what it found and what to do. Exit code 0 where all pass, 1 where any does not, 2 for a wrong command or a database it cannot reach.
  • Nine checks: the connection and server; whether it is initialised; drift from the models (the plan that would bring it to them, and what is held outside); the ledger's chain; the invariants' triggers present and enabled; the guard against weakening them; row security and the seal (key and mark function closed to application roles); the audit chain, recomputed; and what PostgreSQL enforces and what the application does.
  • Connection. Bun's own client (Bun.SQL) on Bun, with no dependency; pg, an optional peer dependency, on Node. With no URL it reads libpq's environment (PGHOST, PGUSER, .pgpass, pg_service.conf) as psql does; a password is never an option, and is taken out of anything printed, including a driver's error that quotes the URL.
  • Tested on PGlite, the in-process PostgreSQL: a database as it should be, and one with each fault planted (a trigger dropped or disabled, the guard stepped aside, a table missing, a stray column, a ledger entry changed, an audit event forged, a seal left open). Not shown: a server over the network.

Issues as code 0044 0045

A weakness written in a document can be forgotten, reworded away or called fixed with nothing to show. Here an issue is a value of a type, in the code of the library or the module it is about, and the database can hold a copy.

  • A governed Issue (governance/issue.ts): its status is a sum, so a fixed issue carries a non-empty proof, a duplicate the number it duplicates and a wont-fix, not-a-defect or deferred issue its reason; one without what it needs does not compile. It says its severity, priority (P1 to P3), goals (G1 to G8), size, the engines it is about (an engine that cannot do what is missing is not charged with it) and the day it was raised.
  • One file for each issue. A library or module keeps issues/mod.ts and issues/00001-<slug>.ts, 00002-..., in number order with none missed; mod.ts lists them and exports the set under the folder's scope. The library's own are in issues/; the modules' in sql/extensions/<name>/issues/.
  • An issue is never lost. checkIssueSet checks numbers, slugs, dates, that a critical issue is P1 and a low one never, a proof that is not only a review, duplicates, links and citations; checkIssueMoves checks a set against the version before it (nothing taken out, a number never renamed, a finished issue only reopened). liveIssues lists what is still to be done, most pressing first.
  • The gate is in bun run verify. Every issues/ folder is held: files named and listed, each issue the one its file is named for, and the proof of a fixed issue resolves (the file exists, the test's title is in its file, the specification exists, the commit exists).
  • A copy in the database (models/issues and sql/extensions/issues): a model that requires nothing (issue, goals, engines, evidence, links, a ledger of syncs) and syncIssues(driver, schema, dialect, sets), which adds what is new, rewrites what changed (by a hash of what the code says), marks what the code no longer has as withdrawn (never deleted), brings it back when it returns, and writes a ledger row, all in one transaction; where the records already match it writes nothing. Git is the source of truth and the database is never ahead of it. It runs on SQLite and PostgreSQL (DuckDB cannot update a row another row refers to).

Operations 0031

A model is tables; a business is what is done to them. SQL has no portable control flow (a refresh token that is found to have been used already must revoke its whole family and still commit and tell the caller; an exception would roll the revocation back), so the business operations of a model are done in the application's language, in one transaction, in three parts.

  • A contract, in governance (operation(name, spec)): what it is for, its typed inputs, the concepts it reads and writes, the permission it requires (or that it is public, or what its implementation checks: it says exactly one) and the input that holds the tenant, what it emits to the audit trail, whether it runs as its caller or as the service. It holds no SQL and names no database. lintOperations(domain, operations) holds contracts to their domain: an unknown concept, a query that writes, a malformed permission or action, a restricted concept written as the caller, a command that writes and records nothing.
  • A runtime (sql/extensions/operations): operations(schema, dialect, driver, contracts, implementations, options) runs an implementation in one transaction. Input is checked first; the caller is authorized by the project's authorizer, and a refusal is itself recorded in the audit trail and kept; what the operation wrote must be what its contract says; a command that wrote must have recorded one of the actions it emits, in the same transaction. A business outcome is a value ({ status: "reuse-detected" }), never an exception: only what is thrown rolls back, so an outcome that must be kept is kept, and commit: false says not to.
  • Implementations, written once against typed row operations (tx.insert, update and remove with the number of rows changed, select, count, a raw read written from the names, audit) by the words of table and column names (a column that holds a relationship by the key of the relationship), so they do not change with the dialect, case style or schema. Values enter only as literals the dialect writes, and a query cannot write.

The context an operation is given (clock, identifiers, tokens, token and identifier hashes, the check of a password) has defaults that need no secret and is replaceable, so a test is the same every time; the password algorithm is the application's. DuckDB cannot update a row that another row refers to (its foreign key limitation), so operations that do are for PostgreSQL and SQLite. Not shown by the tests: two connections acting at once, which these in-process engines cannot do.

Generating files

generate(schema, { generators, naming?, dialect? }) runs Generators and returns Artifacts ({ path, text }); a generator reads only what it is given and gives the same text for the same input. Writing the files to disk is not a generator's job.

Dialects

A dialect says how an engine writes what a logical schema says: its types, quoting, literals, the longest name, and the features it has. Each of ./sql/dialects/postgres, /sqlite and /duckdb exports dialect and extension (dialectExtension(dialect)), so that a fourth is added without changing the physical layer. The features below are the ones each dialect value declares.

Beyond features, a dialect may carry hooks the extensions use: catalog (reading its own catalog), advisory (one instance applying at a time), locks, rebuild, and attach (attaching a database file for reading, on SQLite and DuckDB, used by integrations).

Extensions check the features: partitions on a dialect without partitions is an error value; access on a dialect without row security is carried as data by the governance tables, or an error where unsupported: "error" says so. The dialect also carries the catalog queries that the lifecycle needs (probes for idempotency, a reader for convergence, an advisory lock where there is one).

Lifecycle

A database outlives the schema it was made from, so what changes it from one physical schema to the next is a layer of its own (0011). It names no tool or workflow; it makes what every workflow needs.

State and hash

The state of a database (State, made by snapshotOf(schema, { dialect, naming?, schema?, tableClauses? })) is the written structure of its tables as a plain value. stateHash is the SHA-256 of its canonical JSON (canonical, hashOf, sha256Hex), so a state is addressed by its content and never by a number; two states of the same structure are one state whatever order their tables were made in, and another dialect or naming is another state. emptyState(dialect, naming, qualifier?) is the state of an empty database. What governance said of the past (lifecycle.renamedFrom) is a hint beside the structure, not part of it.

Diff and plan

diff(from, to) finds what differs by the identity of each element, not by its name, so a change of case style is a rename; applyChange and applyChanges compute the state a change leads to. The kinds of change (ChangeKind) are: renameTable, renameColumn, dropConstraint, renameConstraint, addColumn, dropColumn, alterType, alterNullable, alterDefault, alterPrimaryKey, alterClause, createTable, addConstraint, upsertRows, removeRows and dropTable.

plan(from, schema, desired, options) returns a Result of a Plan (from and to hashes and ordered steps), or every PlanError together (write, dialect, schema, refused, manual, unresolved, not-idempotent, inconsistent). Each step carries statements to do it (up) and to undo it (down), the hash of the state it needs (from) and leaves (to), the logical elements it is made from (of), and an identifier made of its content, so a step names the one database it is for.

Step classes and reversibility

What the dialect cannot change in place (for example a primary key, or the type of a column) is refused as an error value that says a person writes the step, unless a fallback (the rewrite extension) makes it.

Repeatables

What extensions add to a schema (comments, views, policies, routines) is Repeatable: a key, the hash of its text, its statements and the elements it is made from. A repeatable is applied again whenever its text changes, or when a step changes one of its elements (dueRepeatables). A statement group setup (a schema, for example) is run before the steps; the other repeatables run after them.

Ledger

The ledger (lifecycle_ledger by default) records what was applied, in order. Each LedgerEntry (seq, kind step or repeatable, key, from, to, hash, chain, appliedAt, appliedBy) holds the chain hash of the entry before it (chainOf, nextEntry, starting at GENESIS). An entry that is changed, removed, added or moved breaks the chain from there on, and verifyChain finds the first break.

Execute and resume

import { emptyState, execute, stateHash } from "@intellectual-frontiers/data/sql/lifecycle";
// driver: { exec(sql): Promise<void>; query(sql): Promise<Record<string, unknown>[]> }
const r = await execute(pl.value, driver, dialect, { empty: stateHash(emptyState(dialect.name, { names: "snake", codes: "snake" })) });

execute(plan, driver, dialect, options) runs on a Driver (exec and query). Each step runs in a transaction together with its ledger entry; verification checks run inside it, so a step that did not do what it said is rolled back and not recorded. The ledger is verified first and a broken chain is refused (RunError kind ledger). The database is found among the plan's states by the ledger; one that is in none of them is refused (kind base), so a plan only runs on the database it was made for. Resume: steps the ledger already holds are skipped, so a plan that stopped at a failed step runs on from there when run again, and a plan run twice does nothing the second time. RunOptions also takes before (statements at the start of each transaction), retry, by, now and ledgerTable.

Extensions

An extension is a feature of the physical schema or of the lifecycle, never part of a core. Each is switched on by composing it, or by passing its source, transform or fallback directly; each is checked against the dialect's features. Every example below uses exports that exist in the source.

Documentation 0008

Governance is the documentation of everything below it, so it must reach the database. Three sources, all on by default: commentsSource (COMMENT ON where the engine has it), documentationTableSource (a table of descriptions where there is no COMMENT, by default for SQLite) and governanceTablesSource (every annotation as a row of JSON, and a trace from each table and column to its governance element). defaultDocumentation(settings) gives the three as extensions.

import { documentationSources } from "@intellectual-frontiers/data/sql/extensions/documentation";
bind(schema, { dialect, sources: documentationSources() });

Views 0009

A view is derived, so not governance; it is made from a typed definition by governance names. viewsSource(definitions), or viewsExtension (sql.features.views). A definition has name, description, from, joins, columns and where conditions.

bind(schema, { dialect, sources: [viewsSource([{ name: "personDirectory", description: "The people in use", from: "party", columns: [{ table: "party", column: "partyId" }] }])] });

Access 0009

What governance says of who may see what becomes what the engine enforces. A column with security.scope makes its table's rows visible only where the column equals the setting of the scope; a concept with security.access grants its read roles SELECT and its write roles INSERT, UPDATE and DELETE. The policy reads current_setting('<prefix>.<scope>', true), PostgreSQL's way. Roles are named, never created.

const p = bind(schema, { dialect: postgres, sources: [accessSource()] });
const loud = accessSource({ unsupported: "error" }); // an error value where the dialect lacks row security

Settings: unsupported (carry by default, or error), settingPrefix (app), viewsSchema.

Routines 0009

Functions and procedures written with typed references to tables, columns and parameters (table, column, columnName, param). The SQL between the references is the author's and is not read; the engine refuses it. Only PostgreSQL has the routines feature.

routinesSource([{ kind: "function", name: "authorCount", description: "How many authors there are",
  returns: { type: { kind: "integer" } }, language: "sql", volatility: "stable",
  body: ["SELECT count(*)::int FROM ", table("author")] }]);

Partitions 0009

partitions(divisions) returns { clause, source } (a table clause and a statement source); partitionsExtension contributes both. Strategies: range, list, hash. PostgreSQL only.

const { clause, source } = partitions([{ table: "event", key: ["happenedOn"], strategy: "range",
  partitions: [{ name: "y2025", from: ["2025-01-01"], to: ["2026-01-01"] }] }]);
bind(schema, { dialect: postgres, sources: [source], tableClauses: [clause] });

Vectors are a business datatype (vector) whose storage each dialect says (0009).

Generators 0010

Files made from the logical schema, never written beside it: an entity-relationship diagram in Mermaid (mermaid) and D2 (d2), the data dictionary in Markdown (dictionary) and HTML (dictionaryHtml), row types in Rust (rust) and Zod (zod), and a register of personal data and security (register). generators is all seven; generatorExtensions() is each as an extension sql.generate.<name>.

const files = generate(schema, { generators });
// library.erd.mmd, library.erd.d2, library.dictionary.md, library.dictionary.html, library.rs, library.zod.ts, library.register.md

Idempotency 0012

On by default: every generated step is safe to repeat, in one of three ways that the step names (Step.idempotency). natural: the engine has a form (IF NOT EXISTS, IF EXISTS, an upsert). guarded: the statement carries a Guard, a catalog query that says its work is done, which the runner honours (guardInline can write it as a block where the engine has one). ledger-only: neither is possible, and only the ledger keeps it from running twice; unguardable: "refuse" (requireIdempotent) turns that into an error value.

plan(from, schema, { dialect }, { transforms: [idempotency()] });

Protected access 0014

Nothing reaches a table except through a layer that can change without changing the table, and nothing changes a table except the lifecycle. protection(settings) gives what a project passes on: tables in a schema (data by default), a view of each in another (api), roles granted on the views only, and, where the engine can enforce it (PostgreSQL), row policies and a guard that refuses to alter or drop a table outside a migration (lifecycle.migrating by default). Where it cannot (SQLite, DuckDB) the schemas and views are a convention, and capabilities(dialect) says so; a project that asks for enforcement: "enforced" there is told it cannot have it. Views also keep a renamed column under its old name for as long as governance says, and carry security.mask.

const p = protection({ tablesSchema: "data", viewsSchema: "api" });
bind(schema, { dialect, ...p.bind });
plan(from, schema, { dialect, ...p.desired }, { transforms: p.transforms });
execute(plan, driver, dialect, { empty, before: p.session(dialect) });

Safety and quarantine 0015

Three features, on by default, each a transform of the lifecycle. Quarantine: a dropped column or table is never destroyed by the step that removes it: its values are copied to a quarantine table (quarantine and quarantined suffixes), or the table is renamed away, so the step can be undone; purge is the step a person asks for to destroy one. Lock discipline (lockTimeouts, lockRetry, validateLater): locks are asked for with a timeout (5000 ms by default) and tried again (3 attempts), and a constraint is added without checking rows and then validated, so the strongest lock is short. Verification (verification): every step says what must be true after it, such as the number of rows, and the run checks it in the step's transaction.

const s = safety();
plan(from, schema, { dialect }, { transforms: s.transforms });
execute(plan, driver, dialect, { empty, retry: s.retry(dialect) });

Plan report 0016

What a plan does in the words of governance, for the person who approves it. reportArtifacts({ plan, before?, after, dialect }) returns Markdown (<domain>.plan.md) and JSON (<domain>.plan.json), the same content and the same every time. It says each step's class, reversibility, idempotency and lock; what governance says of every element a step is made from; what governance itself changes; who must approve and why (privacy for personal data, security for a restricted element, owner for a destructive or hand-written step, by default; the steward is routed to); and what is new. recordStatements records it in a table (governance_migration by default).

const files = reportArtifacts({ plan: pl.value, after: schema, dialect });

Rewrite 0017

SQLite and DuckDB cannot change a column's nullability or default, a primary key or a constraint of a table that exists, and PostgreSQL will not change a type without a cast. rewrite is the fallback of plan that makes the table again from the state after the change (new table, rows copied, old dropped, new renamed, indexes made) in the step's own transaction. A change of type is cast in place where the engine can and by making the table again where it cannot, when casts: "allow" (the default is refuse, which leaves it to a person). It never remakes a table in PostgreSQL where PostgreSQL can alter in place.

plan(from, schema, { dialect }, { fallback: rewrite({ casts: "allow" }) });

History and convergence 0018, 0019

The two strategies, in their own section.

Rollout, parallel versions 0020

Two versions of an application meet one database for a while. The tables hold what every live version needs; each live version has a schema of views (api_v2, api_v3 by default, from the pattern api_{label}) with its own table and column names, so a renamed column is read under its old name by the older version and the new one by the newer, with nothing copied. expandSchema(latest, olderVersions) is what the tables hold during the overlap: nothing that destroys, columns an older version uses kept, and what only the latest needs made optional. versionViews(versions) makes the schemas of views; retireStatements ends a version. The expand and the contract are the ordinary plans, so every strategy and feature applies.

const during = expandSchema(v3, [v2]);
plan(from, during, { dialect, sources: [versionViews([{ label: "v2", schema: v2 }, { label: "v3", schema: v3 }])] });

Integrations 0022

Rows come into a model's tables from outside: reference data written in code, CSV text, a table of another database file, or an adapter (an API, a queue). An integration names its table and columns by the words of their names (so it is the same for every dialect and schema qualifier), its source, its strategy (append, upsert by default, replace or snapshot) and its key (the primary key by default). loader(schema, spec, { dialect }) resolves it; load(driver, loader) lands the rows in a typed temporary table, then, in one transaction, checks, counts, loads and records them.

  • Checked before it touches a table. Duplicate keys in the landing, a null in a column the target requires, an empty snapshot, and a snapshot that would delete more than half of the target (a setting) are refused as error values, and the target is as it was. A failure rolls back, and the landing is dropped either way.
  • Recorded. Each load is a row of a ledger table (integration_run) with its counts and the hash of what it landed; an append of rows that have not changed since the last load does nothing, which is what stops a re-run from doubling rows. When it skips is a setting (append, all or none).
  • Sources. CSV text is parsed by the library (quoted fields, a delimiter setting, an empty field is null) and cast to the target's types, so it works on every engine. A table of another database file is attached for the load and detached after it, on SQLite and DuckDB (a dialect says it can); PostgreSQL gives an error value. An adapter that fails, or gives a column the contract lacks, is an error value.
  • Lineage. lineageOf(loader) gives the edges from source to landing to target, and upstream(edges, node) what reaches a node.
const l = loader(schema, { name: "authors", table: "author",
  source: { kind: "csv", text: "id,name\na1,Ann" }, strategy: "upsert" }, { dialect });
if (l.kind === "ok") await load(driver, l.value); // { outcome: "loaded", landed: 1, inserted: 1, ... }

Transforms 0023

A model is a query whose result is kept as a view (the default), a table, an incremental table or nothing at all (ephemeral, written into the SQL of the models that read it). The SQL is written by a person but its names are not: the model's function is given Refs (from sql/physical), and r.table("author") and r.column("author", "name") give the written, quoted, qualified names for the dialect, so an unknown name is an error value when the project is made and the same model runs on every dialect. transformer(schema, models, { dialect }) puts the models in the order of what they read (a cycle is an error value) and gives their lineage; build(driver, project) builds them.

  • Published only if it passes. Each model is built in one transaction together with its tests (unique, not-null, accepted-values, relationship, custom). If a test of severity error finds a row, the transaction is rolled back, so the table or view that was published before is still there; the models that read it are reported as blocked and not built. A warn is reported and does not stop the build. A finding gives the count and a sample of the wrong rows.
  • Tables are made again under their views with CASCADE where the dialect has it, and a build of some models also builds everything that reads them. An incremental model adds the rows whose key it does not hold and never changes a row it holds.
  • Recorded. Each built model is a row of a ledger table (transform_run) with the hash of its definition and its row count. Models are best written in a schema of their own (a setting) so that convergence does not read them as drift.
const p = transformer(schema, [{ name: "author names", materialization: "table",
  select: (r) => `SELECT ${r.column("author", "id")} AS id, ${r.column("author", "name")} AS name FROM ${r.table("author")}`,
  tests: [{ kind: "unique", columns: ["id"] }] }], { dialect });
if (p.kind === "ok") await build(driver, p.value); // { ok: true, models: [{ outcome: "built", rows: 3, ... }] }

Queries 0024

An application's reads are a catalog of named queries. Each is SQL a person writes, but its names are the schema's (given by Refs, so an unknown table or column is an error value when the catalog is made) and its values come in only as typed parameters (text, integer, number, boolean, each possibly nullable) written as literals by the dialect: a value can never become SQL. queries(schema, specs, { dialect }) makes the catalog.

  • Read-only by construction. A query must be one SELECT or WITH; with strings, quoted names and comments left out, a ; or a word such as INSERT, DELETE, DROP or COPY is refused. run(driver, query, values) runs it in a transaction that is rolled back.
  • Verified against a database. verify(driver, catalog) prepares every query with sample values (SELECT * FROM (query) LIMIT 0) and reports the ones the engine refuses with its message.
  • Compared between versions. impact(specs, from, to, options) says, for each query, fine, breaks (fine before, broken after, with the errors), broken or fixed: the queries a schema change breaks are known before it is applied, which is what parallel versions (rollout) needs.
const c = queries(schema, [{ name: "by name", params: { name: "text" },
  sql: (r, p) => `SELECT ${r.column("author", "id")} FROM ${r.table("author")} WHERE ${r.column("author", "name")} = ${p("name")}` }], { dialect });
if (c.kind === "ok") await run(driver, c.value.get("by name")!, { name: "Ann" });

Ephemeral targets 0025

Some databases are not the system of record: a catalog an agent reads, reference data shipped with an application, a test fixture. For these the source (governance, plus rows written as typed values) is the record and the database is a build product. targetBuild(schema, { dialect, rows, module }) makes one SQL file: a header (that it is generated, from which module, the dialect, the hash of the schema's state and the hash of the rows), the structure bind makes, then the rows as INSERT statements, tables after the tables their foreign keys refer to, rows in the order of their primary key, a hundred to a statement (a setting). The same source gives the same bytes on every runtime and run, whatever order the rows were given in, with nothing from the clock; the file is committed and a change to a row is a line in a pull request.

  • Checked when it is made. An unknown table or column, a required column a row leaves out, a primary key twice, a column twice and a cycle among tables are error values.
  • Made in one transaction. materialize(driver, build) runs the statements in a transaction that is rolled back if one fails.
  • Kept current. staleness(committedText, build) says whether a committed file is what the source makes and, if not, the first line that differs; sizeFindings(build, limit) reports a table that has grown past a limit.
const b = targetBuild(schema, { dialect, module: "catalog.ts", rows: { author: [{ id: "a1", name: "Ann" }] } });
if (b.kind === "ok") { writeFileSync("catalog.auto.sql", b.value.text); await materialize(driver, b.value); }

Kinds 0026

Reference data (the kinds of things, statuses, ranks) is kept by people in a spreadsheet. kindsFromCsv(text, { name, types }) reads it into typed rows in the order of the file (each column text, integer, number or boolean; an empty field is null), with a bad header, a ragged row, a value of the wrong type and a repeated key as error values carrying their line. checkKinds(kinds, schema, table) compares the rows with a table by the words of the names. kindsModule(kinds) writes a TypeScript module (an interface and a readonly array, the same text every time, marked not to be edited) that imports as the rows that were read, and rowsOf(kinds) gives the rows to integrations and ephemeral targets: one file is the module in code, the rows in a build and the load into a database. The CSV reader (parseCsv) is shared and lives in sql/physical.

osquery ATC 0027

osquery can expose a local SQLite database as tables of its own through Automatic Table Construction. atc(schema, entries, { dialect }) makes the auto_table_construction configuration, and its JSON (the same bytes every time, entries in the order of their names), from a logical schema: an entry has an osquery table name, a table and columns by the words of their names, the path of the database and optionally a platform, and its query is SELECT of those columns written by the SQLite dialect. What osquery refuses is refused first, as error values: a column called path in any case (osquery adds its own), no columns, a name that is not lower-case letters, digits and underscores, a platform other than darwin, linux, posix, windows, any or all, and a path that does not fit its platform. The database behind it is an ephemeral target (0025) built from the same source, and the tests run every entry's query against it; the configuration was checked against osquery's documented rules and was not run in osquery itself.

Strategies

A strategy is how a plan reaches a database. There are two, and a preset names the features each needs.

History 0018

A plan is computed once and frozen into files that never change: one file for each step (statements to do it and undo it, what must be true after it) and a manifest that chains them by hash. Every environment replays the same files in the same order and ends in the same state, provable by the hash. A change to a frozen file is found, never silently applied. Exports: freeze, replay, historyPlan, checkHistory, renderManifest, renderStep, parseStep, releasePackage, installer. freeze returns migrations/NNNN_<slug>.sql, manifest.json and repeatable.json files.

deliveryHow the files reach the database
pipeline (default)the files and a replay, through the pipeline of the team that owns the application
release-packageone package for a DBA to run with a SQL client: an installer, a preflight, a verification, a back-out and a runbook (releasePackage)
in-databasea procedure inside the database that applies its own history, keeps its own ledger and refuses what does not follow (installer; schema lifecycle by default)

Settings (HistorySettings): delivery, folder (migrations), release, unguardable (refuse or leave-out) and runnerSchema.

const files = freeze(existing, plan, { folder: "migrations", state });
await replay([...existing, ...files.value], driver, dialect, { empty });

Convergence 0019

The state is read from the database's own catalog (readState), so a database made by hand or restored from a backup is met as it is: drift is a plan, not a surprise. How the plan is approved is the setting approval:

  • Reviewed (the default): propose writes a pinned proposal (renderProposal, proposalText) that a person reads; applyProposal(text, approved, driver, dialect, wanted) applies it only if the text hashes to the approved hash and the database is still in the state it was computed from (otherwise unapproved or stale).
  • Autonomous: connect(driver, dialect, schema, desired, settings, options) on first access takes an advisory lock where the dialect has one, computes the plan and applies it only if every step is allowed by the Policy (by default safe, lossless, and only createTable, addColumn, addConstraint, upsertRows). Otherwise nothing is changed and the plan is held (held, with why); a failed step leaves the database at the step before and the next access resumes. An optional rehearse callback can say no. The result is current, applied, held or failed.
  • Version gate: versionGate(driver, dialect, expected) returns the hash or why the application should not start.
  • Defaults are read. A column default changed by hand is drift (compared after casts, parentheses and case are set aside), and the defaults the model made are not, on all three engines.
  • Held, not dropped. With unmanaged: "hold" a table, column, index or constraint that a person made outside the model is left alone and named in the proposal (held); the default is still to drop it with approval, into quarantine.
  • A table made again keeps its triggers or fails. SQLite drops a table's triggers with it, so a step that makes a table again verifies that the number of triggers is the same after as before and rolls back whole if not (0017).

Settings (ConvergenceSettings): approval, policy, ledgerTable and ignore (tables the reader leaves out).

Presets 0021

Convergence is the primary strategy and reviewed-convergence is the default preset (defaultPreset; preset() with no name gives it): it reads each database's own state and computes the plan from there, so it cannot be fooled by a history the database has left. History (team-managed, dba-managed) is for teams that must hand files to a pipeline or to a database administrator; its weaknesses are tracked, and lower priority.

A preset is named for how a team works. It is a composition of one strategy with the features that approach needs (idempotency, quarantine, lock discipline, generated verification, the plan report), with the settings the approach calls for. It is data: nothing is applied by choosing one. preset(name, changes?) returns a Result of a Preset (strategy, roles, history or convergence, safety, idempotency, report, planOptions, runOptions(dialect)), or a PresetError (unknown, not-used). Every setting is the default of the thing it sets and a project may change it.

PresetStrategyWho does whatSettings it calls for
team-managedhistorythe application's team writes the SQL, a reviewer approves it in the change, the pipeline applies itdelivery: "pipeline"
dba-managedhistorypeople write the SQL, a DBA checks the release package and runs it by hand, possibly twicedelivery: "release-package", unguardable: "refuse" for history and idempotency
reviewed-convergenceconvergencea tool computes the SQL from the database as it is, a person approves the text, it is applied only if the database is unchangedapproval: "reviewed"

const p = must(preset("autonomous-convergence"));
connect(driver, dialect, schema, { dialect }, p.convergence!, { ...p.planOptions, run: p.runOptions(dialect) });

Passing history settings to a convergence preset (or the reverse) is the not-used error. With quarantine on, the convergence reader leaves out the quarantine tables so they are not drift.

How it is verified

From the repository root:

cd commons/data && bun run verify

which runs, in order (package.json): the TypeScript compiler (tsc -p tsconfig.json); the specification checker on spec-kit/ (mizan-check.ts --root spec-kit); the Mizan rules at level L1 on it; tools/check.ts, the trace of sources and tests to the specifications and the layers check, held against trace.baseline.txt, which only shrinks; and bun test suite/. bun run test:node runs the same tests under node --test.

  • Spec kit. Forty-six specifications, 0001-layers to 0046-arcactl, each spec-kit/specs/<number-slug>/spec.md with an input paragraph, numbered requirements (FR-nnn), edge cases, success criteria and an out-of-scope list; registry.tsv lists them, all in force.
  • enforcement.tsv. Says what enforces each requirement (0024-spec-format): a mechanism of check, gate, review or none, and by what. At the time of writing 230 of its rows are a check by cd commons/data && bun run verify, and one (0001 FR-012, the logical and physical naming conventions) is marked none with the note Planned.
  • proves(). A test is suite/<kebab-case>.test.ts on IFC TypeScript, and proves(["0001-layers FR-004"], "what it shows", fn) names the requirements it proves, which the trace joins to the specifications. The sources carry // Spec: headers for the same join.
  • Real engines. suite/engines-fixture.ts opens SQLite (the runtime's node:sqlite), DuckDB (@duckdb/node-api) and PostgreSQL (PGlite, in process), in memory, and the tests load what bind and execute make and read the structure back. There is no stand-in for an engine.
  • Golden and property tests. The DDL of small domains is written out in physical-bind.test.ts; the lifecycle uses fast-check to check that applying the changes of diff(a, b) to a reaches b.

The tests include (suite/): layers, naming, governance, logical and physical, lifecycle, idempotency, safety, plan report, rewrite, history, convergence, rollout, presets, protected access, qualified names, generators and features.

Known limits

Taken from the out-of-scope sections of the specifications and from the source.

  • Layers. Only relational databases; a graph or document store would be a later folder beside sql/ (0001). The sql/cli/ unit is in the table but not yet built; generators return text and writing files is the command line's (0010, 0018).
  • Engine. No sandbox for code in the same process; extensions are listed by the project, not found (0002).
  • Governance. A name is ASCII; an identity follows its names, so renaming keeps the identity only through lifecycle.renamedFrom (0003, 0005, open question OQ-1 of 0003).
  • Features. Routine bodies are text and typed references, not a query algebra; no materialized views, triggers, sequences or domains; roles are named and never created; no vector or mask indexes (a mask is carried as data until then) (0009, 0014).
  • Lifecycle. A primary key, a table clause or a type changed in place is a hand-written step unless the rewrite is used; a constraint or index renamed with its table is dropped and made again; an index cannot be made without blocking writes because the run has no steps outside a transaction (0011, 0015). The ledger's table is in the connection's default schema (0013).
  • Idempotency. A step the engine cannot repeat and that has no probe (a constraint of SQLite) is ledger-only (0012).
  • Quarantine. Purging is a step a person asks for; there is no schedule (0015).
  • Rewrite. A table made again takes its lock for the length of the step; there is no type change that proves it loses nothing yet (0017).
  • Convergence. Defaults, the text of checks and partitions are not compared with the catalog; signing the approval is the project's workflow; each database is met on its own (0019).
  • Parallel versions. A type change, split or merge of columns that needs a trigger is a later specification; choosing when to retire a version and routing a client are the project's (0020).
  • Access. The policy is PostgreSQL's; no other dialect has row-security yet.

Roadmap

As about.ts states it: views that leave out removed rows, a type change that proves it loses nothing, masks and vector indexes as features, and interchange formats for other migration tools (Flyway, Liquibase and Atlas exports).

  • Views that leave out the rows marked as removed (Arca's deleted_at) (0014).
  • Changing a column's type without loss: a second column, a check that every value survives the cast, a swap (0015, 0017).
  • Masks (security.mask) and vector indexes (hnsw, ivfflat) as features (0009).
  • Interchange formats of Flyway, Liquibase and Atlas, as exports of the history files (0018, 0021).
  • Phase 10 is built (0022 to 0027: integrations, transforms, queries, ephemeral targets, kinds, osquery ATC).
