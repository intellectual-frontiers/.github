01The idea in one page

Mizan is Arabic for "balance" and "scale". We use it as the code name of the IF Spec Profile: the discipline that keeps what we say (specifications), what we define (the ontology) and what we run (code) in balance.

1

Spec Kit is the method

We keep GitHub Spec Kit's commands, constitution and spec.md, plan.md, tasks.md. Mizan is a profile on top, not a replacement.

2

Two languages

Natural language for specifications. TypeScript 7+ for ontology, code, tools and tests. Bun by default, Node 26 as backup.

3

One typed ontology

Strongly, algebraically typed TypeScript on commons' RDF kernel. Turtle and the rest are generated, never edited. Four are published: mz, ifccm, ifqs, ifws.

4

Standards first

No invented terms where a consensus standard exists. Law, then US and NIST standards, then ISO, then broadly used vocabularies.

5

An invention is drift

A term no standard backs is unaligned: justified, recorded, counted, and the count only falls.

6

One ladder

Eleven rungs: 0 to 7 required, 8 lifecycle (optional), 9 Evidence (observer), 10 Workspace (environment). A rung relies only on the rungs below it that it names.

7

Everything traces

Code names its requirements, tests name what they prove, terms name their specifications.

8

Integrations module

commons/ts/mizan/integrations/ brings standards in as typed TypeScript and turns our ontologies into well-known forms.

9

AI-first, AI-native

Artifacts an agent can read, write and be checked on. Deterministic checks, not the agent, judge whether work is true to the spec.

How to read this document

Sections 2 to 4 give the rationale. Sections 5 to 9 are the substance: format, ladder, standards, ontology, integrations. Sections 10 to 12 are the three products written in Mizan's form: IFCCM, IFQS and IFWS. Section 13 is how agents work in it, section 14 is the list of controls against drift, and sections 15 and 16 say honestly what is built, what is not yet verified and what was decided. Every item is marked Built, Specified or Planned.

02Why: the drift problem

A company that writes specifications, defines an ontology and builds code keeps its facts in three places. Left alone, the three drift apart, and nobody notices until something breaks, an auditor asks, or an agent builds the wrong thing from the wrong source.

A. Specification and ontology

A requirement uses a word the ontology never defined, or the ontology's definition changed and the specification still uses the old meaning.

B. Ontology and code

Code branches on a list of words written again by hand, and one list changes without the other.

C. Us and the world

A control, a clause or a schema is revised by NIST, FedRAMP or FDA, and our copy stays at the old version.

D. Invention

We invent a term for something a standard already names. Every invention is a private dialect that an auditor, a partner or an agent must learn.

Why it matters more for us

Most of what Intellectual Frontiers builds is regulated by United States law: federal security (NIST, FedRAMP), medical-device quality (FDA's QMSR, 21 CFR Part 820) and electronic records (21 CFR Part 11). For regulated work, "we meant the same thing" is not a defence. The words must be the law's words, the evidence must trace to a requirement, and the requirement must trace to its authority. A private vocabulary makes every audit a translation exercise.

And it matters more when agents write code. An agent works from whatever it can read. If the specification, the ontology and the code disagree, the agent will pick one, confidently.

Honest limit

Drift can be reduced, not eliminated. A type checker cannot check prose against code. Mizan narrows the gap with typed data, traceable identifiers and deterministic checks, and it states plainly what only a person can judge (section 14).

03Two languages

We keep specifications, ontology and code in two vertically integrated languages: natural language and TypeScript 7 or later. Every additional language or format is another place for facts to drift.

Natural language: specifications

Markdown, in Spec Kit's layout. It states what must be true, for people, auditors and agents. Requirements are written with RFC 2119 keywords and EARS patterns (section 5).

TypeScript 7+: everything else

The ontology, the code, the tools, the tests and the configuration. Bun is the default runtime, Node 26 the backup, so the same code runs on servers, workstations and devices.

Why TypeScript

  • Modern and strongly typed. Types are checked at compile time, and algebraic types (discriminated unions, branded types, exhaustive switch) let us state facts so that a wrong one does not compile.
  • Interpreted, and compilable. It runs as it is under Bun or Node, and compiled forms are available where they are wanted.
  • Portable. Servers, workstations and devices, on Linux, macOS and Windows.
  • Known. Popular with people, and known to every AI agent.
  • One language for ontology and code. The words code branches on are the ontology's code lists, imported as a union type, never typed twice.

What this rules out

A fact, a setting or a schema is not kept as source in YAML, JSON, XML, Turtle or SQL. Those are generated from the TypeScript, marked .auto., checked for staleness, and never edited by hand. Third-party files (a lockfile, a vendor's manifest) are theirs, and need no exception.

The exception that proves the rule: integrations

Best tool for the job, recorded

Code that integrates with, extends or plugs into another system is TypeScript 7 when possible. Where TypeScript does not support what the job needs natively, and a hand-written minimal parser or client would not be good enough, it is not only allowed but incumbent to choose and use the best stack (format, language or tool) for that job. An integration that works matters more than language purity.

Each such choice is a typed Exception in the ontology, so it is visible, bounded and tested:

FieldWhat it records
Tool and language or formatWhat is used, for example an XML reader or a SHACL validator.
Why not TypeScriptWhy TypeScript or a hand-written parser is not enough.
Pinned versionThrough the packaging specification, so the supply chain knows it.
IsolationA typed TypeScript wrapper with files in and files out, so nothing else depends on the tool.
PlatformsWhere it runs. Its tests run only there.
Real-tool testsTests that run the real tool, never a stand-in.

04Mizan and GitHub Spec Kit

Should we move to GitHub Spec Kit, or to another well-known format? We looked at what each does and does not do, and decided: use Spec Kit as the method, and keep a thin profile for what it does not do.

What we found

Our harnesses had grown three dialects. Two of them (stolos and another harness) already work in GitHub Spec Kit: .specify/, a constitution, the /speckit-* commands, and a specs/NNN-name/ folder with spec.md, plan.md and tasks.md. Commons had a third, its own format with a register of numbers and a register of proofs, which was also called "spec-kit" and so collided with the real one.

What Spec Kit gives us

  • A workflow agents already know: specify, clarify, plan, tasks, implement.
  • A constitution that governs a repository.
  • Templates with user stories and Given, When, Then scenarios.
  • A community, and tooling that moves.

What it does not give us

  • A register of numbers that never gap or repeat.
  • A mapping from every requirement to what proves it.
  • Tracing from source files and ontology terms to requirements.
  • A shared ladder, standards rules or drift controls.
The decision

Adopt Spec Kit as the method. Do not adopt it as the conformance standard. Mizan is a profile: it keeps Spec Kit's commands, constitution and feature files, and adds only the registers, the tracing, the ladder, the requirement syntax and the standards rules. Replacing our register and tracing with Spec Kit's would lose the thing the compliance chain depends on.

The rename

Commons' own format is now 0003-mizan, its checker commons/tools/mizan-check.ts (the old spec-kit-check.ts remains as a wrapper for one repin cycle, so harnesses that run it keep working). The folder commons/spec-kit/ keeps its name for the natural-language specifications; Mizan's documentation says that it holds the Mizan profile, to avoid the old confusion. Built

Why not another format?

AlternativeWhat it is good forWhy not instead of Mizan
OpenSpec, Kiro-style specsAgent-driven spec workflowsSame gap as Spec Kit: no proof register, no tracing, no standards rules. We borrow ideas (EARS) instead.
Architecture decision recordsRecording one decisionNot requirements. We keep a typed Decision for terms that are unaligned.
OSCALControls, assessment, evidenceExactly right for controls, wrong for describing features. We map the proof register to OSCAL where it can say it.
Gherkin / CucumberExecutable scenariosWe use its Given, When, Then shape for scenarios; our tests are TypeScript with proves(...).
TLA+, AlloyFormal modelsValuable for some systems, not for everything. Not ruled out for a specification that needs it.

What Mizan adds, and what Spec Kit keeps

The profile adds what Spec Kit does not state: the gapless registry.tsv and the proof register enforcement.tsv, the tracing of source files, tests and ontology terms to requirements, the ladder, the requirement syntax (RFC 2119 and EARS) and the standards rules. IFCCM departs from Spec Kit's words in one place: the unit of change is a capability, not a feature, and what Spec Kit calls a feature is a capability here. The specifications of IFCCM, IFQS and IFWS (0020 to 0025) are themselves written in Mizan's form. Mizan stays the name of the specifications and ontology strategy; the workspace product is IFWS and has its own ontology.

Spec Kit moves quickly (it already has a deprecated command and a new one for converging), so each Mizan specification says which version of Spec Kit's templates it follows where it departs from them.

05How a specification is written

Mizan adds a small, strict layer on Spec Kit's format. The checker enforces it; new rules start as warnings.

The folder and its registers Built

  • registry.tsv: every specification number ever assigned, in force or retired, with no number twice and no gap.
  • specs/NNNN-slug/spec.md: one folder per specification. Requirements are - **FR-nnn**:, numbered in order and never reused; every edge case cites the requirements it exercises.
  • enforcement.tsv: exactly one row per requirement, naming its mechanism: check, gate, review or none (with the reason). This is the proof register.
  • Citing another repository's specification always names the repository: commons 0005-typescript-runtime FR-029.

One status vocabulary Built

StatusMeaning
DraftWritten, not yet built.
ActiveIn force: every requirement is proven by a test or declared as reviewed.
DeferredOut of scope until its owner decides.
SupersededReplaced by another specification.
AdoptedThe word commons used before Mizan. Accepted until every specification has moved to Active.

Requirement syntax: RFC 2119 and EARS Built, warn-only

A vague requirement cannot be tested, and a requirement that is not testable cannot be proven. We write requirements with RFC 2119 keywords (MUST, SHOULD, MAY) in one of the six EARS patterns (Easy Approach to Requirements Syntax). EARS is small enough for an agent to follow and regular enough for a checker to parse.

PatternFormExample
UbiquitousThe <system> MUST …The checker MUST write nothing.
Event-drivenWHEN <event>, the <system> MUST …WHEN a source file has no // Spec: line, the check MUST report trace/no-spec-line.
State-drivenWHILE <state>, the <system> MUST …WHILE a term is unaligned and its Decision is missing, the check MUST warn until 90 days have passed.
Unwanted behaviourIF <condition>, THEN the <system> MUST …IF an imported source's SHA-256 differs from its record, THEN the import MUST be refused.
Optional featureWHERE <feature present>, the <system> MUST …WHERE a harness has no windowed hosts, rung 6 MUST hold only the headless hosts.
ComplexA combination of the aboveWHEN a term is added, WHILE it is unaligned, the check MUST count it.

Scenarios: Gherkin's shape Built, warn-only

Spec Kit's acceptance scenarios already use Given, When, Then. Mizan requires each scenario to cite the requirements it exercises, so a reader can walk from a story to its rules, and a checker can verify that the rules exist.

Scenario: an unaligned term with no Decision after the grace period
  Given a term added on day 0 whose basis is unaligned
  And no Decision records why
  When the check runs on day 91
  Then it fails and names the term, per 0018-standards-first FR-005

The Standards considered section Built, warn-only

A feature's plan.md has a required section naming the standards looked at and the one chosen. It makes "did you check whether a standard exists?" a question with a written answer.

The proof register and OSCAL Built

Where OSCAL can say it, the register maps to OSCAL; where it cannot, it stays as enforcement.tsv, so no proof is written twice. The proposal: a requirement is an implemented-requirement of a component-definition of the harness; a passing proof is an assessment-results observation; a reviewed requirement carries its reason there; an open finding is a plan-of-action-and-milestones item. The command that proves it, and the harness path, stay in the TSV. bun commons/ts/mizan/oscal-register.ts writes the component definition and the assessment results to commons/generated/, and --check fails where they differ from what the folder makes.

06The ladder

Our harnesses each described a ladder of rungs: a stack of layers, each relying only on those below. Mizan states it once, as typed data in commons (mz:Rung, with mz:RungKind), and each harness states its own homes as an instance of it. The ladder now has eleven rungs.

The four kinds of rung

mz:RungKind is a code list, so code branches on a type the ontology owns.

KindRungsMeaning
required0 to 7Every harness has the rung and builds on the rungs it names.
optional8A harness may have it; it relies on no rung and no rung relies on it.
observer9Records and proves what the other rungs do; required where a regulated domain is claimed; no rung relies on it.
environment10The working environment everything is built in; required where a regulated domain is claimed; it relies on no rung and no rung relies on it.

The rules

  1. Dependency direction. A rung relies only on the rungs below it that it names, and never reaches around the rung under it. An import that climbs, or skips a rung it may not, is refused.
  2. Order of work. A change is complete only when every rung it touches is updated and proved by that rung's checks, lowest first: the term in the ontology, then the requirement in a specification, then the data, the code and the documentation.
  3. Headless first. Rungs 0 to 5 are headless; rung 6 holds the headless hosts before the windowed ones; every operation a window offers is also a command or a tool.

An instance, not a copy

A harness states its ladder as individuals of the commons Rung class in its own ontology. It may add homes, checks and rely-on edges; it may not renumber, rename or drop rungs 0 to 7, and a rung it leaves empty says why. Its constitution table and the layout in its AGENTS.md are generated from those individuals between marker comments, and the generator's --check fails if either differs. Every file belongs to exactly one rung, by the most specific of the rungs' homes.

Built the tracing and layer checks (0015-trace, in the kernel), and the shared mz:Rung and mz:RungKind with the eleven rungs as typed individuals (commons/ontology/mizan/, 0016-ladder). Planned moving each harness's ladder to an instance.

The ladder is itself an invention

No standard names these rungs (ISO/IEC/IEEE 42010 and layered architecture are related, but define none of them). Under our own rule the ladder is therefore unaligned, and its justification and Decision are the first entry in the register.

07Standards first

We do not invent terms, schemas or ontologies where a well-known consensus, international or national standard exists. Most of our work is regulated by US law, so US federal, state and local law and standards get special consideration. A custom invention is treated as drift.

The order of precedence

  1. Law. US federal law and regulation, and state or local law where it applies. The law's definition is authoritative.
  2. US and NIST standards. NIST publications, OSCAL, FedRAMP, CISA and NTIA SBOM guidance, NIEM, ONC's USCDI.
  3. ISO standards. Cited by identifier and clause. ISO text is not redistributable, so we do not copy it.
  4. Broadly used vocabularies. schema.org, Dublin Core, SKOS, PROV-O, SPDX, DPV and their like.
  5. State and local standards that are not law, where they do not conflict with the sources above.

Only after all of these is a term our own.

The basis of every term Built

Every class, property, individual and code list carries a basis. A term with none does not compile.

BasisMeaningExample
adoptsIt is the standard's own term, by its IRI.dcterms:title
specializesA subclass or subproperty of a standard term.pm:PackageManager is a schema:SoftwareApplication
mapsIt has a mapping, such as skos:exactMatch, to a standard term, published as SSSOM.pm:sha256 to an SPDX hash value (candidate)
unalignedNo standard names it.The ladder's Rung
// Illustrative sketch: the specification states the requirement, not this exact code.
type Basis =
  | { readonly kind: "adopts";      readonly standard: StandardRef }
  | { readonly kind: "specializes"; readonly of: Iri; readonly standard: StandardRef }
  | { readonly kind: "maps";        readonly to: Iri; readonly relation: "exactMatch" | "closeMatch" }
  | { readonly kind: "unaligned";   readonly justification: Justification; readonly decision?: DecisionRef };

function countsAsDrift(b: Basis): boolean {
  switch (b.kind) {
    case "adopts": case "specializes": case "maps": return false;
    case "unaligned": return true;
    default: return absurd(b); // the compiler refuses a basis we forgot to handle
  }
}

Unaligned is allowed, never hidden

  • An unaligned term carries a justification: the standards looked at and why none fits.
  • It needs a Decision, a typed individual of the shared ontology that a harness may link to its own decision record. The Decision does not have to come first, but it must exist within 90 days of the commit that adds the term, a grace period that leaves room to experiment. Within the 90 days, its absence is a finding in the baseline; after it, the check fails.
  • The count of unaligned terms is the measure of drift. It is reported, and the baseline only shrinks.

The law's words

  • A term taken from law keeps the law's wording as its label, carries the law's definition as skos:definition and cites the law. It is not paraphrased, because a paraphrase can change the legal meaning.
  • Where laws differ by jurisdiction, each is its own jurisdiction-qualified individual, never one merged invented concept.
  • A requirement that comes from law cites its authority as typed data: title, part and section (for example 21 CFR Part 11, or 45 CFR 164.312).

Standards as data

Each standard is a typed Standard: issuer, name, version, location, license (an SPDX identifier) and the SHA-256 of what was imported. A newer upstream version than the pin is a finding, so drift against the world (drift C) shows up as a check result. We copy only what a license permits.

The first domains

Federal security

NIST publications and OSCAL, FedRAMP baselines and Key Security Indicators. Only the controls we cite are imported.

FDA QMSR, 21 CFR Part 820

Effective 2 February 2026; it incorporates ISO 13485:2016 by reference. Verified from the FDA and the Federal Register. ISO 13485 is cited, not copied.

21 CFR Part 11

Electronic records and electronic signatures. The text is law; authority records cite its paragraphs.

Other domains are added as products need them, and are pulled up into commons when more than one harness should read the same facts.

Mizan follows its own rule

Requirements: RFC 2119 and EARS. Scenarios: Gherkin. Mappings: SSSOM. Provenance: PROV-O. Catalogs: DCAT. Licenses: SPDX identifiers. Controls: OSCAL. The format of a standard is chosen before ours is.

Spec: Draft 0018-standards-first. Built the checks, as warnings held by a baseline that only shrinks (76 terms await a Decision; none is past its 90 days). The first audit is commons/spec-kit/audits/2026-11-standards-audit.md.

08The typed ontology

One ontology, stated once, as algebraically typed TypeScript on commons' RDF kernel. Every RDF form (Turtle, N-Triples, JSON-LD) is written from it, and none is a source.

What "algebraically typed" gives us Built

  • Branded IRIs. An IRI is checked once and carries its type; a reference to an individual of the wrong class does not compile.
  • Typed vocabularies. RDF, RDFS, OWL, XSD, SKOS, Dublin Core terms, PROV-O and SHACL are typed; a term not listed does not compile.
  • Class schemas. A class and its fields; each field is a property with a range, and the individual's type is derived from the schema. A missing required field fails tsc.
  • Code lists as unions. The individuals of a code list are a TypeScript union, so code branches on a type the ontology owns.
  • Findings as values. What a type cannot state (an unsafe integer, a malformed string) is a finding with one plain sentence.
  • Deterministic output. Canonical Turtle and N-Triples, and a SHA-256 over the whole ontology, so any change of fact changes the hash.

Using the ontology from your harness

  1. Keep your own namespace. State your terms with vocabulary(NS, {...}) and class schemas on commons' RDF kernel; import the shared classes (Rung, OntologyTerm, Decision and the rest) from commons/ontology/mizan/ and do not copy them.
  2. Take standards by import, not by hand. Write a manifest (a TypeScript module) naming the pinned standard, its versioned URL, the slice you need and where the generated module goes; run bun commons/ts/mizan/integrations/host/import.ts MANIFEST.ts. The generated module is the standard's own terms, typed; commons' packaging ontology takes schema:SoftwareApplication this way.
  3. Record the basis of each of your terms in an audit file of mz:OntologyTerm individuals (see commons/ontology/audit/packaging.ts): specializes or maps with the standard's term and relation, or unaligned with the candidates you examined. A mapping to a term your import does not hold does not compile.
  4. Run the checks. commons/ts/mizan/check.ts fails for a term with no record, holds the pending Decisions in a baseline that only shrinks, and fails a Decision past its 90 days.
  5. Publish the generated forms, not the TypeScript, to anyone outside your stack: Turtle with owl:versionIRI, SHACL shapes, JSON Schema, SKOS, SQL code-list tables, SSSOM mappings and the HTML view (commons/generated/mizan-ontology.auto.html is the example).

The four published ontologies Built

Each ontology has its own namespace and a typed record of the basis of every class and code list (mz:OntologyTerm). Each is published through the same function (publish-ontology.ts) as canonical Turtle, RDF/XML, OWL 2 functional syntax, SHACL shapes, JSON Schema, SKOS code lists, SQL tables, SSSOM mappings and an HTML view, all under commons/generated/ and checked for staleness by --check.

Tests that need those Python tools skip where they are absent.

Strengths and weaknesses, by who uses it

Inside a TypeScript stack

Strengths. Compile-time errors for wrong facts. One language for ontology and code. Refactoring tools work. No YAML or JSON to drift. Agents read and write it fluently.

Outside TypeScript

Strengths. Standard output (Turtle, JSON-LD) with standard IRIs, so regulators, auditors and other-language consumers see the standard's own terms.

WeaknessWhere it bitesHow Mizan addresses it

09IFC Mizan Integrations

The module of Mizan extensions and plugins at commons/ts/mizan/integrations/. It does two jobs: bring outside ontologies into our typed TypeScript form, and turn ours into well-known, reusable ontologies. Spec: Draft 0019-mizan-integrations; Built.

Import: only when necessary

  1. An import is made only where a term or schema a specification uses is not already available, and it names the slice it needs, never a whole standard.
  2. It refuses a source whose SHA-256 or license differs from its Standard record.
  3. It writes a generated .auto.ts module whose header names the source, version, hash, license and generator; its terms have the basis adopts.
  4. What the typed form cannot hold is a finding, never a silent drop.
  5. The written graph, in canonical N-Triples, must equal the source's graph for the slice (the round trip).
  6. An ImportRecord keeps the provenance in PROV-O: what, from where, when, by which generator, with which hash.
There is already a precedent

The stolos engine vendors FedRAMP's machine-readable rules under a pinned commit and SHA-256 and generates TypeScript from them, and does the same for OCSF. The integrations module generalizes that pattern, and re-importing what we already use (schema.org, PROV-O, DPV, OSCAL, OCSF) turns hand-written copies into generated ones.

Export: to well-known forms

Turtle, N-Triples, N-Quads and JSON-LD already come from the kernel. The module adds SHACL shapes and JSON Schema (from class schemas), SKOS concept schemes and SQL code-list tables (from code lists), SSSOM mapping files (from terms whose basis is maps), and later OWL, RDF/XML and a DCAT catalog entry for each published ontology. We use SSSOM and DCAT rather than invent a mapping or catalog format, which is the standards-first rule applied to our own tooling.

Never published without a person. Where one of our terms could improve a standard (schema.org, SPDX), the module prepares a proposal bundle. It sends nothing.

The plugin model Built (rules); importers and exporters are typed records

// Illustrative sketch of the typed integration record.
interface Integration<In, Out> {
  readonly id: string;
  readonly direction: "import" | "export";
  readonly from: Format;
  readonly to: Format;
  readonly standard: StandardRef;
  run(input: In): Result<Out, Finding[]>;  // errors are values, never thrown
}
  • A registry looks integrations up by their formats; no any, no non-null !, exhaustive switch over every union.
  • Mizan's own checks (the EARS rules, the standards rules) are plugins through the same extension point, so a harness can add its own rules without a fork.
  • Two layers: pure/ (functions over text, no effects) and host/ (fetching, files, pins).
  • TypeScript 7 first. Where it cannot do the job and a hand-written parser would not be good enough, the best stack is used through a typed Exception (section 3). XML-based formats (RDF/XML, NIEM's XSD) are the likely first case, decided when the first one is needed.

10IFCCM: change control

Intellectual Frontiers Capabilities Configuration Management (0020-ifccm, ifccm:) is how a harness controls change. The unit of change is a capability, every commit names its issue, and each requirement can be followed from its issue to the test run that proved it. The abbreviation is never used as "CCM" alone: that is also the Cloud Security Alliance's Cloud Controls Matrix. Built (M2) Spec: Draft

A capability is the unit of change

One ability of a harness that can be named, specified, built, proved and released. Each area (a rung, or a subject) has one parent change request, and each capability is a child (sub-issue) of it.

Every commit names an issue

On a line of its own: Refs #N for work toward it, Closes #N for the commit that finishes it. Other words (Fixes, Resolves, Closed) are findings. With --strict, Closes on an issue whose checkboxes or Done when are not done is a finding too.

Warn, then gate

Until a harness declares its production day, a finding is a warning held by a baseline that only shrinks. From that day it is a gate. A declaration that relaxes in Git history is itself a finding (changes/gate-relaxed).

Authority is kept apart

What a specification binds, a Decision authorizes, a check verifies and an issue only plans. A departure with no Decision is a finding; so is a Decision approved by the change's own author where the harness declares a regulated domain.

The trace chain

The check follows each requirement through six stages and reports the first stage with no link: issue (Refs/Closes), requirement, ontology term, code (// Spec:), test (proves([...])) and quality run. A generated view lists the capabilities touching each rung, with --check.

The command

bun commons/ts/mizan/changes.ts [--range A..B] [--strict] [--declaration FILE] [--check]
bun commons/ts/mizan/changes.ts --capability-trace --range A..B [--issues FILE] [--terms FILE] [--rungs FILE] [--format json]
bun commons/ts/tools/changes.ts   # the same; the result is kept as a quality record

Exit 0 is clean, 1 findings, 2 usage, 3 environment. The host (GitHub, GitLab or plain Git) is reached through one interface, GitHostClient. On plain Git, or where the host cannot be reached, the strict rules are not_run with their reason, never a pass. Only what a specification folder can judge offline (the shape of the declaration) is wired into holdHarness as a rule plugin; the commit rules need a range and belong to the command.

Where a harness has no Git host account, --capability-trace makes the chain offline: from the Refs and Closes lines of the commits of a range, the requirements of the specifications, the mz:definedBy of the ontology's terms (a JSON file, or a module loaded by its file: URL), the Spec: and Proves: lines (after two slashes or in a block comment) and a quality record, it gives for each capability and requirement the terms, code and tests on each rung and the stage where the chain ends, as a table or as JSON. A harness whose specifications are numbered with three digits, or whose registers are in another folder, says so to mizan-check.ts and check.ts with --register, and gives the proof register's path to oscal-register.ts with --enforcement.

Regulated domains, and what this is not

A harness declares from a code list of five domains: federal security (NIST SP 800-53, FedRAMP), device quality (21 CFR Part 820, which incorporates ISO 13485), electronic records (21 CFR Part 11), device software (IEC 62304) and trust services (SOC 2, ISO/IEC 27001). The specification maps its parts to those standards as mapping statements. It does not claim that any harness complies with any of them: it keeps the evidence an assessor would ask for.

11IFQS: the quality system

Intellectual Frontiers Quality System (0021-ifqs, 0022-trust, ifqs:) is based on Operational Truth: what is true of a system is what the system reports when it runs, kept as evidence anyone can check, with the grade of that evidence shown, and with a failure opened as a nonconformance by the system itself. A person's statement is recorded, and graded below a run. Tiers 0 and 1 built Tier 2 in progress

Tier 0: evidence exists Built (M3)

  • One canonical record per run. An OpenTelemetry log record per case (OTLP/JSON, the OpenTelemetry test attributes, a CTRF-shaped body), extending the test record of 0008-test-evidence. Outcomes are pass, fail, skip, todo, cancelled and not_run, which carries its reason and is never counted as passed.
  • Immutable files, chained. quality/evidence/YYYY/MM/DD/<run>.json, one file per run, never edited (a writer refuses to overwrite). Each file names the hash of the one before it (ifc.quality.previous.sha256), so a verifier finds the first record that does not match.
  • An append-only quality branch (an orphan branch written with real Git), signed through Git's own signing where configured, with a note on the tested commit under refs/notes/quality.
  • Renderings, on demand: JUnit XML, CTRF, SARIF, TAP and the documents of ISO/IEC/IEEE 29119-3. The command commons/ts/quality/quality.ts has record, verify and render; ifc test is unchanged.

The evidence grade

GradeMeaning
E0 noneNo record of any kind.
E1 statedA person or an agent says it is met; nothing ran.
E2 reviewedA review is recorded, by a person or by an agent (said to be an agent's).
E3 testedAn automated run proved it and its record exists.
E4 attestedThe run is kept on the quality branch, chained, signed and linked to its commit, so a third party can verify it.
E5 observedA probe of the system in operation reports it met.

Tier 1: the system reports itself Built (M7)

  • Grades and review debt attached to each requirement of the proof register, the debt as a number.
  • Freshness. A proof is fresh, due or stale. A proof older than its requirement's last change, or whose tested commit is not an ancestor of the specification's last revision, is stale, and a stale proof opens a nonconformance by itself.
  • Nonconformance and CAPA as typed, append-only records. A CAPA is open, then verified when a named test passes in a later run, then closed only when a named person approves, recorded as a Decision. The person is data in the record, never inferred.
  • Objectives. The SC-NNN success criteria of the specifications are read as quality objectives with targets and error budgets, emitted as OpenTelemetry metrics.
  • An index of all of it, deterministic, generated from the branch and --checkable; commands index, freshness, nonconformances, capa open|verify|close, register, tier and attest.

Tier 2: people see and prove In progress (M9)

Being built now, in commons/ts/quality/: the assessor pack (a deterministic archive of the records, their chain, the index and the crosswalks, with an offline verify-pack that checks every hash, the chain and the signatures with no network); the Trust page (0022-trust, a generated page and JSON, redacted by audience: public, assessor, internal; failures and open nonconformances included); attestation by recorded sample (a person samples records at random with a recorded seed); pre-registered test plans (a plan committed before the run, its hash recorded in the run); mutation-run records for proof strength; and agents performing reviews, graded below a test run and sampled by a person. The console (a user interface) belongs to a harness and is not built here.

Evidence, not a verdict

The Trust page states what was proved, how and when. It does not say that a harness conforms to a standard, and it does not claim compliance with any regulation.

12IFWS: workspaces

Intellectual Frontiers Workspaces (0023-if-workspaces, 0024-ifws-host, 0025-ifws, ifws:) is the managed place on a computer where repositories, worktrees, approved tools, policy and generated workspace files live. It is rung 10 of the ladder. Its command is ifws. Built (M4 to M6) Specs: Draft

One root, a layout that mirrors remotes

$IFC_WORKSPACES_HOME (default $HOME/workspaces, %USERPROFILE%\workspaces on Windows). Repositories are at <home>/<git-host>/<path>/<repo>. IFWS's own area is <home>/.if-workspaces/: the typed manifest, generated *.auto.* files, the state record, evidence, tools and hooks.

Portable by construction

Branded path types reject Windows reserved names, trailing dots and spaces, forbidden characters, over-long names, non-NFC Unicode, case-fold collisions and paths over 259 characters. No symlinks are needed.

Plan, then apply

plan(desired, observed) is a pure function. Updates are fast-forward only; a tree with unpushed commits or changes is never deleted; one writer holds a lock; refusals say why.

GitHub, GitLab, plain Git

One interface, three adapters. GitLab groups nest to any depth. A token is read only from the environment (GITHUB_TOKEN, GH_TOKEN, GITLAB_TOKEN, CI_JOB_TOKEN) and never stored or logged. Plain Git answers only the capabilities every host shares.

The command

ifws is a controller in the style of git: ifws name runs the module ifws-name, found among typed built-in modules, then modules a workspace registers in .if-workspaces/modules.auto.json, then executables named ifws-* on the PATH. Built in: init, plan, apply, status, doctor, verify, render, worktree, list, help, shell, setup, tools and hook. Exit codes: 0 ok, 1 findings, 2 usage, 3 environment. It manages only the workspace; it is not a general Mizan or IFC controller and does not front ifc.

  • Typed templates, not a template language. The manifest is the source state; typed TypeScript functions generate *.auto.code-workspace, lefthook.auto.yml, AGENTS.auto.md and the hooks. A state record lets ifws verify see a hand edit. Git settings go to each repository's local configuration and core.hooksPath, never to the global configuration.
  • ifws setup is a dry run by default; --apply is required to change anything. It is the only command that installs. It sets core.longpaths per repository, and returns the exact steps to run where elevation is needed.
  • Tools are pinned. The catalog gives each tool a version and a per-platform URL and SHA-256; latest is refused; the hash is checked before anything is written. git, bun and node are verified by a version probe and never installed. A tool or an ifws-* module outside the catalog is informational for 90 days from first seen, then a warning. The catalog and the inventory export as OSCAL, SPDX and CycloneDX.
  • Secrets fail from day one. A plaintext token, private key block or credential in a URL in managed configuration is an error, and the scan never prints the secret. Signed commits are required where IFCCM declares a regulated domain and warned elsewhere.
  • ifws shell <bash|zsh|fish|pwsh|nu> prints a reversible snippet to standard output and writes nothing: the root, the tools on the PATH, completions and one function, wcd, that changes to a repository by name. --install shows a diff of one marked block and asks; --uninstall removes exactly that block.
  • Evidence. Every run writes records in the IFQS shape under .if-workspaces/evidence/, with not_run and its reason where something did not run.

Credits

The layout and the ensure, status and doctor ideas come from the earlier workspace tools of Intellectual Frontiers' founder. chezmoi (Tom Payne and contributors, MIT) is credited as inspiration: source state and target state, templates over data, apply, diff, verify and a state record. IFWS uses no chezmoi code or program and is not a dotfiles manager. The convention that git foo runs git-foo is Git's. See commons/ts/workspaces/CREDITS.md.

13AI-first, AI-native

AI-first means we assume an agent will read, write and change this system every day. AI-native means the artifacts are designed for that: structured, identifiable, checkable. The central principle is the same in both: the agent proposes; deterministic checks and a person decide.

Why this design suits agents

One entry point

AGENTS.md tells an agent what the repository is, which rules bind and what to run. The constitution and the ladder tell it where a change belongs.

Stable identifiers

FR-nnn, // Spec: lines and proves([...]) let an agent walk from a requirement to its code and its proof, and back, without guessing.

Typed ground truth

The ontology and its code lists are typed TypeScript. An agent that invents a term or misspells a value gets a compiler error, which is an instruction it can act on.

Findings as sentences

Every check reports a place and one plain sentence. An agent can read, understand and fix a finding without a human translating it.

Regular requirement shapes

EARS and Given, When, Then are patterns models produce reliably and checkers parse. Vague prose is the hardest thing to verify.

One language

TypeScript is known to every agent. Ontology, code, tools and tests in one language mean fewer context switches and fewer places to hallucinate a format.

The agent's working rules

  1. Read first. AGENTS.md, then the constitution, then the specification you are changing.
  2. Specification before code. Use the Spec Kit workflow (specify, clarify, plan, tasks, implement) and, in a Mizan harness, climb the ladder lowest rung first.
  3. Look up before you coin. Before adding a term, search the ontology and the standards in the precedence order. Write the result in Standards considered. If nothing fits, mark the term unaligned, justify it and record a Decision.
  4. Cite. Every source file names the requirements it implements; every test names what it proves.
  5. Run the checks and read the findings. A finding is the specification talking. Baselines only shrink: never add a baseline line to make a check pass.
  6. Never edit generated files. Change the ontology and run the generator.
  7. A person decides what only a person may: publishing, accepting an unaligned term's Decision, anything outward-facing.

What agents are not trusted with

Self-verification

An agent's statement that its work matches the specification is not evidence. The check is. And no check can tell whether a requirement means what its authors meant: that is what review in the proof register is for, with a named person and a reason.

AI-native, concretely

  • Specifications are data. A registry, a proof register, parseable requirements and typed scenarios. A model can be asked "which requirements have no proof?" and a program can answer it.
  • The ontology is a context an agent can load. Typed individuals, code lists and per-area about.ts facts are compact and precise, unlike a prose glossary that has drifted.
  • The generated artifacts are for everyone else. Turtle, SHACL and JSON Schema let non-TypeScript tools and non-agent readers see the same facts without learning our stack.
  • Standards-first helps models. Agents already know NIST, schema.org and PROV-O. An invented dialect is something no model has seen; a standard's own term is something it has.

The warn-first discipline

A new rule never fails what a harness already holds. It starts as a warning, with a baseline file listing today's findings. A new finding fails; a baseline line that no longer occurs also fails, so the baseline can only shrink, and you cannot "fix" a check by adding a line. This is the same mechanism stolos already uses for its trace and layer checks.

What the audits found

  • The packaging ontology has 61 terms: 5 specialize schema.org, 5 map to a schema.org property, and 51 are unaligned, each with the candidates still to examine. Across the ontologies, 76 terms await a Decision; all are within their 90 days and are held by a baseline that only shrinks; a Decision past its day fails whatever the baseline holds.
  • stolos has the best precedent for importing: vendored, pinned, hashed, generated. The integrations module generalizes it.

Verified for real

  • OSCAL 1.2.3 is the newest release (tags 1.2.4, 1.2.5 and 1.3.0 do not exist) and is public domain and CC0. NIST SP 800-53 Rev. 5.2.0 (1,196 controls with enhancements) imports from a pinned oscal-content commit in 0.7 s.
  • A slice of the real schema.org 30.1 Turtle, fetched by pinned SHA-256, makes exactly the vocabulary commons used to write by hand. The reader's triple counts on schema.org (17,515), PROV-O (961) and SHACL (1,112) agree exactly with rdflib; sssom-py parses the SSSOM file; pySHACL finds the ontology conforms to its own shapes and rejects a broken individual; ROBOT reads the generated OWL.
  • TypeScript 7 checks a 5,000-entry code list in 0.18 s and 85 MB, linear in its entries.
  • The GitHub, GitLab and plain Git adapters are tested with recorded exchanges written from the hosts' documented answers, a real HTTP server on loopback for the live transport, and real Git repositories. The change check, the quality branch (including signing with an SSH key made in the test where ssh-keygen exists) and ifws run as programs on Bun and on Node 26 against real temporary repositories.

Not verified

What we have not seen work
  • Windows. The Windows path rules are pure and tested everywhere, and CI includes a Windows job, but some of the tests that run Git, shells and the file system have not been seen to pass on Windows.
  • Private repositories on GitHub and GitLab. The adapters map an unauthenticated answer for a private repository to unauthorized or not-found as the host says, and take a token only from the environment; this is tested against recorded answers, not against a real private repository on either host.
  • The shell snippets for zsh, fish, PowerShell and Nushell are generated and were read, not run in those shells. Only bash is run.
  • The licenses and redistribution terms of the remaining candidate importers (DPV, SPDX, CycloneDX, FHIR, NIEM), before each first import; SPDX 3 could not be fetched from the build environment.
  • Compliance. Nothing here claims that any harness complies with any regulation or standard. IFCCM, IFQS and IFWS keep evidence an assessor can check.
