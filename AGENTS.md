# `.github` — agent entry point

This repository is small on purpose: the organization's public profile (`profile/`), the machine setup (`bin/`: the two one-command installers of agora, `agora-install.sh` and `agora-install.ps1`, which sign GitHub CLI in, copy `erga` and run the installer in it), `commons/` and the tests
(`tests/`). `commons/` holds what any company or harness of Intellectual Frontiers may use, with its own ontology, specifications and generated tables (see `commons/about.ts`, and the site at <https://intellectual-frontiers.github.io/.github/>); a capability goes there when more than one harness should read the same facts. Its specifications are in `commons/spec-kit/`, not in a company's repository. The installers' specification is `274-agora` (FR-096) in `erga`, the company's private monorepo, like every other specification of erga. Everything else (erga itself, its specifications, ontology and content) is in the private `erga` repository; do not add any of it here.

- **The development loop is not the release loop** (commons 0001-libraries FR-011, FR-012). The loop you run between edits and before every push is `bun run dev:check` at the root (once: `bun install`): it finds the libraries your working tree changes since `origin/main` and the libraries whose own sources import them, links
  every library under `commons/node_modules` (a library imports another by its package name, and the `exports` of each package are its sources, so a local import is the checkout, never a copy from npm and never a relative path out of the folder), type-checks them with TypeScript 7 (a second a library) and
  runs their tests, each library in its own `bun test` process and several at a time, and prints a short summary (`--only NAME`, `--files A,B`, `--all`, `--list`, `--no-tests`, `--bail`; `bun run dev:check --help`). `bun run repoctl prove [--why|--plan]` is the proof of a change by its blast radius (commons repoctl 0008-repoctl-prove: the change classes, the fingerprint of each library's public types, the importers of the changed symbols, tests selected by imports and cached by content, and the reason for every proof left out; `commons/docs/guides/proof-by-blast-radius.md`), and `ci` writes the same plan to the summary of its run. `dev:check` proves less than a library's `verify` and says so; a change to `commons/libraries`, to a specification or to a manifest wants that library's `bun run verify` as well (seconds, in its folder).
  CI runs the rest, once, in one workflow: `.github/workflows/ci.auto.yml` plans (`commons/libraries/src/plan.ts`, the same affected code) and runs `verify` and the tests on Node 26 for the libraries a push or pull request affects, on Linux, and on Windows and macOS only for the libraries whose record in `LIBRARY_CI` names them
  (`system`, `net`, `headless`, `libraries`: code of their own for those systems); the job `ci` is its one result. A library has no workflow of its own; registering one is a folder with a manifest. `tests` and `docs` stay as they are.
  **WIP-push often**: a fork commits and pushes small steps to `main` as soon as `dev:check` passes (`bun run repoctl merge origin/main` first, which makes a generated file that conflicts again and never leaves one to be hand-merged; never force-push), so that forks meet in small merges and CI proves each step while the next is written. `bun run repoctl commit -m "Subject" --refs N` makes the commit (the identity, the trailers, no `.claude/`, no `node_modules`, no secret, and no stale generated file), and `git push origin HEAD:main` pushes it. The release (versions, register, packing, publishing) is a separate, rarer act and is not done per push.
  **`repoctl` is a generic host** (commons repoctl 0009-repoctl-config, 0010-repoctl-host): every fact it knows of this repository (the generators of its generated files, its checks, the commit identity and trailers, the hygiene policy and the optional verbs) is in `repoctl.config.ts` at the root, and a generator or a check is added there and nowhere else; the same package, installed from npm, operates any other repository with its own configuration.
  **Versions grow at the release, never per push** (commons 0026-works-versioning FR-022, FR-041; libraries 0001-libraries FR-013 to FR-015): do not raise a `version` in `release.ts`, `library.ts` or `package.json` when you change a library; `versions check` finds only a record that is wrong, an identity that changed and a version that went back.
  The release is one command, `bun run repoctl release plan` (what it would do, from the tags; writes nothing) and `bun run repoctl release apply` (`bun run release plan|apply` is the same program of the libraries, which Repoctl wraps and follows with every generated file of its table). **In `single` distribution mode, the mode of this repository (commons 0036-distribution FR-019, FR-027), the release is one release, `commons`: the one package `@intellectual-frontiers/commons` is raised, from the tag `commons-v<version>` and the files of every library since it, by the greatest `Impact:` of the commits that touched any library (a patch where none states one) and by the floor of the keys of its `exports`, a breaking impact raising the minor while the major version is 0; a version ahead of its tag (raised by hand) is released as it is unless the registry holds it with other files; the versions of the libraries are not raised.** Where `per-library` mode is asked for (`--distribution per-library`, or `IFC_DISTRIBUTION=per-library`) the rules are the per-library ones: it raises each library changed since its last tag by the greatest `Impact:` of its commits, a patch where none states one, its importers by at least a patch, and releases a version that has no tag as it is unless npm already holds that version with other files, which raises it (`--raise NAME[=IMPACT]` raises any library, `--offline` does not ask the registry); the greater of the `Impact:` of the commits and the floor of the keys of the package's `exports` against the version the registry holds raises a library, and a library is released unless its manifest carries a typed `held` reason not to (`tests-only`, `unfinished`, `owner-blocked`); `plan` says per library why, and which are not released and for what. `apply` refreshes the lockfile of each package it releases, makes the generated files once, runs `repoctl sync`, runs the proof that packs, installs and type-checks (`tests/release/commons-package.test.ts` in `single` mode: the tarball installed with npm and Bun, every entry of every library imported on Node 26 and Bun, a consumer type-checked with and without `dom`), writes `commons/generated/release.auto.json`; commits nothing. `repoctl commit --impact major|minor|patch` writes the `Impact:` line.
  The owner commits and pushes what `apply` made (`repoctl release publish`, the releaser tier, publishes by hand behind a preview and a typed confirmation, and prints no credential) and runs the workflow `release` from main (`.github/workflows/release.auto.yml`, by hand, `publish` off by default for a dry run): it publishes the packages of the record in dependency order to the registries the record names, and the runner makes the tags (the Git proxy refuses a tag push). In `single` mode the one tarball goes to the GitHub package registry alone (`https://npm.pkg.github.com`, the job's `GITHUB_TOKEN` and `packages: write`); the npm target is the typed list `SINGLE_TARGETS` in `commons/libraries/src/distribution.ts`, off now, and adding `npm` to it is the one change that turns it on (trusted publishing with provenance, or the secret `INFRO_NPMJS_TOKEN`). `ci` packs the one package where a library changed its `exports`.
  **Environment**: the cloud environment should have Node 26 (`node --version` is `v26.x`; the commons' engines are `>=26`, the CI pin is `NODE_VERSION` in `commons/libraries/src/workflows/definitions.ts`) next to Bun; where the setup script does not install it, `node --test` runs on an older Node and fails on what Node 26 added. The setup-script lines are `curl -fsSL https://nodejs.org/dist/v26.13.1/node-v26.13.1-linux-x64.tar.xz | tar -xJ -C /usr/local --strip-components=1` and `node --version` (nodejs.org must be an allowed host of the environment; keep the version in step with `NODE_VERSION`).
- **Complete a package change in Erga** (commons 0036-distribution FR-035): release a new Commons version to the configured registry, refresh every Erga pin and lockfile to it, and install from the registry with frozen lockfiles. Run `./agora doctor`, `./agora check` and `./agora test` in Erga and run each consumer's verification commands. Review the findings and record the published version and the verification results.
- Work spec first: change the specification (`274-agora` in `erga` for the installers, `commons/spec-kit/` for commons), then the code, then the tests. Every requirement has a test or says why it has none.
- Bun is the default TypeScript 7 runtime and Node 26 the backup (commons 0005-typescript-practice). Every program and every test is TypeScript, and a test is `<kebab-case>.test.ts` written with the library `test` (`@intellectual-frontiers/test`, `proves`), found by `bun test` and `node --test` with no configuration. A library's tests are in its own `suite/` and run by its `verify`; the tests of the root are in `tests/`, type-checked by `tests/tsconfig.json`. Every `tsconfig.json` extends `commons/tsconfig.base.json`; `bunfig.toml` at the root holds the settings of `bun fmt` and `bun lint`.
  A test runs the real programs: real `git`, real `sh`, the real tools, never a stand-in for Git or GitHub CLI (a remote is a real temporary repository); what needs an account, a browser or administrator rights is left untested, and the header of the test says so.
  What CI runs before a merge (`bun run repoctl check` runs the checks of the repository below that are not a compiler, a linter or a test, in one report with a code for each finding, and `bun run repoctl sync --check` runs the generators' checks and writes nothing), which you run by hand only where your change touches it, and which is the release's whole check: at the root `bun x tsc -p tests/tsconfig.json` and `bun x tsc -p commons/tools/tsconfig.json` (which `repoctl check` runs), `bun fmt --check commons/tools tests` and the linter as `.github/workflows/tests.auto.yml` runs it; at the root run
  `bun test ./tests/*.test.ts` and `node --test "tests/*.test.ts"` (`tests/release/` is the release's), `bun commons/tools/generate-packaging.ts --check`, `bun commons/libraries/src/affected.ts --base origin/main` (the libraries a change affects, read from each library's package and imports; commons 0027-commons-libraries FR-019 to FR-022), `bun commons/libraries/src/generate-workflows.ts --check` (the workflows are TypeScript values in `commons/ts/githost/workflows/` and `.github/workflows/*.auto.yml` is made from them, never edited; commons 0030-generated-workflows), `bun commons/libraries/src/generate-ontology.ts --check`, `bun commons/libraries/src/check.ts` (the rules Mizan adds, held by `commons/spec-kit/mizan.baseline.txt`, which only shrinks; `--level L0` to `L3` runs the rules of a conformance level, L3 where none is given, and `--all` also runs every library's `verify`), `bun commons/libraries/src/libraries.ts --check` and `bun commons/tools/mizan-check.ts`. `.github/workflows/tests.auto.yml` runs all of them on every push and pull request. A test fails if a new top-level entry appears in the repository.
- A file under `commons/generated/` is generated: change the ontology under `commons/ontology/`, never the file, and run `bun run repoctl sync` before you push (it makes every generated file of the repository, in dependency order, and only the stale ones; the table of generators is `commons/repoctl/src/governance/generators.ts`); a
  test fails where it is stale. Commons specs are worked spec first, like every other (`commons/spec-kit/`).
- Commons' tools (`commons/tools/`) are strongly typed TypeScript on Bun and Node 26: options parsed once at the boundary, discriminated unions with an exhaustive `switch` (`default: return absurd(x)`), errors as values (`Result`), no `any`, no non-null `!`,
  and the one cast is `brand` in `core.ts`; the typing test checks it. The ontology is TypeScript (`commons/ontology/`, commons 0012-ontology, typed by the RDF library `commons/rdf/src/mod.ts`; Turtle is generated, never a source), decoded once (`ontology.ts`) from its typed
  values into typed records, and findings are a union with one sentence each. The tools import nothing outside `commons/tools/` but the ontology, the TOML reader of `formats` and two built-ins of `node:`, and erga runs the specification checker as `bun commons/tools/mizan-check.ts`.
- `commons/data/` (`@intellectual-frontiers/data`) is the data library: governance, the logical and physical schemas, dialects for PostgreSQL, SQLite and DuckDB, lifecycle (including reading a live database), typed tables and queries, SQL-DQ data tests, loads and extracts, the models and `arcactl`. It replaced SQL Aide, File Aide and IFRFS . Work spec first in its own `spec-kit/`, and in `commons/data` run `bun run verify` before you push; the generated typed tables of each model are written by `bun tools/typed.ts --write`.
- Repoctl (`commons/repoctl`, `@intellectual-frontiers/repoctl`) is the operations program of this repository, a headless program in the layers of Kanon; its command is `repoctl` (`bun run repoctl <verb>` at the root, `repoctl mcp` for a tool server), and its specifications are its own (`0001-repoctl-layers` to `0007-repoctl-hygiene`). Its verbs: `sync` (every generated file in dependency order, only the stale ones; `--check` writes nothing and names the generator and the command that fixes it), `merge <ref>` (a generated file that conflicts is made again, never resolved by hand; a conflict in a file a person wrote is reported untouched), `check` (every check in one report, each finding with a code that `repoctl explain <code>` explains), `status` (each library's version in the repository, on npm and in its tag; `--offline`), `hygiene` (the rule of consuming commons as a published package, for any repository), `release plan|apply|publish`, `new library <name>`, `commit -m <subject> [--refs N]`, `doctor`. A verb is a governance action with a reach policy and an audience tier (`public`, `contributor`, `releaser`; the host fixes it with `REPOCTL_TIER`, `contributor` where it says nothing), and `release publish` is a destruction of the releaser tier that needs a preview, `--yes` and the phrase the preview printed. It calls the programs of `commons/libraries` and `commons/tools` and does not make their logic again: a generator that is added to the repository is added to its table of generators, and nowhere else. Where a library's sources say their own version in a constant (`CORE_VERSION`), its manifest names it in `versionConstants`, so that the release writes it and `repoctl check` finds it where it disagrees.
- Nothing we install on a person's computer invents a folder under their home: the folders come from `runtime/dirs.ts` (commons 0031-install-locations: XDG on Linux and macOS, known folders on Windows, `XDG_*` honored everywhere), command files and shims are never written by us (a runtime's global install, WinGet, or `~/.local/bin`). No program of commons assumes where repositories are kept or how a workspace is laid out (0031-install-locations FR-005): it finds the repository by the Git root, an explicit path or variable, or the caller's configuration. A top-level folder of commons that has a `spec-kit/` of its own is an independent library (`commons/data` first; commons 0027-commons-libraries): it declares itself with a manifest, `library.ts` (name, conformance level, spec kit, verify, version, exports, distribution; read as data, L1 where it declares no level, commons 0028-conformance-levels; `distribution` is `["github"]` by default and adds `"npm"` only by a decision about that package, commons 0027 FR-015 to FR-018), and registering a library is adding a folder with a manifest and running `bun commons/libraries/src/libraries.ts`, which writes its requirement in 0027 and its row of the register (`--check` fails where they are stale). Its specifications are numbered from 0001 in its own
  registry and are never listed or proved here; this repository knows it as one requirement of 0027, proved by `bun run verify` in its folder (the compiler, the specification checker and the rules on its
  spec kit, its tests), and it imports other libraries by package name (a `link:` dependency, never `file:`), never by a relative path out of its folder. Work spec first there too, in its own `spec-kit/`.
  The folders `tools`, `generated` and `spec-kit` are not libraries: their specifications stay in `commons/spec-kit/`.
- **Commons reaches another repository only as a published package** (commons 0036-distribution FR-001 to FR-028): a repository other than `.github` installs commons from a registry and from nowhere else: a public library from npm, a private package (one of a private repository) from the GitHub package registry
  (`npm.pkg.github.com`: a scoped `@intellectual-frontiers:registry=` line in `.npmrc` and a token that may read packages). It has no Git dependency on this repository, no `file:` or `link:` dependency into a checkout of commons, no vendored copy and no fetch of raw source, and `repoctl hygiene` (a verb of the public tier that any
  repository runs; `--json` for CI) finds each of those, two installed copies of one library and an `@intellectual-frontiers` dependency that is not an exact version. Every library of commons declares `distribution: ["github", "npm"]` (a private package would declare `["github"]`); a manifest says `publishes` where the package is not `@intellectual-frontiers/<name>` (`data` publishes `arcactl`; in `per-library` mode). **The distribution mode is typed, `per-library | single`, one constant in `commons/libraries/src/distribution.ts`, and `single` is active** (commons 0036-distribution FR-019 to FR-028; `IFC_DISTRIBUTION` names the other mode for one run): the whole of commons is ONE package, `@intellectual-frontiers/commons` (folder `commons/commons`; `bun tools/pack.ts` there; `commons/libraries/src/pack-commons.ts`), holding every library (every folder with a `library.ts` that is not a metapackage, `held` libraries and `lab` included, none left out unless `SINGLE_EXCLUDED` names it), with one version and one tag `commons-v<version>`. A library is imported `@intellectual-frontiers/commons/<library>[/<subpath>]` by a consumer (the specifiers of the compiled files, declarations and shipped sources are written so; the sources of this repository keep `@intellectual-frontiers/<library>`, Kanon FR-010), its dependencies are the union of the libraries' and of the database drivers (`SINGLE_DRIVERS`), its commands are `anyfs`, `arcactl`, `ifc-docs` and `repoctl`, and its `sideEffects` name the files that do something when loaded (the telemetry host installs a port into `system`). The per-library packaging (`tools/pack.ts` of a library, the five metapackages `commons`, `foundation`, `patterns`, `programs`, `standards` with their `dependencies.auto.json`, the per-library release) is switched off, not deleted: `IFC_DISTRIBUTION=per-library` runs it, and changing the constant switches back. The root `package.json` stays `private`: it is the workspace of the development loop, never installed elsewhere. `commons/docs` is the library Docs, its command `ifc-docs` is in the one package.
- Acceptance kits (commons 0027-commons-libraries FR-025): a library may keep testing by people or agents, for the experience beyond the code, in `acceptance/` (or `oat/`, `uat/`, `aat/`): kits with made-up data, each a folder with its README and findings and its own checks, and one spec kit of their own beside them (`acceptance/spec-kit`, numbered from 0001). It is not a library, is never moved out of or into the library's `suite/` (the unit and integration tests, which run on every change), and is run apart: in `commons/data`, `bun run acceptance`. The three tiers of specifications (the repository's, the library's, the kits') only cite upward. The first is `commons/data/acceptance/arcactl-pg`.
- Documentation is the code's (commons 0011-documentation): `commons/docs/` is the library Docs (0001-docs), the generator of the site published on GitHub Pages and a package of the registry
  (`@intellectual-frontiers/docs`, command `ifc-docs`) so that other repositories build their sites with it; it reads
  only the TypeScript and the spec kit a repository's `docs.config.ts` names (commons' is `commons/docs.config.ts`, with its lenses in `commons/docs/src/lens/`). Commons keeps no README. A module's documentation is its TSDoc: the module comment says what it is, `@remarks` the longer account, `@limits` what it
  does not do; an area's typed facts (folders and what each may import, commands, rules, phases, examples) are its `about.ts`. When you change code, change its
  documentation in the same commit, in the module it is about. In `commons/docs` run `bun run verify` (the compiler, the tests, `check` on commons) before you push,
  (which also packs the package and installs it into an empty project); `bun src/main.ts build --out ../../_site` builds the
  site, which is never committed. The pages are one model with presentations (docs 0001-docs FR-007, FR-008): `--presentation web,markdown,data` is the site, and `bun src/main.ts build --presentation book --out DIR` writes the AsciiDoc of the volumes of the Commons Manuals (`DIR/<volume>/generated/<volume>.adoc`, which a book of `erga` includes; `--check` compares without writing); the volumes are `books` in `commons/docs.config.ts`. The root `README.md` is the repository's front page (what it is, its big ideas, where to go): its table of the libraries is generated between `<!-- libraries-map:begin -->` and `<!-- libraries-map:end -->` by `bun commons/libraries/src/readme.ts` (`--check` fails where it is stale; commons 0001-libraries FR-017, FR-018), so run `bun run repoctl sync` after a manifest or an `about.ts` summary changes, and write the rest of it as what is, with no history; `MIZAN.html` is the one self-contained strategy and implementation document of Mizan (embedded CSS, no external resource), kept by hand in step with `commons/spec-kit/`.
